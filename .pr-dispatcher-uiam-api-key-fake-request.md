# [Alerting v2][Dispatcher]: authenticate with the raw secret of UIAM policy API keys

## 📄 Summary

> [!important]
> Alerting v2 work behind the `alerting:v2:enabled` setting, disabled by default. See Verification steps > Environment Setup.

With UIAM enabled, action policy API keys are stored as `base64(id:essu_…)`. `DispatchStep` sent that value as is (`authorization: ApiKey <stored value>`), so Elasticsearch looked the id up as a native API key and rejected it (`unable to find apikey with id …`). The workflows engine then could not resolve a user and the execution was created as `FAILED` with `no execution identity attached`. The dispatcher now sends only the raw `essu_…` secret, using `getUiamApiKeySecret` from Task Manager, which applies the same unwrapping before building its own fake request. ES keys pass through unchanged.

Policies written with a user-created Cloud API key (a raw `essu_…` credential, which has no key id) could not be stored correctly either: `ApiKeyService` mis-parsed it and returned a generic 500, or stored garbage. They are now rejected with a 400 and the code `ACTION_POLICY_CLOUD_API_KEY_NOT_SUPPORTED`. Supporting those keys (store the raw key, keep UIAM's external verdict and mark the dispatcher request as Task Manager does) is left for a follow-up.

Scheduling the workflow also needs Task Manager to run with `xpack.task_manager.grant_uiam_api_keys: true`. With the default (`false`) it clones the request key through the native ES endpoint, which rejects raw `essu_…` credentials (`Illegal base64 character 5f`). This PR sets it for the Scout serverless config and for local development, but how to guarantee it elsewhere is not part of this PR. A serverless project deployed from the first commit of this PR (without that setting) ran the executions correctly, according to a review, so deployed serverless probably already has it. That has not been verified in the deployment configuration.

## Changes
- `DispatchStep.craftFakeRequest` sends `getUiamApiKeySecret(apiKey)`; unit tests for a UIAM key and an ES key.
- `ApiKeyService` rejects a raw Cloud API key with `Boom.badRequest` and the new error code `ACTION_POLICY_CLOUD_API_KEY_NOT_SUPPORTED`, which covers create, update, upsert and API key rotation; documented in the errors README, with a unit test.
- Scout: `workflows.waitForSuccessfulExecution` helper, and an API test that checks that a policy runs its workflow to completion (stateful and local serverless), using a least-privilege role and a user session to create the policy.
- Scout: an API test that checks that every write route rejects a Cloud API key (local serverless, using the Mock IdP organization key).
- Scout: `xpack.task_manager.grant_uiam_api_keys=true` in the `alerting_v2` serverless Observability config.

## 🧪 Verification steps

</summary>

### ⚙️ Environment Setup

Run local serverless Observability with UIAM, using a fresh environment, and add this to `kibana.dev.yml`:

```yaml
xpack.alerting_v2.enabled: true
uiSettings.globalOverrides.alerting:v2:enabled: true
xpack.task_manager.grant_uiam_api_keys: true
```

```bash
yarn es serverless --projectType=observability
yarn serverless-oblt
```

### ✅ Happy Path
1. Create a workflow and an action policy whose destination is that workflow, from the UI or with a user session.
2. Create an `alert` rule that breaches, so there are `type: "alert"` events in `.rule-events`.
3. Wait for the dispatcher tick (every 5s).
4. The workflow has a completed execution. It is not `FAILED` with `no execution identity attached`.
5. Create or update an action policy with a Cloud API key (`Authorization: ApiKey essu_…`). The response is a 400 with `code: ACTION_POLICY_CLOUD_API_KEY_NOT_SUPPORTED`, and the policy is not created or changed.
6. Run the unit tests:
   - `node scripts/jest x-pack/platform/plugins/shared/alerting_v2/server/lib/dispatcher/steps/dispatch_step.test.ts`
   - `node scripts/jest x-pack/platform/plugins/shared/alerting_v2/server/lib/services/api_key_service/api_key_service.test.ts`
7. Run the Scout tests against local serverless Observability:
   ```bash
   node scripts/scout.js start-server --arch serverless --domain observability_complete --serverConfigSet alerting_v2
   node scripts/scout.js run-tests --arch serverless --domain observability_complete --testFiles x-pack/platform/plugins/shared/alerting_v2/test/scout_alerting_v2/engine_dispatcher/api/tests/dispatch_workflow_execution.spec.ts
   ```

### ⚡️ Edge Cases
- Without `xpack.task_manager.grant_uiam_api_keys: true`, the dispatch still fails, now with `Illegal base64 character 5f` from Task Manager.
- Stateful (ES API keys): the header is unchanged, covered by a unit test.
- `bulk_update_api_key` with a Cloud API key returns 200 with one error per policy, not a 400.
