# DEx API Performance Testing Harness

Standalone performance testing harness for the Security Solution prebuilt rules
batch install endpoint (`POST /internal/detection_engine/prebuilt_rules/installation/_perform`).

Orchestrates benchmark runs across N cloud-deployed serverless security projects,
writing structured results into a dedicated Elasticsearch cluster for
Kibana dashboard visualization.

## Prerequisites

- Node.js 18+ with `npx tsx` available (ships with the Kibana repo)
- [QAF](https://docs.elastic.dev/appex-qa/qaf/getting-started) installed and configured
- `jq` installed
- A **results cluster** (separate serverless project) for storing performance data

## End-to-End Workflow

```bash
cd x-pack/solutions/security/test/dex_api_performance

# 1. Provision target environments + generate config
./provision_environments.sh \
  --cold-count 3 \
  --warm-count 1 \
  --results-es-url https://results.es.us-central1.gcp.staging.elastic.cloud:443 \
  --results-api-key "YOUR_BASE64_API_KEY"

# 2. First-time setup: create index templates + data views on results cluster
npx tsx run.ts --config environments.json --setup-only

# 3. Run all scenarios
npx tsx run.ts --config environments.json

# 4. Tear down target environments
./teardown_environments.sh --config environments.json
```

## Provisioning Environments

The `provision_environments.sh` script creates serverless security projects via
QAF and outputs an `environments.json` config file ready for the harness.

```bash
./provision_environments.sh \
  --cold-count 3 \
  --warm-count 1 \
  --results-es-url https://results.es:443 \
  --results-api-key "base64key" \
  [--region gcp-us-central1] \
  [--iterations 5] \
  [--prefix dex-perf] \
  [--output environments.json]
```

| Flag | Default | Description |
|------|---------|-------------|
| `--cold-count` | 3 | Number of pristine cold-boot projects |
| `--warm-count` | 1 | Number of reusable warm projects |
| `--results-es-url` | (required) | Results cluster ES URL |
| `--results-api-key` | (required) | Results cluster API key |
| `--results-kb-url` | (auto-derived) | Results cluster Kibana URL (overrides auto-derive) |
| `--region` | `gcp-us-central1` | Cloud region for projects |
| `--iterations` | 5 | Default iterations per scenario |
| `--prefix` | `dex-perf` | Project name prefix |
| `--output` | `environments.json` | Output file path |

## Running the Harness

```bash
# Run all scenarios
npx tsx run.ts --config environments.json

# Run specific scenarios only
npx tsx run.ts --config environments.json --scenarios warm_boot,scalability

# Dry run (validate config + connectivity, no tests)
npx tsx run.ts --config environments.json --dry-run

# Setup only (index templates + data views, no tests)
npx tsx run.ts --config environments.json --setup-only

# Verbose logging
npx tsx run.ts --config environments.json --verbose
```

## Tearing Down Environments

The `teardown_environments.sh` script reads the `environments.json` and deletes
all target projects via the QAF Python API directly, bypassing the
`SecurityProjectTask.delete()` path that requires org-member-list permission.

```bash
# Preview what would be deleted
./teardown_environments.sh --config environments.json --dry-run

# Delete all target projects (with confirmation)
./teardown_environments.sh --config environments.json

# Skip confirmation
./teardown_environments.sh --config environments.json --yes
```

The results cluster is never deleted by teardown.

## Configuration Schema

The `environments.json` file (generated by `provision_environments.sh` or
created manually) defines the results cluster and target environments:

```json
{
  "results_cluster": {
    "es_url": "https://results.es.us-central1.gcp.staging.elastic.cloud:443",
    "api_key": "base64encodedapikey",
    "kibana_url": "https://results.kb.us-central1.gcp.staging.elastic.cloud:443"
  },
  "defaults": {
    "iterations": 5,
    "memory_sample_interval_ms": 1000,
    "change_history_enabled": true
  },
  "max_parallel_environments": 3,
  "environments": [
    {
      "id": "dex-perf-cold-1",
      "role": "cold_boot",
      "kibana_url": "https://...",
      "es_url": "https://...",
      "credentials": "user:pass",
      "kibana_memory_mb": 0,
      "es_heap_mb": 0,
      "stack_version": "9.6.0"
    },
    {
      "id": "dex-perf-warm-1",
      "role": "warm_boot",
      "scenarios": ["warm_boot", "scalability", "contention", "double_click", "memory_stability"],
      "kibana_url": "https://...",
      "es_url": "https://...",
      "credentials": "user:pass",
      "kibana_memory_mb": 0,
      "es_heap_mb": 0,
      "stack_version": "9.6.0",
      "iterations": 5
    }
  ]
}
```

### Results Cluster

| Field | Required | Description |
|-------|----------|-------------|
| `es_url` | Yes | Elasticsearch URL for the results cluster |
| `api_key` | Yes | Base64-encoded API key (or `env:VAR_NAME`) |
| `kibana_url` | No | Kibana URL. Auto-derived from `es_url` by swapping `.es.` for `.kb.` if not set. |

### Environment Roles

| Role | Behavior |
|------|----------|
| `cold_boot` | Single install on a pristine project. Captures first-touch latency including Fleet/EPR package download. Project is consumed after the test. |
| `warm_boot` | Primer pass to warm caches, then runs assigned scenarios with delete/install cycles. Reusable across runs. |

### Credentials

Inline `"user:pass"` format in the config (generated by `provision_environments.sh`),
or `"env:VAR_NAME"` to resolve from environment variables.

## Scenarios

| Scenario | Description |
|----------|-------------|
| `cold_boot` | First-ever install on pristine project. Measures full initialization cost including Fleet/EPR bootstrap. |
| `warm_boot` | N repeated delete/install cycles on warmed project. Steady-state install latency. |
| `scalability` | Install 100, 500, 1000, 1965 rules. Tests linearity -- is 2x rules = 2x time, or worse? |
| `contention` | Install all rules while firing concurrent customer read queries (`rules/_find`). Measures whether batch install starves customer-facing reads. |
| `double_click` | Two concurrent install requests via `Promise.allSettled()`. Verifies the concurrency limiter rejects the second cleanly (no deadlocks, no duplicates). |
| `memory_stability` | 20 consecutive delete/install cycles without delay. Detects memory leaks by tracking RSS/heap drift across cycles. |

## Results Indices

Three Elasticsearch indices are created on the results cluster:

| Index | Granularity | Key Fields |
|-------|-------------|------------|
| `perf-dex-prebuilt-rules-runs` | One doc per scenario per environment per run | `median_duration_ms`, `p95_duration_ms`, `p99_duration_ms`, `mean_duration_ms`, `peak_rss_mb`, `peak_heap_mb`, `errors` |
| `perf-dex-prebuilt-rules-iterations` | One doc per iteration | `duration_ms`, `http_status`, `rules_succeeded`, `rules_failed`, `rss_before_mb`, `rss_after_mb`, `heap_before_mb`, `heap_after_mb`, `delete_duration_ms`, `customer_read_latency_p95_ms`, `concurrent_install_rejected` |
| `perf-dex-prebuilt-rules-memory` | Time-series samples during execution | `rss_mb`, `heap_used_mb`, `heap_total_mb`, `event_loop_delay_ms` |

## Dashboards

Data views are created automatically during `--setup-only` via the Kibana Data
Views API. The Kibana URL is auto-derived from the results ES URL (swaps `.es.`
for `.kb.` in the hostname), or can be set explicitly via `results_cluster.kibana_url`.

Three data views are created:

- **DEx Perf Runs** (`perf-dex-prebuilt-rules-runs`)
- **DEx Perf Iterations** (`perf-dex-prebuilt-rules-iterations`)
- **DEx Perf Memory** (`perf-dex-prebuilt-rules-memory`)

### Suggested Dashboard Panels

Build these visualizations in the results Kibana on top of the data views:

| Panel | Type | Data View | Description |
|-------|------|-----------|-------------|
| Cold vs Warm Duration | Bar chart | Runs | `boot_type` on x-axis, `median_duration_ms` on y-axis |
| Install Duration Over Time | Line chart | Runs | `@timestamp` on x-axis, `median_duration_ms` on y-axis, split by `scenario` |
| Scalability Curve | Line chart | Iterations | `total_rules` on x-axis, `duration_ms` on y-axis (filter: `scenario: scalability`) |
| Memory Profile | Area chart | Memory | `@timestamp` on x-axis, `rss_mb` + `heap_used_mb` on y-axis |
| Peak Memory by Scenario | Bar chart | Runs | `scenario` on x-axis, `peak_rss_mb` on y-axis |
| Contention Impact | Bar chart | Iterations | `iteration` on x-axis, `duration_ms` + `customer_read_latency_p95_ms` on y-axis (filter: `scenario: contention`) |
| Memory Stability | Line chart | Iterations | `iteration` on x-axis, `heap_after_mb` + `rss_after_mb` on y-axis (filter: `scenario: memory_stability`) |
| Environment Comparison | Data table | Runs | Columns: `environment_id`, `scenario`, `median_duration_ms`, `peak_rss_mb`, `errors` |
| Error Summary | Metric | Runs | Sum of `errors` |

## Architecture

```
environments.json
      |
      v
  Orchestrator (runner.ts)
      |
      |--- cold_boot environments (parallel, single-shot)
      |         |
      |         +-- KibanaClient --> Cloud Kibana (serverless)
      |
      +--- warm_boot environments (parallel, scenario-driven)
                |
                +-- Scenarios (delete/install cycles)
                         |
                         +-- ESWriter --> Results Cluster --> Dashboards
```

## Future Improvements

The following scenarios are planned to extend the harness beyond prebuilt rule
installation into broader rule management operations:

### Synthetic Rule Generation at Scale

Generate N thousands of custom detection rules (not prebuilt) and benchmark
the full lifecycle:

- **Bulk import** (`POST /api/detection_engine/rules/_import`): import 1K, 5K,
  10K rules from an NDJSON payload. Measure duration, memory, and whether
  Kibana remains responsive to other requests during import.
- **Bulk enable/disable** (`POST /api/detection_engine/rules/_bulk_action`
  with `action: "enable"` / `"disable"`): toggle all N rules on and off.
  Measures task-manager scheduling overhead at scale.
- **Partial import**: import a subset (e.g., 500 of 10K) into an environment
  that already has rules installed. Measures duplicate-checking cost and
  skip/conflict resolution at scale.
- **Import after delete**: delete all N rules, then re-import the full set.
  Measures whether Saved Object tombstones or index fragmentation degrade
  re-import performance.

### Suggested Metrics for Rule Lifecycle Scenarios

| Operation | Key Metrics |
|-----------|-------------|
| Bulk import | `duration_ms`, `rules_succeeded`, `rules_failed`, `heap_before/after`, `rss_before/after` |
| Bulk enable | `duration_ms`, `total_rules`, `event_loop_delay_ms` (task scheduling overhead) |
| Bulk disable | `duration_ms`, `total_rules` |
| Partial import | `duration_ms`, `rules_skipped` (duplicates), `rules_succeeded` (new) |
| Re-import after delete | `duration_ms` vs fresh import (regression from SO tombstones) |
| Mixed load | `customer_read_latency_p95_ms` during import (contention with reads) |

### Implementation Approach

1. Add a `rule_generator.ts` utility that creates synthetic NDJSON rule
   payloads with configurable count, rule types, and field variations.
2. Add new scenarios (`bulk_import.ts`, `bulk_enable_disable.ts`,
   `partial_import.ts`) following the existing `Scenario` interface.
3. Reuse the existing `ESWriter`, `MemorySampler`, and orchestration
   infrastructure -- results go into the same indices with new `scenario`
   values.
