# Domain: Graph Visualization

## What every reviewer must know

Graph data flows from Security Solution flyout wrappers through `@kbn/cloud-security-posture-graph` (`GraphInvestigation` → `useFetchGraphData` POST to `/internal/cloud_security_posture/graph`) into ReactFlow rendering, while the CSP server validates requests, runs parallel ES|QL fetches (events, entity relationships), then a single consolidated entity-store enrichment pass (risk score, asset criticality, `entity.source`), and builds the response via a fetch-then-parse pipeline (`fetchGraph` → `regroupEvents` / `regroupRelationships` → `parseRecords`). The DTO returned to the frontend must stay decoupled from the raw underlying data (logs-\* and entity latest index) — always transform raw fields into the neutral shape the graph package expects; leaking index-specific field names or entity-store schema details into the DTO breaks the backend's ability to evolve independently. ES|QL grouping (`STATS … BY`) must be maintained at the query level for correctness: pre-aggregation is the authoritative source for node counts and graph shape; TypeScript grouping is only acceptable for the final type/sub-type merge that requires post-enrichment data. Reviewers must treat client payload size, ES|QL grouping/pinning correctness, and space-aware index resolution as first-class constraints — graphs can be massive and incorrect grouping or partial failure handling degrades investigation UX. Server-side label resolution and per-entity enrichment under `documentsData[].entity` are intentional; do not reintroduce client-side label logic, and keep node-level fields to compact server-computed aggregates.

Two client-side correctness surfaces need the same care as the server. First, `search_filters.ts` translates EUID namespace DSL into filter-bar chips, and that translator must agree exactly with its own translatability gate — an unmodeled clause shape silently produces an over-matching filter rather than a visible error. Second, all graph filter state (filter chips, expanded relationships, pinned EUIDs) lives in a module-level `FilterStore` registry keyed by `scopeId` (`graph/src/components/filters/filter_store.ts:277`); two mounted graphs that share a scope share filters, and unmounting one destroys the other's store. The package also emits semantic telemetry events (`graph_telemetry.ts`) that only Security Solution maps to EBT (`use_graph_telemetry.ts`), so the package never calls `telemetry.reportEvent` itself.

The graph visualization feature is owned by **@elastic/contextual-security-apps** (the `kbn-cloud-security-posture/graph` package, the `cloud_security_posture` graph routes, and the CPS common schema/types). The Security Solution flyout files that embed the graph are thin consumers owned by other teams per CODEOWNERS (`flyout_v2` → @elastic/security-threat-hunting; `flyout/entity_details` → @elastic/security-entity-analytics), and are not the domain's maintainers. Current consumers of the full graph (`GraphVisualization`, which lazy-loads `GraphInvestigation`):

- **flyout v2 (document):** `flyout_v2/document/tools/graph/index.tsx` (`GraphDetails`, passes `scopeId={GRAPH_SCOPE_ID}`, `:146`)
- **flyout v2 (entity):** `flyout_v2/entity/shared/tools/graph_view/index.tsx` (`GraphView`, passes the page `scopeId`, `:135`)
- **legacy flyout v1 (document details):** `flyout/document_details/left/components/graph_visualization.tsx` (passes `scopeId` and `graphScopeId={scopeId}`, `:110-111`)
- **legacy flyout v1 (entity details):** `flyout/entity_details/shared/components/left/graph_view_tab.tsx` (passes `scopeId` and `graphScopeId={scopeId}`, `:106-107`)

Preview (non-full) graphs are mounted by `flyout_v2/document/main/components/graph_preview_container.tsx` (via `useGraphPreview`) and the legacy `flyout/entity_details/shared/components/right/entity_graph_preview_container.tsx` (gated by `useShouldShowGraph`: license + `useIsEntityStoreV2Available`).

The graph telemetry files (`common/lib/telemetry/events/graph/**` and `flyout_v2/shared/hooks/use_graph_telemetry.ts`) are maintained by @elastic/contextual-security-apps.

## Architectural invariants

- **DTO must stay decoupled from the raw data sources** — The shape returned to the frontend must be neutral to the underlying data (logs-\* indices, entity latest index). Do not leak raw Elasticsearch field names, index-specific structures, or entity-store schema details into the graph DTO; always transform them into the shape the `@kbn/cloud-security-posture-graph` package expects. This decoupling lets the backend data model evolve (e.g. ENRICH → LOOKUP JOIN → follow-up enrichment query, entity-store v1 → v2) without breaking the frontend contract.

- **ES|QL grouping must be maintained at the query level** — Pre-aggregation (`STATS … BY`) must stay in ES|QL rather than being deferred to TypeScript, at least to the extent CPS limitations allow. Readable, explicit ES|QL grouping (actor, target, relationship type) is the authoritative source of correctness for node counts and graph shape; TypeScript grouping is only acceptable for the final type/sub-type merge that depends on post-enrichment data. Removing ES|QL grouping degrades both readability and correctness (TypeScript then groups over LIMIT-truncated raw rows).

- **The translatability gate and the translator must agree exactly on representable shapes** — `isFullyTranslatable` and `euidDslClauseToFilters` must model the same set of clause shapes. Any divergence produces a silently weakened filter rather than a visible error. Two consequences follow:
  - **Handle both single-value and array clause shapes.** Elasticsearch DSL allows bool clauses (`must_not`, `must`, `should`, `filter`) to be either a single object or an array. Normalize to an array before iterating; a `?? []` default only covers `undefined`, not the single-object shape.
  - **Fail closed on unmodeled shapes.** Do not fall through to `return []` for clause types the translator does not know (`match`, `terms`, `wildcard`, `range`). Return `undefined` or throw and catch in `buildEntityDslFilter` so `getEntityFilterSpec` falls back to the `fields` path — the broad-but-honest behavior. A silent fall-through contributes nothing to the surrounding AND and just weakens it, collapsing the filter to a single chip (`user.email: alice@example.com`) that matches `alice@aws`, `alice@okta` and `alice@entra_id` alike.

  ([PR #289467](https://github.com/elastic/kibana/pull/289467) · @niros1 · `x-pack/solutions/security/packages/kbn-cloud-security-posture/graph/src/components/filters/search_filters.ts`)

- **Client payload must stay minimal** — The graph schema must pass only fields needed for the current use case, not all entity/asset fields; violating this inflates responses for large graphs and risks client performance degradation. [PR #290980](https://github.com/elastic/kibana/pull/290980) expanded the payload deliberately and narrowly: per entity it adds only `riskScore` (normalized 0-100 number), `assetCriticality` (raw level string) and `sources` (array bounded by `ENTITY_SOURCES_MAX_SIZE`) to `entitySchema`, and every new array in the response schema carries a `maxSize` bound (`common/schema/graph/v1.ts:208-243`). New fields must follow the same pattern: one concrete visualization use case per field, bounded arrays, and nothing copied wholesale from the entity-store document. ([PR #227784](https://github.com/elastic/kibana/pull/227784) · @kfirpeled; [PR #290980](https://github.com/elastic/kibana/pull/290980) · @alexreal1314 · `x-pack/solutions/security/packages/kbn-cloud-security-posture/common/schema/graph/v1.ts`)

- **Per-entity enrichment must live under `documentsData[].entity`; node-level fields are limited to compact aggregates** — The original rule (PR #227784) was that per-node asset/expansion data goes under the existing document-data placeholder rather than new top-level schema fields. The placeholder is the `documentsData` array (`nodeDocumentDataSchema`, `common/schema/graph/v1.ts:245-264`), and [PR #290980](https://github.com/elastic/kibana/pull/290980) follows it for per-entity values (`documentsData[].entity.riskScore | assetCriticality | sources | sourceFields`). The same PR also added two top-level fields to `entityNodeDataSchema`: `riskScore: { min, max }` (the range across the entities a grouped node stands for) and `assetCriticality: [{ level, count }]` (a distribution ordered most to least severe) (`v1.ts:334-358`), computed server-side by `aggregateRiskScore` / `aggregateAssetCriticality` (`server/routes/graph/utils/enrichment_utils.ts:137,162`). These sit alongside the pre-existing node-level `ips` and `countryCodes`. Reviewers should accept new node-level fields only when they are a bounded, server-computed summary of `documentsData` that the node card renders directly; raw per-entity values must stay in `documentsData`. ([PR #227784](https://github.com/elastic/kibana/pull/227784) · @kfirpeled; [PR #290980](https://github.com/elastic/kibana/pull/290980))

  The team generally avoids adding top-level schema fields, but node-level `riskScore` and `assetCriticality` are accepted: they sit at the root of the node data, like `color`, `shape` and `count`.

- **Absent enrichment is not zero** — `riskScore` is omitted when the entity has no score (not in the entity store, or not yet scored by the risk score maintainer), and `assetCriticality` is omitted when unassigned; consumers must not default either to `0` / lowest level, and the server must not emit placeholder values (schema comments, `common/schema/graph/v1.ts:226-233,334-349`). Emitting zeros would render a misleading "low risk" badge on unscored entities.

  Reviewers enforce this for every enrichment field added to the graph DTO: a missing risk score or asset criticality is absent, never `0`.

- **Asset criticality must use the entity store's exported type and raw levels** — Do not redefine the entity store's `AssetCriticalityLevel` values locally as `readonly string[]`; import the type from `@kbn/entity-store/common` and the values from `AssetCriticalityLevelEnum`, typed as `readonly AssetCriticalityLevel[]`. The severity order is listed explicitly because the levels do not sort correctly as strings, and unknown levels are dropped through `isKnownAssetCriticalityLevel`. Violating this lets the graph drift from the entity store when levels change. ([PR #290980](https://github.com/elastic/kibana/pull/290980) · @JordanSh · `x-pack/solutions/security/plugins/cloud_security_posture/server/routes/graph/asset_criticality_levels.ts`)

- **The server sends raw criticality levels, never display labels** — Criticality labels are i18n'd by the consumer (`CRITICALITY_LEVEL_TITLE` in security_solution); sending labels from the server would make them untranslatable and fork wording shared by other call sites (`asset_criticality_levels.ts` header comment; `common/schema/graph/v1.ts:344-349`). This is an explicit, scoped exception to "node label logic must stay server-side" below: entity/node *names* resolve on the server, translated *enum labels* resolve on the client.

  The client uses the risk score and asset criticality labels exported by the entity store, which is why the backend does not compute them.

- **Index names must be space-aware** — Entity/asset index resolution must not hard-code a `_default` suffix; fixed suffixes can query the wrong space's data. Today the entity store index is resolved per space by `resolveEntitiesIndexName(esClient, logger, spaceId)` (`server/routes/graph/utils/enrichment_utils.ts:76-92`); the original `fetch_entity_data.ts` named in the source PR no longer exists. ([PR #227784](https://github.com/elastic/kibana/pull/227784) · @kfirpeled · `x-pack/solutions/security/packages/kbn-cloud-security-posture/common/utils/helpers.ts`)

- **Origin IDs must not appear in logs** — Origin IDs (which may contain PII such as IP addresses) must be omitted from server logs unless there is a concrete use case; otherwise PII may reach Kibana operational logs. ([PR #227784](https://github.com/elastic/kibana/pull/227784) · @kfirpeled · `x-pack/solutions/security/plugins/cloud_security_posture/server/routes/graph/route.ts`)

- **Backend modules must have single responsibility** — Large mixed-responsibility modules (fetch + parse + enrich in one file) must be split into dedicated files with dedicated tests (e.g. `parse_records`, `fetch_graph`, `fetch_events_graph`, `fetch_entity_enrichment`); monolithic files hinder navigation and test coverage. ([PR #227784](https://github.com/elastic/kibana/pull/227784) · @kfirpeled · `x-pack/solutions/security/plugins/cloud_security_posture/server/routes/graph/v1.ts`; [PR #275276](https://github.com/elastic/kibana/pull/275276) · @kfirpeled · `x-pack/solutions/security/plugins/cloud_security_posture/server/routes/graph/fetch_events_graph.ts`)

- **Fetch-then-parse pipeline must be preserved** — Entity enrichment must not be interleaved inside `parseRecords` loops with scattered fetch params; all relevant data (graph records + entity metadata) must be fetched first, then passed to `parseRecords`. The current shape is: events + relationships + entities fetched, all actor/target ids collected into one set, one `fetchEntityEnrichment` pass, then regroup/enrich/parse (`server/routes/graph/fetch_graph.ts:93-189`). PR #290980 added risk score, asset criticality and source to that same single pass rather than a second query. Interleaving degrades efficiency when parsing many records. ([PR #227784](https://github.com/elastic/kibana/pull/227784) · @kfirpeled · `x-pack/solutions/security/plugins/cloud_security_posture/server/routes/graph/v1.ts`)

- **System-status queries must use `asInternal`** — Internal system-status queries must use `asInternal`, not `asCurrentUser`; user-scoped permissions can block operations the user lacks access to even when the query is about system state. User-scoped permissions remain for data queries. ([PR #227784](https://github.com/elastic/kibana/pull/227784) · @kfirpeled · `x-pack/solutions/security/plugins/cloud_security_posture/server/routes/graph/fetch_graph.ts`) See also the enrichment exception under Security considerations.

- **TypeScript errors must not be suppressed** — `@ts-ignore` and `@ts-expect-error` must not be used; fix the root cause or update upstream types. ([PR #269755](https://github.com/elastic/kibana/pull/269755) · @niros1 · `x-pack/solutions/security/plugins/cloud_security_posture/server/routes/graph/fetch_entity_enrichment.ts`)

- **ES|QL must pre-aggregate with `STATS … BY` (never return raw rows)** — The events and relationships queries must run a `STATS … BY` pre-aggregation over the dimensions available *without* entity-store enrichment, instead of returning one raw row per document/triple. Removing ES|QL grouping (as happened when the unsupported `LOOKUP JOIN` was dropped for CPS support) degrades the graph: grouping logic then runs in TypeScript over ungrouped — and `LIMIT`-truncated — records, producing fewer/incorrect results (wrong grouped nodes and counts). The final merge by entity type/sub-type still happens in TypeScript (`regroupEvents` / `regroupRelationships`) because type/sub-type are only known after the follow-up enrichment query, but ES|QL grouping must remain a **strict refinement** of the TS group key so the rendered graph is unchanged — just computed over far fewer rows. ([PR #275276](https://github.com/elastic/kibana/pull/275276) · @alexreal1314, @kfirpeled · `x-pack/solutions/security/plugins/cloud_security_posture/server/routes/graph/fetch_events_graph.ts`, `fetch_entity_relationships_graph.ts`, `parse_records.ts`)

- **Actor→target pairing must be preserved in ES|QL** — ES|QL must not group results by `actorEntityId` and `targetEntityId` separately; use `targetIds = VALUES(targetId)` (not bare `targetId`) to preserve pairing; separate grouping breaks graph data presentation. ([PR #275276](https://github.com/elastic/kibana/pull/275276) · @kfirpeled · `x-pack/solutions/security/plugins/cloud_security_posture/server/routes/graph/fetch_events_graph.ts`, `fetch_entity_relationships_graph.ts`)

- **Pinned relationships must stay in ES|QL** — Pinned-relationship splitting must not move to TypeScript runtime grouping; split pinned relationships in the ES|QL query (group/sort by pinned first), consistent with `fetch_events_graph`; runtime splitting breaks pinning logic. ([PR #272452](https://github.com/elastic/kibana/pull/272452) · @kfirpeled, @albertoblaz · `x-pack/solutions/security/plugins/cloud_security_posture/server/routes/graph/fetch_entity_relationships_graph.ts`)

- **Relationship queries must be bidirectional** — Queries must cover both `entity.id equals to` and `entity.relations.* equals to` (reverse direction); one-direction queries miss relationships visible in the entity store. ([PR #251178](https://github.com/elastic/kibana/pull/251178) · @kfirpeled · `x-pack/solutions/security/plugins/cloud_security_posture/server/routes/graph/fetch_graph.ts`)

- **Relationship query failures must fail the request** — Partial graph results must not be returned when the relationships query fails; the graph request must fail so the UI can surface the error (the UI handles failures better than partial results). ([PR #251178](https://github.com/elastic/kibana/pull/251178) · @kfirpeled · `x-pack/solutions/security/plugins/cloud_security_posture/server/routes/graph/fetch_entity_relationships_graph.ts`)

- **Only approved relationship fields are supported** — Bidirectional support must be limited to approved fields: Accesses_frequently, Communicates_with, Depends_on, Owns, Supervises; supporting all entity-store relationship fields was explicitly dropped. ([PR #251178](https://github.com/elastic/kibana/pull/251178) · @kfirpeled · `x-pack/solutions/security/packages/kbn-cloud-security-posture/common/constants.ts`)

- **Node label logic must stay server-side** — Label/display resolution must not move to the client; server-side logic keeps behavior consistent across consumers and reduces client CPU on re-render. (Scoped exception: translated enum labels such as asset criticality, see above.) ([PR #227784](https://github.com/elastic/kibana/pull/227784) · @kfirpeled · `x-pack/solutions/security/packages/kbn-cloud-security-posture/graph/src/components/utils.ts`)

- **Empty entity names must fall back to ID** — Whitespace-only or empty entity names must not render as blank labels; fall back to entity ID. ([PR #227784](https://github.com/elastic/kibana/pull/227784) · @kfirpeled · originally `entity_data_to_node_props.mapper.ts`)

  When an entity has no `entity.name`, the node's `id` is what is displayed. `server/routes/graph/entity_data_to_node_props.mapper.ts` no longer exists.

  The label is resolved by `generateEntityLabel` (`server/routes/graph/parse_records.ts:198-219`): a single non-enriched entity shows its node id, a single enriched entity shows its `entity.name` (the first value when there are several), and a grouped node (more than one entity) shows the entity sub type. When no label results it is omitted from the node (`parse_records.ts:279`) and the node's `id` is displayed.

- **Entity-type constants must stay readable (PascalCase)** — Constants must not be stored all-lowercase; normalize casing at comparison time to avoid easy-to-miss comparison bugs. ([PR #227784](https://github.com/elastic/kibana/pull/227784) · @kfirpeled · `x-pack/solutions/security/plugins/cloud_security_posture/server/routes/graph/entity_type_constants.ts`)

- **Entity query deduplication must use ES|QL STATS** — When deduplication is known to be needed, duplicate rows must be deduplicated in the query via STATS, not returned to the client/parser. ([PR #227784](https://github.com/elastic/kibana/pull/227784) · @kfirpeled · originally `fetch_entity_data.ts`, since removed)

- **Pinned entities must check target side** — Pinned-entity resolution must not only check the actor side; when pinned, target relationships must be checked too (entities can be grouped by target or actor). ([PR #272452](https://github.com/elastic/kibana/pull/272452) · @kfirpeled · `x-pack/solutions/security/plugins/cloud_security_posture/server/routes/graph/fetch_entity_relationships_graph.ts`)

- **FORK branch limit must be documented when adding relationship fields** — New relationship fields must document the 8-FORK-branch ES|QL limit when approaching it; undocumented additions risk query failure at the ES|QL layer. ([PR #251178](https://github.com/elastic/kibana/pull/251178) · @kfirpeled · `x-pack/solutions/security/packages/kbn-cloud-security-posture/common/constants.ts`)

- **Avoid premature meta-mapping generalization** — Generic meta-mapping utilities must not be built before the use case is proven; use simple hard-coded field assignments (e.g. `entity.name` → label, `entity.type` → icon) visible in code. ([PR #227784](https://github.com/elastic/kibana/pull/227784) · @kfirpeled · originally `fetch_entity_data.ts`, since removed)

- **Graph PRs must not include out-of-scope API changes** — Unrelated OpenAPI/API diffs must not ship in graph PRs; cross-API changes slow review and blur scope. ([PR #269755](https://github.com/elastic/kibana/pull/269755) · @kfirpeled · `oas_docs/output/kibana.serverless.yaml`)

- **Unused schema types must be removed** — Schema types that existing schemas do not reuse must not be added or left in place. ([PR #227784](https://github.com/elastic/kibana/pull/227784) · @albertoblaz · `x-pack/solutions/security/packages/kbn-cloud-security-posture/common/schema/graph/v1.ts`)

- **Graph filters and actions always expand, never narrow** — `addEntityFilter` intentionally wraps graph-generated chips in OR. This is by design: filters and actions performed on the graph always add to and expand the graph view. Intersecting all filters with AND would narrow the results too much and hide valuable investigative information. Do not change this to an AND relationship. (@alexreal1314, [PR #289467](https://github.com/elastic/kibana/pull/289467)) The default origin pills follow the same rule: when user filters exist, the filter bar renders the default pills, then an `OR` separator (`data-test-subj="graphDefaultFilterOr"`), then the user chips (`graph_investigation.tsx:856-869`).

- **Default origin filters are display-only and graph-owned** — When the graph opens from an event/alert flyout, `GraphInvestigation` builds non-interactive `event.id` pills (`phrase` for one origin id, `phrases` for several) from `originEventIds`; when it opens from an entity flyout it builds `entity.id` pills from the `entityIds` marked `isOrigin: true` (`graph_investigation.tsx:330-414`). They are tagged `meta.controlledBy: CONTROLLED_BY_GRAPH_INVESTIGATION_DEFAULT_FILTER` (`'graph-investigation-default'`, `filters/search_filters.ts:25`), rendered through `prependFilterBar` / `DefaultFilterItems` (`:817-898`), and are **not** part of `searchFilters`, so they never enter the `esQuery` built from `[kquery]` + `searchFilters` (`:436-455`). The origin scope reaches the server only through `originEventIds` / `entityIds` in the request (`:457-475`). Reviewers must not add these pills to `searchFilters` or the filter store: that would AND them with user chips (contradicting the expand-never-narrow rule) and send a duplicate origin constraint in `esQuery`. ([PR #286754](https://github.com/elastic/kibana/pull/286754) · @JordanSh, "[Entity Graph] Show default graph filter; fix grouped node label; fix filter forwarding to timeline")

  PR #286754 covers both the event-mode and the entity-mode default pills, and it also fixes the filters that are forwarded to the timeline.

- **Each mounted graph must own its filter scope** — `FilterStore` instances live in a module-level `Map<string, FilterStore>` (`filters/filter_store.ts:277`, class at `:287`) and subscribe to global RxJS buses (filter toggle, entity relationship toggle, pinned EUID) filtered by `event.scopeId === this.scopeId`; `useGraphFilters(scopeId, …)` gets or creates the store and calls `destroyFilterStore(scopeId)` on unmount (`filters/use_graph_filters.ts:49,62-66`). Two graphs mounted at the same time with the same scope therefore share filters, expanded entities and pins, and closing one destroys the store the other is still using. Any emitter (`emitFilterToggle`, `emitEntityFilterToggle`, `emitEntityRelationshipToggle`, `emitPinnedEuidToggle`) and any grouped-node panel opened from a graph must use **that graph's** filter scope, not the page scope. How scope is passed today:
  - **flyout v2:** `GraphVisualization` derives `graphScopeId = props.graphScopeId ?? \`${scopeId}-graph${useId()}\`` (`flyout_v2/document/tools/graph/components/graph_visualization.tsx:134-135`), passes it to `GraphInvestigation` (`:285`) and as `params.scopeId` to `onShowGrouped` (`:210,219`). The flyout v2 document tool and entity `GraphView` pass no `graphScopeId` and no longer override the grouped panel's `scopeId` with the page scope (`flyout_v2/document/tools/graph/index.tsx:97-119`), so each mounted graph gets its own scope. This matters because flyout v2 keeps previous flyouts mounted (hidden) in its Back history.
  - **legacy flyout v1:** document details and entity `GraphViewTab` pass `graphScopeId={scopeId}` (the stable page scope). The legacy flyout mounts only one graph at a time and restores grouped-node previews from the URL (`GraphGroupedNodePreviewPanelForFlyout`, `flyout/index.tsx:138-220`), so a stable scope keeps restored previews connected to the graph after a reload.
  - The page `scopeId` is still what entity, document and network flyouts opened *from* the graph receive.

  ([PR #301396](https://github.com/elastic/kibana/pull/301396), "[Graph] Fix for Carried over filter when opening different graphs"; store introduced in [PR #250105](https://github.com/elastic/kibana/pull/250105))

  PR #301396 is merged (commit `7725eeb02fe7` on `main`, 2026-11-03), so the behaviour above is current. Before it, every document graph used the constant `GRAPH_SCOPE_ID` scope and flyout v2 consumers overrode the grouped panel's `scopeId` with the page scope.

- **Grouped-events previews are keyed by document `_id`, never `event.id`** — The grouped-events flyout must build its document list from `documentsData[].id` (capped at `MAX_DOCUMENTS_TO_LOAD = 50`, `flyout_v2/document/tools/graph/components/graph_visualization.tsx:51,213`) and fetch with an `ids` query (`bool.filter.ids.values`, `graph_grouped_node_preview_panel/use_fetch_document_details.ts:70-87`). Events resolved by runtime integration evaluations (for example Qualys VMDR) have no `event.id`, and the node count is based on distinct `_id`s; building the list from `event.id` left the query disabled (react-query v4 reports a never-run disabled query as `isLoading: true`, so the panel never left loading), listed nodes partially, and could include documents that share an `event.id` but are not part of the node. Items carry both `id: hitSource.event?.id` and `docId: hit._id` (`use_fetch_document_details.ts:99-122`); `nodeDocumentDataSchema` keeps `event.id` optional (`common/schema/graph/v1.ts:245-257`), and the `graph/events` endpoint aggregates `BY docId, eventId, index` with `_id IN (...)` (`graph_events/fetch.ts:152-173`). ([PR #296210](https://github.com/elastic/kibana/pull/296210) · @alexreal1314)

  The per-document `index` is intentionally not sent with each id; it will be added if errors show up (see Common review patterns).

- **Grouped-event actor/targets must resolve to the same EUIDs the graph shows** — Rows resolve actor and targets client-side with the entity store's `euid.getEuidFromObjectForSearch` via `resolveActorAndTargets(source, euidApi)`, not from `actor.entity.id` / `target.entity.id` (which nothing writes outside test fixtures) and not with the gated `getEuidFromObject` (which answers "may this document create an entity" and returns `undefined` for, e.g., a gcp user the graph resolves to `user:admin@example.com@gcp`). The actor is the first match in `ALL_ENTITY_TYPES` order (user, host, service, generic), matching the graph's ES|QL resolution order; targets are every match from the `.target.` counterparts, deduplicated. Items are built in a memo keyed on the async `useEntityStoreEuidApi()` value so rows fill in when the API loads without a refetch. ([PR #296210](https://github.com/elastic/kibana/pull/296210) · @alexreal1314 · `graph_grouped_node_preview_panel/resolve_actor_and_targets.ts`, `use_fetch_document_details.ts`)

  The actor ranking order is determined by the ES|QL resolution order, so the client order must stay in lockstep with it.

- **The graph package emits semantic telemetry; only Security Solution maps it to EBT** — Package components report `GraphTelemetryEvent`s (`node_action`, `filter_changed`, `search_submitted`) through the `onTelemetryEvent` prop (`graph/src/components/graph_telemetry.ts:26-83`; call sites `graph_investigation.tsx:424-431,872-878`). `flyout_v2/shared/hooks/use_graph_telemetry.ts:20-61` is "the only place that knows which EBT event each one becomes" and adds `reportPreviewExpanded` (used by `flyout_v2/shared/components/graph_preview_panel.tsx:50-54`). EBT schemas live in `common/lib/telemetry/events/graph/index.ts` (`Graph Node Action Clicked`, `Graph Filter Changed`, `Graph Search Submitted`, `Graph Preview Expanded`) and are registered through `graphTelemetryEvents` spread into `telemetry_events.ts:56`. The node type / action / toggle-state values are exhaustive records (`GRAPH_NODE_TYPE`, `GRAPH_NODE_ACTION`, `GRAPH_TOGGLE_STATE` in `events/graph/types.ts`). Do not call `telemetry.reportEvent` from the package, and add new node actions to both the package event union and the exhaustive records so the schema description stays complete. ([PR #297168](https://github.com/elastic/kibana/pull/297168) · @alexreal1314)

  Both the legacy flyout and the flyout v2 report graph EBT events: both render the shared flyout v2 `GraphVisualization`, which calls `useGraphTelemetry` and passes `onTelemetryEvent` to `GraphInvestigation` unconditionally (`flyout_v2/document/tools/graph/components/graph_visualization.tsx:169,312`). `Graph Preview Expanded` is shared as well: the shared `GraphPreviewPanel` (`flyout_v2/shared/components/graph_preview_panel.tsx`) calls `reportPreviewExpanded`, and it is rendered by both the flyout v2 `graph_preview_container.tsx:48` and the legacy entity flyout's `entity_graph_preview_container.tsx:47`.

- **Origin highlighting is driven by origin flags plus a display option** — The server computes `isOrigin` / `isOriginAlert` in ES|QL as `COALESCE(event.id, "") IN (?og_id...)` (`server/routes/graph/fetch_events_graph.ts:470-482`) and bakes them into label node ids (`…oe(0|1)oa(0|1)`, `parse_records.ts:386`). The client re-derives `originEventIdsSet` / `originAlertIdsSet` / `originEntityIdsSet` and tags entity nodes by `node.id`, label nodes by `documentsData[].event.id`, and relationship nodes through their incoming edges' sources (`graph_investigation.tsx:676-770`). Rendering is gated on `isOrigin && globalOpts.highlightOrigin` (`node/entity_card_node.tsx:985`); `highlightOrigin` defaults to `true` (`graph/graph_display_options_context.ts:28-31`), is read from stored display options (`graph/graph.tsx:163-164`) and toggled from the Layers panel (`controls/layers_panel.tsx:120-122`). ([PR #296646](https://github.com/elastic/kibana/pull/296646), "Graph Toggle for Highlight Origin Node"; display options introduced in [PR #295879](https://github.com/elastic/kibana/pull/295879))

  **Known gap:** events without `event.id` (for example runtime-evaluated events) are never highlighted as origin. `useGraphPreview` does not fetch `eventIds` when they are missing, so no origin event is sent, and origin matching keys on `event.id`. Whether origin detection can fall back to the document `_id` (which might cause cross-index id collisions) is tracked in [issue #302917](https://github.com/elastic/kibana/issues/302917).

## Common review patterns (learned from real PRs)

- **Count naming encodes what is counted** — `count` is the combined total (`uniqueEventsCount + uniqueAlertsCount`); use `uniqueEventsCount` and `uniqueAlertsCount` for the sub-aggregates. This is the intended convention across the entire graph API — schema, parser, and integration tests — not just test files. (@JordanSh, [PR #285449](https://github.com/elastic/kibana/pull/285449) · `x-pack/solutions/security/test/cloud_security_posture_api/routes/graph.ts`)

- **EUID filter translation bugs are caught by unit/integration/FTR coverage, not archive fixtures** — The bugs in [PR #289467](https://github.com/elastic/kibana/pull/289467) were not caught because no fixture exercised condition-based namespaces (`local`, asset-discovery). Adding condition-based-namespace fixtures to the graph test archives is not a standing requirement — sufficient unit test, API integration, and FTR coverage is the team's standard. (@niros1, [PR #289467](https://github.com/elastic/kibana/pull/289467) · `search_filters.ts`)

- **ESQL readability vs extraction** — Reviewers push back on over-extracting ES|QL into many variables or leaving entirely inline blobs; agreed balance is minimal splitting without large duplicated chunks. (@kfirpeled, @albertoblaz, [PR #227784](https://github.com/elastic/kibana/pull/227784) · `fetch_graph.ts`)

- **Exported types belong in `types.ts`** — Exported types that risk cyclic imports should live in `types.ts`, not co-located in implementation files; internal-only types may stay co-located. (@kfirpeled, [PR #227784](https://github.com/elastic/kibana/pull/227784) · `entity_type_constants.ts`)

- **Node shape from `entity.type`** — Prefer entity-store `entity.type` → shape mapping over legacy host/user/ip heuristics; `tag` remains optional when type is missing. (@kfirpeled, [PR #227784](https://github.com/elastic/kibana/pull/227784) · `parse_records.ts`)

- **Connector terminology** — Use `ConnectorEdges` / connector terminology aligned across frontend and backend, not `LabelEdges` / confusing label naming. (@alexreal1314, [PR #251178](https://github.com/elastic/kibana/pull/251178) · `parse_records.ts`)

- **Deduplication default off** — Do not add deduplication without a proven production use case; over-deduplication is considered less harmful than missing data initially. (@kfirpeled, [PR #258435](https://github.com/elastic/kibana/pull/258435) · `parse_records.ts`)

- **Retry helpers in common** — Reusable retry helpers should live under common and align with existing Kibana retry utilities, not ad-hoc helpers inside route files. (@kfirpeled, [PR #269755](https://github.com/elastic/kibana/pull/269755) · `fetch_entity_enrichment.ts`) The enrichment fetch now uses `p-retry` per chunk (`fetch_entity_enrichment.ts:121-125`).

- **Enrichment page size** — Very small pagination (e.g. 100) for parallel entity enrichment fetches is flagged as too small; reviewers suggested 5k, authors settled on 1k. (@kfirpeled, [PR #269755](https://github.com/elastic/kibana/pull/269755) · `fetch_entity_enrichment.ts`)

- **Test business requirements, not ESQL construction** — Tests should assert behavior (e.g. query works for both actors and targets), not internal ESQL string construction details. (@albertoblaz, [PR #251178](https://github.com/elastic/kibana/pull/251178) · `fetch_entity_relationships_graph.test.ts`)

- **Re-add disabled tests with the follow-up change, softly held** — A reviewer preferred removing graph API route tests that a PR disables pending a later feature (pinning) and re-adding them in the follow-up PR, for cleaner Git history; then softened it: "for the sake of velocity, let's keep this file as-is and keep these tests disabled." Treat as a preference, not a blocker. (@albertoblaz, [PR #272452](https://github.com/elastic/kibana/pull/272452) · `x-pack/solutions/security/test/cloud_security_posture_api/routes/graph.ts`)

- **Fetch missing event fields in relationship graph** — `fetch_entity_relationships_graph.ts` must fetch the same host/IP fields as the events graph when creating entity nodes not found in `nodesMap`. (@albertoblaz, [PR #251178](https://github.com/elastic/kibana/pull/251178) · `types.ts`)

- **Non-interactive nodes must not respond to clicks** — When `interactive={false}`, mouse click/hover effects must be disabled across node types. (@kfirpeled, [PR #249479](https://github.com/elastic/kibana/pull/249479) · `relationship_node.stories.tsx`)

- **Stacked relationship nodes pending design** — Stacked relationship groups were left supported intentionally while design confirmation is pending; do not assume stacking is permanently rejected. (@kfirpeled, [PR #249479](https://github.com/elastic/kibana/pull/249479) · `common/schema/graph/v1.ts`)

- **No FF gating for expand popover option** — Entity expand popover option should not be gated behind entityStoreV2 FF; graph gating on entity store is expected later. (@kfirpeled, [PR #252803](https://github.com/elastic/kibana/pull/252803) · `use_entity_node_expand_popover.ts`)

- **Entity node height is a single layout constant** — With the node redesign ([PR #291001](https://github.com/elastic/kibana/pull/291001), "Graph Node Design Update"), entity nodes became cards (`node/entity_card_node.tsx`, added in that PR) that render risk badges from `riskScore {min,max}`, the most severe asset criticality, sources, IPs, geolocation and sub-type according to `GraphDisplayOptions` (`entity_card_node.tsx:286-296,518-576,825-985`). Self-review comments on that PR settled that the node has one height defined by `ENTITY_NODE_TOTAL_HEIGHT` (set to 360 rather than assigned from `ENTITY_NODE_LAYOUT_HEIGHT`), and that the hover/half-height value is ~300 because the total includes metadata rows plus hover actions. Changes that add rows to the card must update that constant, since dagre layout (`layout_graph.ts`) spaces nodes from it. (PR #291001 · @animehart)

  There is currently a single total-height constant, `ENTITY_NODE_TOTAL_HEIGHT`. `entity_card_node.tsx` and `layers_panel.tsx` have no co-located unit tests.

- **Grouped-events `_id` collisions across indices were deferred, not rejected** — A bot flagged that grouped-events previews should carry the source index with each document id to avoid `_id` collisions across indices; the author deferred it: "will add it if necessary, we didn't have it for event.id as well". `nodeDocumentDataSchema` already has an optional `index`. ([PR #296210](https://github.com/elastic/kibana/pull/296210), bot-raised, author-only reply)

  No `index` is required for now; it will be added if errors show up. The cross-index collision question is tracked together with the origin-highlighting gap in [issue #302917](https://github.com/elastic/kibana/issues/302917).

- **Where graph flyout behaviour is tested** — Changes to how a flyout opens or drives the graph should come with updates to the matching FTR flyout spec under `x-pack/solutions/security/test/cloud_security_posture_functional/group5/pages/`: `alerts_flyout.ts` (5 `it` blocks), `events_flyout.ts` (13), `entity_flyout.ts` (3), `entity_preview_flyout.ts` (4), using the page objects `page_objects/expanded_flyout_graph.ts` and `page_objects/entity_flyout.ts`. Examples: PR #296210 changed the grouped-item count assertion in the alerts flyout FTR (3 → 2) because the node's documents are now keyed by `_id`; PR #286754 updated `page_objects/expanded_flyout_graph.ts` for the default filter pills. API behaviour is covered by `test/cloud_security_posture_api/routes/{graph,graph_basic,graph_events,graph_entities}.ts`; CPS project routing by the Scout spec `security_solution/test/scout_cps_local/ui/tests/graph_visualization/cps/project_routing.spec.ts`; serverless by `test/serverless/functional/test_suites/ftr/cloud_security_posture/{graph_events_flyout,graph_alerts_flyout}.ts`. Unit coverage of the consumer wiring is uneven. These already have co-located Jest suites to extend with regression tests: `use_graph_telemetry.test.ts`, `use_graph_preview.test.ts`, `use_should_show_graph.test.tsx`, the legacy document `graph_visualization.test.tsx` and `filter_store.test.ts` (the filter store). These have none: `use_graph_filters.ts`, the legacy `graph_view_tab.tsx` and `flyout_v2/entity/shared/tools/graph_view/index.tsx`. (checked against the repo on 2026-11-03)

  FTR changes in the matching `group5/pages/*_flyout.ts` spec are usually expected when a PR changes frontend-facing graph behaviour.

## Security considerations

- **Silently weakened EUID filters are an authorization-adjacent correctness risk** — A filter that falls through to `return []` for an unmodeled clause shape does not fail visibly; it renders a chip that matches a broader entity population than the user's namespace intends (`user.email: alice@example.com` matching `alice@aws`, `alice@okta`, `alice@entra_id`). Reviewers must treat the fail-closed rule as a data-scoping guarantee, not a cosmetic filter-bar concern. An over-matching filter should not reach the user in practice — it can appear only briefly before the EUID API loads. ([PR #289467](https://github.com/elastic/kibana/pull/289467) · @niros1 · `search_filters.ts`)

- **Origin IDs must not be logged** — Server route logging must omit origin IDs that may contain PII (e.g. IP addresses); operational logs can propagate PII into Kibana observability paths. ([PR #227784](https://github.com/elastic/kibana/pull/227784) · @kfirpeled · `cloud_security_posture/server/routes/graph/route.ts`)

- **Index resolution must be space-aware** — Hard-coded `_default` suffixes for entity/asset indices can cause cross-space data access or wrong-space queries in multi-space deployments. Entity index resolution is per space through `resolveEntitiesIndexName(…, spaceId)` (`server/routes/graph/utils/enrichment_utils.ts:76`). ([PR #227784](https://github.com/elastic/kibana/pull/227784) · @kfirpeled · `common/utils/helpers.ts`)

- **User vs internal ES client scope** — Data queries must use user permissions (`asCurrentUser`); internal system-status queries must use `asInternal` so permission gaps do not block legitimate system checks or leak unintended access patterns. ([PR #227784](https://github.com/elastic/kibana/pull/227784) · @kfirpeled · `fetch_graph.ts`) Current code: events and relationships use `asCurrentUser` (`fetch_events_graph.ts:134`, `fetch_entity_relationships_graph.ts:272,348`), as do `graph_events/fetch.ts:59` and `graph_entities/fetch.ts:57`; index existence checks use `asInternalUser` (`enrichment_utils.ts:82-83`).

- **Entity enrichment deliberately runs as the internal user** — `fetchEntityEnrichment` queries the entity store with `esClient.asInternalUser.helpers.esql` "to always target the origin project's local entity store, bypassing any CPS routing that might redirect asCurrentUser queries" (`server/routes/graph/fetch_entity_enrichment.ts:114-115,162`). Since PR #290980 that pass returns risk score, asset criticality and `entity.source` for every actor/target id the user's own (user-scoped) event and relationship queries surfaced. Reviewers adding columns to the enrichment `KEEP` list (`fetch_entity_enrichment.ts:150-157`) are adding fields read with internal privileges, so each new column should be one the user is entitled to see for entities already visible to them.

  This is an intentional exception to the "data queries use `asCurrentUser`" rule above: the enrichment must target the origin project's local entity store.

- **Platinum license gate is applied only on the main graph route** — `server/routes/graph/route.ts:64` checks `license.hasAtLeast('platinum')` before serving data (privilege `cloud-security-posture-read`, `:33`). The `graph_events` and `graph_entities` detail routes gate on the `securitySolution` privilege only (`graph_events/route.ts:26`, `graph_entities/route.ts:26`) and have no license check. Reviewers adding new graph endpoints should apply the Platinum gate explicitly rather than assuming it is inherited. **Open question for the team:** whether the detail routes should enforce the gate independently, or whether reachability-only-after-the-main-route is considered sufficient.

- **Client payload minimization** — Passing full entity/asset field sets to the browser expands the attack surface for data exfiltration via large graph responses and increases exposure of fields not needed for visualization. Every array in the response schema is bounded with `maxSize` (`IPS_MAX_SIZE`, `COUNTRY_CODES_MAX_SIZE`, `ENTITY_SOURCES_MAX_SIZE`, `ASSET_CRITICALITY_LEVELS_MAX_SIZE`, `DOCUMENTS_DATA_MAX_SIZE`, `GRAPH_NODES_MAX_SIZE`, `GRAPH_EDGES_MAX_SIZE`; `common/schema/graph/v1.ts:222,241,268-285,330-361`); new array fields must be bounded the same way. ([PR #227784](https://github.com/elastic/kibana/pull/227784) · @kfirpeled; [PR #290980](https://github.com/elastic/kibana/pull/290980) · `common/schema/graph/v1.ts`)

- **Full error messages and stacks must not reach the client** — `use_fetch_graph_data` deliberately withholds the full error message and stack from the browser; richer client-side error detail is not acceptable even for authorized internal API callers. Server logs are the place for diagnostic detail. ([PR #227784](https://github.com/elastic/kibana/pull/227784) · @kfirpeled · `graph/src/hooks/use_fetch_graph_data.ts`)

- **Graph EBT events carry no entity or query data** — The four graph EBT schemas carry only enum keywords and booleans (`nodeType`, `action`, optional `state`; `change: added|removed`; `timeRangeChanged`, `queryChanged`; no fields for preview expanded) (`common/lib/telemetry/events/graph/index.ts:14-79`); `getSearchSubmittedEvent` reports whether the query or time range changed, not their values (`graph_telemetry.ts:74-83`). New graph telemetry fields must not include entity ids, EUIDs, filter values, KQL text or document ids. ([PR #297168](https://github.com/elastic/kibana/pull/297168))

  For now graph telemetry does not pass specific filters, time ranges or other values, only the enum and boolean fields above. The set of events is expected to grow over time.

## Performance constraints

- **Minimize client payload** — Graph responses can be massive; only pass fields required for the current visualization use case. ([PR #227784](https://github.com/elastic/kibana/pull/227784) · @kfirpeled · `common/schema/graph/v1.ts`)

- **Fetch-then-parse for large record sets** — All fetches (graph records + entity metadata) must complete before `parseRecords`; interleaved enrichment in parse loops is inefficient at scale. ([PR #227784](https://github.com/elastic/kibana/pull/227784) · @kfirpeled · `v1.ts`)

- **ES|QL grouping and pairing must stay in-query** — Actor→target pairing and pinned-relationship splitting belong in ES|QL; moving them to TypeScript risks record-limit trade-offs and breaks pinning/grouping correctness. ([PR #275276](https://github.com/elastic/kibana/pull/275276) · @kfirpeled; [PR #272452](https://github.com/elastic/kibana/pull/272452) · @kfirpeled, @albertoblaz)

- **8-FORK-branch ES|QL limit** — Relationship field additions approach an 8-branch FORK limit documented in constants; exceeding it breaks ES|QL query execution. ([PR #251178](https://github.com/elastic/kibana/pull/251178) · @kfirpeled · `common/constants.ts`)

- **Enrichment pagination page size** — Parallel entity enrichment fetches should not use very small page sizes (e.g. 100); team settled on 1k after reviewer suggested 5k. Entity enrichment is chunked at `ENRICHMENT_CHUNK_SIZE = 1000` unique ids per query, capped there to stay under Elasticsearch's dynamic boolean-clause limit, with chunks run in parallel under `p-retry` (`server/routes/graph/fetch_entity_enrichment.ts:34-36,121-149`). ([PR #269755](https://github.com/elastic/kibana/pull/269755) · @kfirpeled · `fetch_entity_enrichment.ts`)

- **ES|QL STATS for deduplication** — Prefer STATS in the query for known duplicate rows rather than shipping duplicates to the parser/client. ([PR #227784](https://github.com/elastic/kibana/pull/227784) · @kfirpeled · originally `fetch_entity_data.ts`)

- **Server-side label resolution** — Label logic on the server reduces client CPU during ReactFlow re-renders for large graphs. ([PR #227784](https://github.com/elastic/kibana/pull/227784) · @kfirpeled · `graph/src/components/utils.ts`)

- **`nodesLimit` truncates the graph and emits a message** — `parseRecords` applies `nodesLimit` and pushes `ApiMessageCode.ReachedNodesLimit` (`REACHED_NODES_LIMIT` in the response `messages`) when triggered (`server/routes/graph/parse_records.ts:449-453`); the client sends `nodesLimit: GRAPH_NODES_LIMIT` (`300`, `graph/src/common/constants.ts:24`; `graph_investigation.tsx:469`). Changes that increase node production per record push graphs into truncation sooner.

- **ES|QL `STATS … BY` pre-aggregation is mandatory; only the type/sub-type merge belongs in TypeScript** — Resolved by [PR #275276](https://github.com/elastic/kibana/pull/275276): the events and relationships queries must pre-aggregate in ES|QL (`STATS … BY` over pre-enrichment dimensions) so grouping runs before the `LIMIT`. Do not move grouping into TypeScript over raw rows. The only grouping allowed in TypeScript is the final merge by entity type/sub-type (`regroupEvents` / `regroupRelationships`), which is unavoidable because type/sub-type are only known after the follow-up enrichment query — and it must be a strict refinement of the ES|QL group key.

- **Client-side bounds in grouped previews** — Grouped-events previews load at most `MAX_DOCUMENTS_TO_LOAD = 50` documents (`flyout_v2/document/tools/graph/components/graph_visualization.tsx:51`), and per-document actor/target EUID resolution is bounded to 100 combinations per entity type so a document with many multi-value identity fields cannot freeze the UI ([PR #296210](https://github.com/elastic/kibana/pull/296210), `resolve_actor_and_targets.ts`). Do not remove either cap.

  > **[VERIFY]:** The 100-combination cap comes from the PR description; confirm the constant still lives in `resolve_actor_and_targets.ts` and whether 50 documents is a product limit or a performance limit.

- **Filter stores must not leak** — Every `getOrCreateFilterStore(scopeId)` must be matched by `destroyFilterStore(scopeId)` on unmount (`use_graph_filters.ts:49,62-66`). With per-mount scopes in flyout v2 (`${scopeId}-graph<useId>`), a consumer that creates stores outside `useGraphFilters` would add a new long-lived store and RxJS subscription per mounted graph. ([PR #301396](https://github.com/elastic/kibana/pull/301396))

  Reviewers enforce this pairing.

## Historical catches

- [PR #289467](https://github.com/elastic/kibana/pull/289467) — Reviewer caught that `must_not` was destructured with an `= []` default and mapped directly, crashing with `TypeError: mustNot.map is not a function` when a node's namespace came from a condition-based `whenClause` (most commonly a local user) because `conditionToQueryDsl` emits `must_not` as a single object. A generic reviewer would read `must_not ?? []` as safe and would not know which upstream namespace resolution path produces the non-array shape. (@niros1 · `search_filters.ts`)

- [PR #289467](https://github.com/elastic/kibana/pull/289467) — Reviewer caught that the DSL-to-filter translator fell through to `return []` for `match`/`terms`/`wildcard`/`range`, silently weakening the AND and re-introducing the exact entity over-matching (`alice@aws` / `alice@okta` / `alice@entra_id`) the PR set out to fix, for asset-discovery-namespaced entities. A generic reviewer would see an empty-array default as a harmless no-op rather than a silent scope expansion. (@niros1 · `search_filters.ts`)

- [PR #275276](https://github.com/elastic/kibana/pull/275276) — All ES|QL `STATS … BY` grouping for the events and entities/relationships queries had been removed by mistake when the unsupported `LOOKUP JOIN` was dropped for CPS support. Without pre-aggregation the queries returned one raw row per document/triple, and grouping then ran in TypeScript over ungrouped (and `LIMIT`-truncated) records — degrading graph capability by producing fewer results and incorrect grouped nodes/counts. Fixed by restoring the `STATS … BY` clauses in ES|QL, keeping the TS type/sub-type merge as a strict refinement of the ES|QL group key. A generic reviewer would treat grouping location as a performance detail and miss that dropping ES|QL pre-aggregation changes the *correctness* of the rendered graph. (@alexreal1314 · `fetch_events_graph.ts`, `fetch_entity_relationships_graph.ts`, `parse_records.ts`)

- [PR #275276](https://github.com/elastic/kibana/pull/275276) — Reviewer caught that grouping `actorEntityId` and `targetEntityId` separately breaks actor→target pairing; fix requires `VALUES(targetId)` in ES|QL — a generic reviewer would not know separate GROUP BY columns collapse paired event semantics. (@kfirpeled · `fetch_events_graph.ts`, `fetch_entity_relationships_graph.ts`)

- [PR #272452](https://github.com/elastic/kibana/pull/272452) — Pinning logic must stay in ES|QL and check both actor and target sides when resolving pinned entities — runtime TypeScript splitting was rejected because it breaks pinning behavior invisible in UI-only review. (@kfirpeled, @albertoblaz · `fetch_entity_relationships_graph.ts`)

Two candidates from this capture: [PR #290980](https://github.com/elastic/kibana/pull/290980) (@JordanSh caught a locally redefined `AssetCriticalityLevel` list; recorded above as an invariant) and [PR #301396](https://github.com/elastic/kibana/pull/301396) (filters carried over between graphs because every graph shared one page-level `scopeId` and flyout v2 keeps prior flyouts mounted).
