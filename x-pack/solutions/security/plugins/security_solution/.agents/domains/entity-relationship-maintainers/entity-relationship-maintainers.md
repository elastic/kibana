# Domain: Entity Relationship Maintainers

## What every reviewer must know

The architecture is a DSL composite aggregation, so we can paginate over distinct actors, followed by ES|QL, which gets specific filters and clauses for a specific integration and maintainer. Those 2 steps either query a specific logs index source if it's a log-based maintainer, or the entities index if it's a raw identifiers-based maintainer. The next step is preparing payloads to be written to the entities index and updating entities — we could either validate if the entity exists before writing or not. The last step is reporting telemetry.

Concretely: the shared 2-step engine lives in `security_solution/.../maintainers/engine/`, with per-relationship, config-driven maintainers (`accesses`, `administers`, `communicates_with`, `owns`, `supervises`) resolving raw signals into canonical `entity.relationships.<relType>.ids` on actor entity documents, validating resolved targets against the entities-v2 index when `validateTargetIds` is set, and dual-writing relationship observation metadata via `EntityMetadataClient`. Each maintainer is registered at plugin setup as a `RegisterEntityMaintainerConfig` into the in-memory `EntityMaintainersRegistry` singleton plus a Task Manager task definition whose `createTaskRunner` delegates to `executeMaintainerRun` (`entity_store/server/tasks/entity_maintainers/index.ts:138`); lifecycle (init/start/stop/runNow/runSync/removeAll) is owned by `EntityMaintainersClient` (`entity_store/server/domain/entity_maintainers/entity_maintainers_client.ts`). Step 1 (`buildActorDiscoveryQuery`) pages actors via composite aggregation against `config.indexPattern(namespace)` with `after_key`, capped at `MAX_ITERATIONS=1000` pages of `COMPOSITE_PAGE_SIZE=3500` buckets (`engine/run_relationship_maintainer.ts:103`); Step 2 (`buildTargetsPerActorQuery`) runs one ES|QL query per actor page, prefixed with `SET unmapped_fields="nullify"` (`engine/run_relationship_maintainer.ts:143`), and results are parsed by `parseTargetsPerActorRows`, written per page via `crudClient.bulkUpdateEntity` (`:287`) and appended as metadata docs (`:329`). Raw-identifiers maintainers (`administers`, `supervises`, `owns`) read from the latest entity index, must set `disableLookbackWindow: true` and gate on `entity.lifecycle.last_seen`, use a `lastProcessedTimestamp` watermark for incremental processing, and require an explicit Task Manager `timeout` (e.g. `1h`) because the framework default `DEFAULT_ENTITY_MAINTAINER_TIMEOUT = '5m'` is insufficient for full scans over 160M+ docs.

## Architectural invariants

- **Abort-signal errors must be detected and treated as a clean (non-error) exit — checked _before_ `isIndexNotFound`** — When the abort signal fires during `esClient.search`, the resulting error does not match `isIndexNotFound`, falls through to the generic error logger and re-throw, and crashes the maintainer, blocking future runs. (PR #266159, @macroscopeapp, `engine/run_relationship_maintainer.ts`)
- **An ES|QL query failure must surface as an error in the return metrics — never write partial data while reporting success** — Continuing with `break` after an ES|QL failure lets already-collected records be written while returning success metrics, so callers/operators cannot distinguish a partial run from a complete one. (PR #266159, @macroscopeapp)
- **The error path of per-page writes must return accumulated `totalWriteResult` / `totalMetadataResult`, never hard zeros** — Per-page writes broke the zero-on-error invariant that held with end-of-integration single writes. Returning zeros makes the completion log report `written=0 records=<big> outcome=error` even though thousands of entities were persisted, misleading operators during exactly the timeout scenario the per-page write is meant to surface. ([PR #281804](https://github.com/elastic/kibana/pull/281804), @github-actions (Claude Reviewer), `maintainers/engine/run_relationship_maintainer.ts`)
- **EUID values in ES|QL must be computed via `euid.esql.getEuidEvaluation(...)`, not manual string concatenation** — Hand-built IDs like `CONCAT("user:", user.name)` bypass the canonical EUID path and force extracting far more fields than necessary; the evaluation helper is the canonical, minimal-extraction path. (PR #255418 @JordanSh; PR #262345 @niros1)
- **Host-scoped user EUIDs must be built from `user.name` alone — never `COALESCE(user.name, user.email)`** — A document with `user.email` but no `user.name` is classified by extraction as an IDP user, never host-scoped, so emitting `user:alice@corp.com@h1@local` references an EUID that does not exist in the entity store and 404s on write. The presence gate stays broader (matching `user.email OR user.name`) to mirror extraction's `documentsFilter`; rows that pass the gate but lack `user.name` yield a NULL EUID and are dropped by the `WHERE COALESCE(actorUserId, "") != ""` guard. ([PR #281804](https://github.com/elastic/kibana/pull/281804), @romulets, `entity_store/common/domain/euid/esql.ts`)
- **An EUID presence gate must match what extraction's `documentsFilter` actually uses — never widen it independently** — Widening the gate beyond extraction's filter admits documents extraction never turned into entities, producing dangling EUIDs. ([PR #281804](https://github.com/elastic/kibana/pull/281804), @romulets)
- **Empty/garbage target entity IDs must be filtered consistently for every entity-type variant in the ES|QL WHERE clause** — Guarding only one type (e.g. `Device`) while leaving another (e.g. `User`) unguarded produces invalid IDs such as `"user:@entra_id"` from an empty UPN, which is neither filtered nor a valid identity. (PR #262345, @macroscopeapp, `communicates_with/integrations/azure_auditlogs/build_esql_query.ts`)
- **The Task Manager `abortController` signal must be propagated through the entire maintainer run** — TM provides an abort controller when creating the task; ignoring it means the task cannot be cancelled cleanly. (PR #255418, @pmuellr, `accesses/index.ts`)
- **The maintainer registry must throw on an unknown ID, never return `undefined`** — A silent `undefined` from `get`/`getLifecycle` hides bugs and makes "not registered" indistinguishable from "not yet initialised". (PR #262317, @chennn1990, `entity_maintainers_registry.ts`)
- **The namespace must be validated against `NAMESPACE_PATTERN` at the engine boundary before any index-pattern interpolation** — `assertValidNamespace` runs at the top of `runRelationshipMaintainer` (`engine/run_relationship_maintainer.ts:401`; pattern `/^[a-z0-9][a-z0-9_-]{0,99}$/` in `engine/validate_namespace.ts`). This is a correctness guard (rejecting malformed namespaces), not a security/injection boundary.
- **The watermark must only advance after a non-aborted run** — `administers`/`supervises`/`owns` return the new `lastProcessedTimestamp` on success but return the prior `status.state` unchanged on abort (`administers/index.ts:48`). Only an abort blocks the watermark; a per-integration ES|QL failure does **not** prevent the watermark from advancing. Advancing on an aborted run would skip un-processed entities permanently.
- **Full-scan and raw-identifiers maintainers must set an explicit Task Manager `timeout` matched to expected run duration** — Leaving `timeout` unset inherits `DEFAULT_ENTITY_MAINTAINER_TIMEOUT = '5m'`; for a daily full scan over a 160M+ doc store, 5m kills the first run before completion, and because the watermark only advances on success, the maintainer keeps re-scanning the same window. Now applied consistently across `administers`, `supervises`, and `owns`. (@darnautov, [PR #274261](https://github.com/elastic/kibana/pull/274261), fix applied across all maintainers in [PR #278471](https://github.com/elastic/kibana/pull/278471))
- **Task Manager saved-object state must persist only what the next run reads — `lastProcessedTimestamp`** — Spreading the full engine `RunResult` (`totalBuckets`, `totalRecords`, `totalWritten`, `totalNotFound`, truncated, redundant `lastRunTimestamp`, …) into TM state bloats the saved object with 9 fields that are never consumed. Return only `{ lastProcessedTimestamp: result.lastRunTimestamp }`; all run counters belong in telemetry, not state. (@darnautov, [PR #274261](https://github.com/elastic/kibana/pull/274261), `maintainers/owns/index.ts`, `maintainers/supervises/index.ts`)
- **Dual-write metadata append must filter to the same validated and successfully-written target set as `writeEntityIds`** — When `validateTargetIds` is set, `writeEntityIds` prunes dangling/unresolved targets from the latest index; appending metadata for the unfiltered target set records relationships the latest index rejected, causing latest-index vs history datastream divergence. (@seanrathier, PR #271806, `engine/run_relationship_maintainer.ts`)
- **Raw-identifiers maintainers must union all candidate identifier fields into EUID candidates, then validate every candidate against `.entities.v2.*` before writing** — The canonical EUID source field is not known a priori (email vs id vs name); picking a single field produces dangling IDs. Only targets passing `LOOKUP`/validation with `validateTargetIds: true` may be written. (@alexreal1314, [PR #274261](https://github.com/elastic/kibana/pull/274261), `maintainers/supervises/configs.ts`)
- **`disableLookbackWindow: true` is mandatory for entity-index sources** — Log-index maintainers use the 30-day `@timestamp` lookback; entity-index maintainers must disable it and gate on `entity.lifecycle.last_seen` instead. Mixing these up silently drops entity documents.
  > **[VERIFY]:** Is `disableLookbackWindow: true` checked anywhere at registration/validation time, or is it purely a convention a reviewer must catch by eye?
- **Relationship metadata writes must not go through the generic `CRUDClient`** — Metadata append and relationship-list logic belongs in dedicated clients (`EntityMetadataClient`); inserting it into the shared CRUD API leaks maintainer-specific behavior to all CRUD consumers. (@romulets, PR #271806, `entity_store/server/domain/crud/crud_client.ts`)
- **Raw Elasticsearch I/O must stay in `infra/elasticsearch/` — domain clients delegate, never call `esClient` directly** — Direct ES calls inside domain clients (e.g. CRUD client) bypass the infra isolation layer and make I/O paths harder to test and reason about. (@romulets, PR #271806, `entity_store/server/domain/crud/crud_client.ts`)
- **Metadata append path must default to `refresh: false`** — Relationship metadata is written to an append-only background datastream; waiting for refresh on every bulk append adds unnecessary latency with no caller requiring synchronous read-after-write. (@romulets, PR #271806, `entity_store/server/infra/elasticsearch/entity_metadata.ts`)
- **Scout maintainer API suites must call `waitForEntityStoreRunning` after install and set `apiTest.setTimeout(180_000)`** — The `running` status flips before the latest alias is ready, so jumping from the install 200/201 straight to seeding races entity-store initialization; and the default 60s Playwright timeout is too short for suites that issue `triggerMaintainerRun(..., { sync: true })` plus `waitForRelationshipIds` polling. (@MadameSheema, @github-actions (Claude Reviewer), [PR #274261](https://github.com/elastic/kibana/pull/274261), `test/scout/.../maintainers/user_target_raw_identifiers_maintainer_suite.spec.ts`)
- **Pre-install cleanup in `beforeAll` must use `clearEntityStoreIndices(esClient)`, covering all three index families** — Deleting only `LATEST_INDEX` and `UPDATES_INDEX` leaks stale history snapshots into the next run and diverges from `afterAll`. (@MadameSheema, [PR #274261](https://github.com/elastic/kibana/pull/274261))

## Common review patterns (learned from real PRs)

- **Omit unchanged relationship fields with `undefined`, not `{ ids: [] }`** — Setting an empty array explicitly clears the field and erases relationships observed in an earlier window but absent in the current one; `undefined` omits the field so prior data is preserved. (@tiansivive, PR #262911, `accesses/update_entities.ts`)
- **Prefer `satisfies SomeType` over `as SomeType`** — `satisfies` validates the object shape without widening it; flagged on update-entity functions. (@tiansivive, PR #262911)
- **Create `esClient` and `cpsEsClient` unconditionally; let each maintainer choose** — Do not gate CPS client creation behind an `isServerless` flag at the execution layer; the decision belongs to each maintainer's data-access intent. (@uri-weisman, PR #269578, `entity_store/server/tasks/entity_maintainers/execution.ts`)
- **Comments explain _why_, not _what_ — do not over-comment obvious decisions** — Long JSDoc blocks and inline comments that restate what the code already expresses (e.g. explaining that `user.name` is the identity field when the constant is already named `HOST_SCOPED_USER_EUID_FIELD`) get flagged as verbosity. Keep comments for non-obvious constraints and rejected alternatives; "future work" comments must link a ticket. (@romulets, [PR #281804](https://github.com/elastic/kibana/pull/281804), seen 2x on `entity_store/common/domain/euid/esql.ts`; @maxcold, PR #272948, `administers/configs.ts`)
- **When a union-based raw_identifiers EUID resolution is deliberate, say so in code** — Reviewers default to assuming a ranked pick (email → id → name) matching extraction's EUID ranking, and will flag unioning as producing dangling id-form EUIDs. State explicitly that unioning is intentional because you cannot know which field generated the entity's EUID, and that `validateTargetIds` (entity-store `LOOKUP`) drops non-matching EUIDs. (@github-actions (Claude Reviewer), [PR #274261](https://github.com/elastic/kibana/pull/274261), `maintainers/supervises/configs.ts`)
- **When bucketing ES|QL `FORK` branches, guarantee every batch has ≥ 2 branches** — Simple `chunk(fields, MAX_SIZE)` on a 9-field list at size 8 produces `[8, 1]`, and the 1-branch batch fails at ES|QL query time. Compute `batchCount = Math.ceil(total / MAX_SIZE)` then `chunk(fields, Math.ceil(total / batchCount))`. Thread was left unresolved and merged without the fix. (@github-actions (Claude Reviewer), [PR #276599](https://github.com/elastic/kibana/pull/276599), `cloud_security_posture/server/routes/graph/fetch_entity_relationships_graph.ts`)
  > **[VERIFY]:** Was this `[8, 1]` FORK-batching hazard ever fixed, or is it still live in the entity-relationships graph route?
- **Scout fixtures: export only what the specs consume** — A 500-line `helpers.ts` largely copied from `entity_store/test/scout/api/fixtures/helpers.ts`, with functions no spec imports, was flagged as dead code plus a parallel copy to maintain. Trim to consumed symbols and lift genuinely shared pieces into `@kbn/scout-security`. Same applies to `ENTITY_STORE_ROUTES`: unused keys (`FORCE_CCS_EXTRACT_TO_UPDATES`, `CHECK_PRIVILEGES`, `CRUD_*`, `RESOLUTION_*`) had incorrect URL paths that would 404 if anyone used them. (@github-actions (Claude Reviewer), [PR #274261](https://github.com/elastic/kibana/pull/274261), `test/scout/api/fixtures/maintainers/helpers.ts`, `.../constants.ts`)
- **One registry map with typed `task` / `lifecycle` sub-properties — not two separate maps** — (@chennn1990, PR #262317, `entity_maintainers_registry.ts`)
- **Fail fast on a missing namespace; do not fall back to `""`** — Keep the `currentStatus?.namespace || currentStatus?.metadata?.namespace` lookup chain and let it surface early. (@chennn1990, PR #262317, `execution.ts`)
- **`autoStart` defaults to `true`; `autoStart: false` is the exceptional, test-only path** — Renamed from a no-default `enabled` flag. (@chennn1990, PR #262317, `utils/validator.ts`)
- **`extends` an existing interface instead of re-declaring its fields** — (@chennn1990, PR #262317, `entity_maintainers_client.ts`)
- **Deduplicate lookback-filter construction into the shared `buildLookbackFilter`** — Used in both `run_relationship_maintainer.ts` and `build_actor_discovery_query.ts`. (@maxcold, PR #272948)
- **Log a run/skip decision once, at the point of decision — not again in the outer loop** — (@alexreal1314, PR #269578, `engine/run_relationship_maintainer.ts`)
- **Keep synchronous-run API execution separate from Task Manager task code** — Extract `executeMaintainerRun` / `runSync` into a dedicated `execution.ts`; the API route calls it directly, bypassing TM status/licensing checks that don't apply to sync API calls. (@chennn1990, PR #262317, `entity_store/server/tasks/entity_maintainers/index.ts`)
- **Use `esClient.helpers.bulk` for high-fan-out metadata bulk writes** — Raw `esClient.bulk` materializes the entire operations array; the helper chunks by `flushBytes`, streams via a generator, retries 429s, and supports an `onDrop` callback for drop-reason logging. (@opauloh, PR #271806, `entity_store/server/infra/elasticsearch/entity_metadata.ts`)
- **Do not expose index-name helpers for the metadata datastream** — Metadata lives in a datastream/write alias, not a concrete index; dead `getEntityMetadataIndexName` helpers and "index" naming mislead callers. (@romulets, PR #271806, `entity_store/common/domain/entity_index.ts`)
- **Do not leak internal implementation details into customer-facing copy** — Fold internal artifacts (e.g. "entity relationship history") under existing customer concepts ("Security Entity store records"). (@romulets, PR #271806, `public/entity_analytics/.../clear_entity_data_button.tsx`)
- **IDP user EUIDs are namespace-suffixed; host targets are namespace-less** — User actors use `CONCAT("user:", <value>, "@<namespace>")` (e.g. `user:<id>@okta`); host targets use `host:<name>`. Null-safe `MV_APPEND` guards are required because `MV_APPEND(null, x)` returns null. ([PR #274261](https://github.com/elastic/kibana/pull/274261), `maintainers/supervises/configs.ts`, `maintainers/administers/configs.ts`)
- **New host-target raw-identifiers maintainers need their own Scout spec file** — `scout_max_one_describe` means a second `registerHostTargetRawIdentifiersMaintainerSuite` call in the same file fails lint; do not rely on a "reuse" comment in an existing spec (a comment saying "add a new entry here" was flagged as actively misleading). (@MadameSheema, [PR #274261](https://github.com/elastic/kibana/pull/274261))
- **`customActor.fields` must not include high-cardinality identifiers that vary per host** — For entity-index maintainers (`administers`, `supervises`, `owns`) the actor is discovered by `entity.id`; for log-index maintainers (`communicates_with`, `accesses`) by identity fields. Including `user.id` in `customActor.fields` for `system_auth` was the root cause of the bucket-explosion bug fixed in [PR #278471](https://github.com/elastic/kibana/pull/278471) — `user.id` varies across hosts, so the same username appeared with dozens of distinct IDs.

## Security considerations

- **Namespace validation (`assertValidNamespace`) is a correctness guard, not a security boundary** — it rejects malformed namespaces before index-pattern interpolation (`engine/validate_namespace.ts`, enforced at the top of `runRelationshipMaintainer`, `engine/run_relationship_maintainer.ts:401`), but is not relied upon as an index-pattern/injection defense.
- **Account-exclusion gaps are a known data-quality (not yet security-enforced) backlog** — Windows machine accounts (`WORKSTATION$`), Linux service accounts (root, bin, daemon, sshd, etc.), and network logon type 3 (machine-to-machine) are not currently excluded from accesses queries; authors deferred these. A reviewer adding a new integration should consider whether non-human/service identities pollute relationship data. (PR #255418, @niros1)
  > **[VERIFY]:** Should machine/service account exclusion be a hard requirement for new accesses/communicates_with integrations, or remain per-integration discretion? (unconfirmed)
- **Scout maintainer install routes require `securitySolution` + entity-analytics privileges that lower test roles lack** — Tests calling the entity-maintainers init/run routes must use `asInteractiveUser('admin')`; omitting the reason in test comments hides why elevated privileges are required. The reviewer asked for an inline comment; the author explained in the PR thread but did not add one. (@MadameSheema, [PR #274261](https://github.com/elastic/kibana/pull/274261))
- **License is checked per run via `licensing.getLicense()` before any ES work** — `DEFAULT_ENTITY_MAINTAINER_MIN_LICENSE = 'basic'` unless a maintainer overrides it (`entity_store/server/tasks/entity_maintainers/execution.ts:54`). A maintainer requiring a higher tier must declare it at registration; the framework will not infer it.
  > **[VERIFY]:** Are any current maintainers expected to require above-`basic`, or is `basic` correct for all of them?

## Performance constraints

- **Each query should run in a few seconds, otherwise it's not scalable when running multiple integrations for each maintainer.** This is the governing budget: every Step 1 composite-aggregation page and every Step 2 ES|QL query is one of many issued per run, across every integration a maintainer is configured with. A query that takes tens of seconds does not just slow one run — it multiplies across integrations and makes the maintainer unschedulable.
- **Step 1 pages actors via composite aggregation at `COMPOSITE_PAGE_SIZE = 3500` per page, capped at `MAX_ITERATIONS = 1000` pages** (`engine/constants.ts`, `engine/build_actor_discovery_query.ts`); each page becomes an OR-of-`terms` DSL filter narrowing the Step 2 ES|QL query. Adding actor fields or relaxing actor-presence filters widens the candidate set and increases ES|QL load per page. `COMPOSITE_PAGE_SIZE` is tuned against source **log** volume (typically higher than entity count), not a fixed entity-count ceiling — large customers reach on the order of ~1M entities, usually fewer.
- **An ES|QL failure for one integration currently stops the entire maintainer run** — no subsequent integration writes its results; per-integration error isolation was suggested but is unresolved. (PR #255418, @niros1)
- **Full-scan maintainers over 160M+ docs require explicit `timeout: '1h'` (or similar) — not the 5m TM default** — A timed-out first run leaves the watermark unchanged, causing repeated full re-scans of the same window on every daily schedule. (@darnautov, [PR #274261](https://github.com/elastic/kibana/pull/274261))
- **Incremental raw-identifiers maintainers advance `lastProcessedTimestamp` only on successful completion** — Watermark-based incremental processing via `entity.lifecycle.last_seen > lastProcessedTimestamp` (`engine/build_raw_identifiers_query.ts`, `administers/index.ts`) avoids re-processing the entire entity index each run; a failed or timed-out run must not advance the watermark.
- **The watermark is per-maintainer, not per-integration** — When one maintainer runs multiple integration configs (e.g. `supervises` runs both `entityanalytics_okta` and `entityanalytics_entra_id`), they share a single `lastProcessedTimestamp`. If one integration's scan is slow, the watermark does not advance until all complete. (@maxcold, PR #272948, raised as a future scaling concern)
- **Metadata bulk append uses `refresh: false` by default** — Background-written append-only datastream records do not require synchronous refresh; adding refresh waits would multiply write latency across high-fan-out actor→target pairs. (@romulets, PR #271806)
- **High-fan-out metadata writes should use `esClient.helpers.bulk` with `flushBytes` chunking** — Prevents exceeding `http.max_content_length` on large maintainer runs. (@opauloh, PR #271806)
- **`disableLookbackWindow` is fully wired into both the composite-agg and ES|QL query builders** (as of follow-up PR #272948) — raw-identifiers maintainers gate out the lookback-window time filter in the actual queries, not only in the `Maintainer.lookback_window` metadata field.
- **`matchExistingTargetIds` issues a single unbounded `search` over all candidate target EUIDs** — The opt-in target-validation step will hit the ES `max_terms_count` limit on large stores. Raised in review and not addressed. (@github-actions (Claude Reviewer), PR #272948)
  > **[VERIFY]:** Is `matchExistingTargetIds` chunked now, or is `max_terms_count` still a live risk for `validateTargetIds: true` maintainers on large stores?
- **Known framework-level gaps raised by @darnautov (PR #272948) and not yet closed:** maintainer configs do not expose Task Manager `cost` / `priority`, so a daily composite-agg + bulk-write task registers as `TaskCost.Normal` when it likely warrants `TaskCost.ExtraLarge`; there is no `stateSchemaByVersion` on task registration even though non-empty state persists between runs; and `runEntityMaintainerTask` always returns normally, so `throwUnrecoverableError` / `throwRetryableError` are never reached and transient ES failures do not trigger TM retries.
  > **[VERIFY]:** Are the TM `cost`, `stateSchemaByVersion`, and error-classification gaps tracked anywhere, and should reviewers block new maintainers on them?
