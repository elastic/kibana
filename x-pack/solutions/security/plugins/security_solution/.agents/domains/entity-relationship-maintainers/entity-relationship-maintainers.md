# Domain: Entity Relationship Maintainers

## What every reviewer must know

The architecture is a DSL composite aggregation, so we can paginate over distinct actors, followed by ES|QL, which gets specific filters and clauses for a specific integration and maintainer. Those 2 steps either query a specific logs index source if it's a log-based maintainer, or the entities index if it's a raw identifiers-based maintainer. The next step is preparing payloads to be written to the entities index and updating entities — we could either validate if the entity exists before writing or not. The last step is reporting telemetry.

Concretely: the shared 2-step engine lives in `security_solution/server/lib/entity_analytics/maintainers/engine/`, with per-relationship, config-driven maintainers (`accesses`, `administers`, `communicates_with`, `owns`, `supervises`) resolving raw signals into canonical `entity.relationships.<relType>.ids` on actor entity documents, validating resolved targets against the entity latest alias when `validateTargetIds` is set, and dual-writing `relationship_observed` metadata via `EntityMetadataClient`. Each maintainer is a `RegisterEntityMaintainerConfig` registered from `security_solution/server/plugin.ts:440-444` (via `plugins.entityStore?.registerEntityMaintainer`) into the in-memory `EntityMaintainersRegistry` singleton plus a Task Manager task definition whose runner delegates to `executeMaintainerRun` (`x-pack/platform/plugins/shared/entity_store/server/tasks/entity_maintainers/execution.ts:107`); lifecycle (init/start/stop/runNow/runSync/removeAll) is owned by `EntityMaintainersClient` (`x-pack/platform/plugins/shared/entity_store/server/domain/entity_maintainers/entity_maintainers_client.ts`). **The Entity Store plugin moved from `x-pack/solutions/security/plugins/entity_store/` to `x-pack/platform/plugins/shared/entity_store/` with solution-neutral index names ([PR #282130](https://github.com/elastic/kibana/pull/282130); consumers that queried only the renamed indices fixed in [PR #286313](https://github.com/elastic/kibana/pull/286313)) — the old path no longer exists; resolve indices via `getEntitiesAlias(ENTITY_LATEST | ENTITY_METADATA, namespace)`, never by hard-coded name.** Step 1 (`buildActorDiscoveryQuery`, `engine/build_actor_discovery_query.ts:55`) pages actors via composite aggregation against `config.indexPattern(namespace)` with `after_key`, capped at `MAX_ITERATIONS=1000` pages of `COMPOSITE_PAGE_SIZE=3500` buckets (`engine/constants.ts`); Step 2 (`buildTargetsPerActorQuery`) runs one ES|QL query per actor page with the `ESQL_ENGINE_PREAMBLE` (`SET unmapped_fields="nullify";`) prepended (`engine/build_targets_per_actor_query.ts:197-206`). Config kinds are a discriminated union (`engine/types.ts:332`): `bucketed` (accesses — default builder, two keys split at threshold 4), `standard` (communicates_with — default builder, one key) and `override` (administers, owns, supervises — the integration supplies the full Step 2 ES|QL). Rows are parsed by `parseTargetsPerActorRows`, written per page via `writeEntityIds` → `crudClient.bulkUpdateEntity` (`engine/update_entities.ts:216`) and appended as metadata docs (`engine/write_relationship_metadatas.ts`); each integration is run stage by stage (`fetch-actors | fetch-targets | entity-write | metadata-write`) and ends with an outcome of `index_missing | empty | partial | producing | error` (`engine/run_relationship_maintainer.ts:172,245`). Entity-index sources (administers/AD, owns/Okta, supervises/Okta+Entra ID+SailPoint) must set `disableLookbackWindow: true`, gate on `entity.lifecycle.last_seen`, and use a `lastProcessedTimestamp` watermark; all five relationship maintainers run on a `1d` interval with an explicit Task Manager `timeout: '1h'` because the framework default `DEFAULT_ENTITY_MAINTAINER_TIMEOUT = '5m'` is insufficient for full scans over 160M+ docs.

### AWS `user.entity.id` ranking and the latest-index mapping migration

- **[PR #296129](https://github.com/elastic/kibana/pull/296129) changed the user EUID that maintainers compute for AWS actors.** The user definition (`x-pack/platform/plugins/shared/entity_store/common/domain/definitions/user.ts`) gained a ranking branch: when `cloud.provider` is in `CLOUD_PROVIDERS_RANKING_USER_ENTITY_ID` (currently `['aws']`), `user.entity.id@entity.namespace` ranks first, then the default ranking is repeated inside the branch (a matched ES|QL branch that yields NULL returns NULL — it never falls through). Translators derive from the definition, so no maintainer code changed, but the generated ES|QL in `accesses/`, `communicates_with/` and `supervises/__snapshots__/configs.test.ts.snap` gained `user_entity_id_present`, `_euid_branch_1_cond = (TO_STRING(cloud.provider) == "aws")` and a separate default `_euid_branch_2_formula`. Net effect: the `aws_cloudtrail` configs in `accesses` and `communicates_with` now key CloudTrail actors (IAM user, or role ARN for an assumed role) as `user:<ARN>@aws`, the same EUID as the Cloud Asset Inventory IAM user/role entity; AWS docs without `user.entity.id` and non-AWS docs are unchanged; `documentsFilter` and the creation gate are unchanged (CloudTrail `event.kind: event` cannot create users). Depends on integrations#21870 and cloudbeat#9034 (EC2 inventory must not put the instance ARN in `user.entity.id`).
- **[PR #305241](https://github.com/elastic/kibana/pull/305241) touched no maintainer files, but changes what the entity latest index holds.** It adds `LATEST_INDEX_MAPPINGS_VERSION` (`common/domain/entity_index.ts`, separate from `MAPPING_VERSION`, stamped in `_meta.latestMappingsVersion`), a one-shot Task Manager task `entity_store:v2:latest_index_mappings_migration` scheduled from `plugin.start()` that `putMapping`s only missing fields per installed space (the latest index is `index.mode: lookup`; conflicting types are warned, not changed; all-400/401/403 failures mark the task unrecoverable), and stores `user.entity.id` on user entity records. Rollout window: between upgrade and migration completion (or on migration failure) the entities index lacks `user.entity.id`, and `SET unmapped_fields="nullify"` does **not** cover a lookup-index column once `STATS`/`KEEP` precedes a `LOOKUP JOIN`.
  Which maintainer queries reference `user.entity.id`: every query built with the full shared user EUID builder reads the field regardless of provider — the default-actor log sources (`accesses` and `communicates_with` Elastic Defend and AWS CloudTrail, `communicates_with` Jamf Pro) and the Workday `supervises` target — while only the ranking branch is AWS-gated (`cloud.provider == "aws"`). The host-scoped sources (System Auth, System Security, CrowdStrike FDR) use the minimized host-scoped EUID and do not read it, and neither do the entity-index sources (`administers`, `owns`, `supervises` Okta/Entra ID/SailPoint), which read the latest alias with `FROM` (covered by the nullify preamble) and validate via `matchExistingTargetIds` (a DSL `terms` query, not `LOOKUP JOIN`). These source-log reads do not depend on the latest-index mapping migration; the migration concerns the entities latest index column that extraction's `LOOKUP JOIN` and record-based lookups read.
  Pre-upgrade AWS user entities lack `user.entity.id` until re-extracted (accepted in #305241). That is acceptable: entities that are not updated are stale, and newer entities created with `user.entity.id` are updated by the maintainer.

## Architectural invariants

- **Abort-signal errors must be detected and treated as a clean (non-error) exit — checked _before_ `isIndexNotFound`** — When the abort signal fires during `esClient.search`, the resulting error does not match `isIndexNotFound`, falls through to the generic error logger and re-throw, and crashes the maintainer, blocking future runs. (PR #266159, @macroscopeapp, `engine/run_relationship_maintainer.ts`)
- **A failed integration must return `outcome: 'error'` with accumulated (non-zero) counters, never zeros** — `runIntegration` streams writes per page, so pages 1..N-1 are already durable when a later page throws. Returning zeros would misreport `written=0` when thousands of entities were persisted. The `outcome` field is how callers distinguish a partial run from a clean one; lying about counts makes that signal useless. (PR #266159, @macroscopeapp; counters-on-error invariant: PR #281804)
- **The error path of per-page writes must return accumulated `totalWriteResult` / `totalMetadataResult`, never hard zeros** — Per-page writes broke the zero-on-error invariant that held with end-of-integration single writes. Returning zeros makes the completion log report `written=0 records=<big> outcome=error` even though thousands of entities were persisted, misleading operators during exactly the timeout scenario the per-page write is meant to surface. ([PR #281804](https://github.com/elastic/kibana/pull/281804), @github-actions (Claude Reviewer), `maintainers/engine/run_relationship_maintainer.ts`)
- **Every failure path in the engine must carry the maintainer/integration log prefix — including non-throwing bulk-item failures** — A stage-qualified error log only on the throw path leaves `bulkUpdateEntity` error items, `bulkAppendMetadata` `failed` counts and "Failed to append ..." from `writeRelationshipMetadatas` logged without context, so "operators cannot associate them with the failing maintainer/integration". Pass `logPrefix` into the helpers and handle returned failures with the same context. ([PR #294653](https://github.com/elastic/kibana/pull/294653), Libra automated review + @maxcold, `engine/run_relationship_maintainer.ts`)
- **One error log per failure — no double logging across layers** — Do not log-and-rethrow in an inner helper (e.g. `matchExistingTargetIds`) and log again in the outer stage wrapper; do not re-log what a lower layer or Task Manager already logs on throw. (PR #294653, Libra; [PR #305241](https://github.com/elastic/kibana/pull/305241), @darnautov: "this one makes it three log lines for the same failure")
- **Telemetry counters must stay per-source and per-stage accurate** — Relationship maintainers report a `funnel` (`scanned, qualified, proposed, applied, droppedNotInStore, targetIdsNotInStore, failed, metadataDocsApplied, metadataDocsFailed`), per-integration `sources[]` and per-relationship `breakdown[]` through `MaintainerTelemetryClient` (`entity_store/server/tasks/entity_maintainers/maintainer_telemetry_client.ts`). Per-source applied counts and the failing-stage label were added in PR #294653; `targetIdsNotInStore` (target EUIDs pruned by validation, distinct from actors `droppedNotInStore`) in [PR #288089](https://github.com/elastic/kibana/pull/288089); relationship-metadata write failures surfaced in telemetry and task logs in [PR #287802](https://github.com/elastic/kibana/pull/287802). A change that swallows a write failure or folds counts across sources breaks the only operator signal for partial runs.
  The failing stage is already sent as a telemetry event (the signal @chennn1990 asked for in PR #294653). The Security portal dashboard still needs to be updated to reflect it.
- **EUID values in ES|QL must be computed via `euid.esql.getEuidEvaluation(...)`, not manual string concatenation** — Hand-built IDs like `CONCAT("user:", user.name)` bypass the canonical EUID path and force extracting far more fields than necessary; the evaluation helper is the canonical, minimal-extraction path. Ranking changes in the entity definition (e.g. the AWS `user.entity.id` branch, PR #296129) then reach every maintainer automatically and show up as `configs.test.ts.snap` churn — that churn is expected, not a reason to special-case maintainers. (PR #255418 @JordanSh; PR #262345 @niros1)
- **Host-scoped user EUIDs must be built from `user.name` alone — never `COALESCE(user.name, user.email)`** — A document with `user.email` but no `user.name` is classified by extraction as an IDP user, never host-scoped, so emitting `user:alice@corp.com@h1@local` references an EUID that does not exist in the entity store and 404s on write. The presence gate stays broader (matching `user.email OR user.name`) to mirror extraction's `documentsFilter`; rows that pass the gate but lack `user.name` yield a NULL EUID and are dropped by the `WHERE COALESCE(actorUserId, "") != ""` guard. ([PR #281804](https://github.com/elastic/kibana/pull/281804), @romulets, `x-pack/platform/plugins/shared/entity_store/common/domain/euid/esql.ts`)
- **An EUID presence gate must match what extraction's `documentsFilter` actually uses — never widen it independently** — Widening the gate beyond extraction's filter admits documents extraction never turned into entities, producing dangling EUIDs. ([PR #281804](https://github.com/elastic/kibana/pull/281804), @romulets)
- **Record-based EUID lookups must resolve the same identity that created the entity** — Whether a field is stored does not establish whether it took part in the resolved identity. Dropping a higher-ranked field from storage (`user.entity.id`) made `getEuidDslFilterBasedOnEntityRecord` rank a lower field (session `user.email`) and lose the "higher-ranked field missing" exclusion; PR #296129 shipped a stopgap (AWS records looked up by `user.id`), PR #305241 stores the field, and the proper fix is tracked in [kibana#297666](https://github.com/elastic/kibana/issues/297666). (Libra automated review, author agreed, `entity_store/common/domain/definitions/user.ts`, `.../euid/dsl.ts`)
- **Empty/garbage target entity IDs must be filtered consistently for every entity-type variant in the ES|QL WHERE clause** — Guarding only one type (e.g. `Device`) while leaving another (e.g. `User`) unguarded produces invalid IDs such as `"user:@entra_id"` from an empty UPN, which is neither filtered nor a valid identity. Originally caught on the now-removed `communicates_with/integrations/azure_auditlogs/build_esql_query.ts` (removed in PR #275067); the rule still applies to every `override` query and `targetEvalOverride`. (PR #262345, @macroscopeapp)
- **The Task Manager `abortController` signal must be propagated through the entire maintainer run — into every Elasticsearch call** — TM provides an abort controller when creating the task; ignoring it, or checking it only between loop iterations while ES calls run uncancellable, means a task timeout or Kibana shutdown cannot cancel in-flight requests. (PR #255418, @pmuellr, `accesses/index.ts`; same rule enforced for entity_store tasks in PR #305241, Libra)
- **The maintainer registry must throw on an unknown ID, never return `undefined`** — A silent `undefined` from `get`/`getLifecycle` hides bugs and makes "not registered" indistinguishable from "not yet initialised". (PR #262317, @chennn1990, `x-pack/platform/plugins/shared/entity_store/server/tasks/entity_maintainers/entity_maintainers_registry.ts`)
- **The namespace must be validated against `NAMESPACE_PATTERN` at the engine boundary before any index-pattern interpolation** — `assertValidNamespace` runs at the top of `runRelationshipMaintainer` (`engine/run_relationship_maintainer.ts:453`; pattern `/^[a-z0-9][a-z0-9_-]{0,99}$/` in `engine/validate_namespace.ts`). This is a correctness guard (rejecting malformed namespaces), not a security/injection boundary.
- **The watermark must only advance after a non-aborted run** — `administers`/`supervises`/`owns` return `{ ...persistedResult, lastProcessedTimestamp: lastRunTimestamp }` on success but return the prior `status.state` unchanged on abort (`administers/index.ts:34,99`, `owns/index.ts:34,100`, `supervises/index.ts:35`). Only an abort blocks the watermark; a per-integration ES|QL failure does **not** prevent the watermark from advancing. Advancing on an aborted run would skip un-processed entities permanently.
- **Full-scan and raw-identifiers maintainers must set an explicit Task Manager `timeout` matched to expected run duration** — Leaving `timeout` unset inherits `DEFAULT_ENTITY_MAINTAINER_TIMEOUT = '5m'`; for a daily full scan over a 160M+ doc store, 5m kills the first run before completion, and because the watermark only advances on success, the maintainer keeps re-scanning the same window. All five relationship maintainers now set `timeout: '1h'`. (@darnautov, [PR #274261](https://github.com/elastic/kibana/pull/274261), fix applied across all maintainers in [PR #278471](https://github.com/elastic/kibana/pull/278471))
- **Task Manager saved-object state must persist only what the next run reads — `lastProcessedTimestamp`** — Spreading the full engine `RunResult` (`totalBuckets`, `totalRecords`, `totalWritten`, `totalNotFound`, truncated, redundant `lastRunTimestamp`, …) into TM state bloats the saved object with 9 fields that are never consumed. Return only `{ lastProcessedTimestamp: result.lastRunTimestamp }`; all run counters belong in telemetry, not state. (@darnautov, [PR #274261](https://github.com/elastic/kibana/pull/274261), `maintainers/owns/index.ts`, `maintainers/supervises/index.ts`)
  The current `run` closures in `administers/index.ts`, `owns/index.ts` and `supervises/index.ts` do not meet this: they return `{ ...persistedResult, lastProcessedTimestamp }`, where `persistedResult` is the engine result minus `lastRunTimestamp`, so counters such as `totalBuckets`, `totalRecords`, `totalWritten`, `totalNotFound`, `totalIterations` and `truncated` are still written into Task Manager state. Treat this as an existing violation of the invariant, not a pattern to copy.
- **Dual-write metadata append must filter to the same validated and successfully-written target set as `writeEntityIds`** — When `validateTargetIds` is set, `writeEntityIds` prunes dangling/unresolved targets from the latest index; metadata is emitted only for actors in `succeededEntityIds` and, when validation ran, only validated targets. Appending metadata for the unfiltered target set records relationships the latest index rejected, causing latest-index vs history datastream divergence. (@seanrathier, PR #271806, `engine/write_relationship_metadatas.ts`)
- **Raw-identifiers maintainers must union all candidate identifier fields into EUID candidates, then validate every candidate against the entity latest alias before writing** — The canonical EUID source field is not known a priori (email vs id vs name); picking a single field produces dangling IDs. Only targets that pass `matchExistingTargetIds` (a `terms` query on `entity.id` against the `getEntitiesAlias(ENTITY_LATEST, ns)` alias) with `validateTargetIds: true` may be written. (@alexreal1314, [PR #274261](https://github.com/elastic/kibana/pull/274261), `maintainers/supervises/configs.ts`)
- **`disableLookbackWindow: true` is mandatory for entity-index sources** — Log-index maintainers use the 30-day `@timestamp` lookback; entity-index sources must disable it and gate on `entity.lifecycle.last_seen` instead. Mixing these up silently drops entity documents. Workday `supervises` is a log-index exception that also disables the default lookback but replaces it with its own `event.ingested` 30d DSL filter.
  `disableLookbackWindow` is an internal property (default `false`, so the 30d `@timestamp` lookback applies, `engine/build_actor_discovery_query.ts:21-26`) and is not checked at registration time, so it is a convention a reviewer must catch by eye. Workday, which snapshots the entire org, sets it to `true` because its `@timestamp` is `Hire_Date`; the default lookback would select only recently hired workers, so it is replaced by a custom `event.ingested` range query (`{ range: { 'event.ingested': { gte: WORKDAY_INGESTED_LOOKBACK_DSL } } }`, `supervises/configs.ts:277-279,299-301`) that selects all employees ingested by the latest snapshot run.
- **Relationship absence does not retract an edge unless the source resets first** — `bulkUpdateEntity` replaces `entity.relationships.<key>.ids` only for actors written in this run; an actor not observed keeps its prior edges. Sources that must retract (Workday `supervises`) set `resetRelationshipsBeforeRun`, which runs `preRunReset` (`engine/pre_run_reset.ts`, invoked at `engine/run_relationship_maintainer.ts:221`): a `hasRepopulatableSource` probe (`terminate_after: 1`) and only then `relationshipsClient.clearRelationshipIds({ entitySource, relationshipKey })` for every key the config writes (both bucket keys for `bucketed`); outcomes `proceed | empty | error`. Clearing without the probe would wipe edges when the source index is empty. (PR #292504)
  A partial reset (`update_by_query` with `conflicts: 'proceed'`) is acceptable: it self-heals on the next run.
- **Relationship metadata writes must not go through the generic `CRUDClient`** — Metadata append and relationship-list logic belongs in dedicated clients (`EntityMetadataClient`, `RelationshipsClient`); inserting it into the shared CRUD API leaks maintainer-specific behavior to all CRUD consumers. (@romulets, PR #271806, `x-pack/platform/plugins/shared/entity_store/server/domain/crud/crud_client.ts`)
- **Raw Elasticsearch I/O must stay in `infra/elasticsearch/` — domain clients delegate, never call `esClient` directly** — Direct ES calls inside domain clients (e.g. CRUD client) bypass the infra isolation layer and make I/O paths harder to test and reason about. (@romulets, PR #271806)
- **Metadata append path must default to `refresh: false`** — Relationship metadata is written to an append-only background datastream; waiting for refresh on every bulk append adds unnecessary latency with no caller requiring synchronous read-after-write. (@romulets, PR #271806, `x-pack/platform/plugins/shared/entity_store/server/infra/elasticsearch/entity_metadata.ts`)
- **Tests must assert on errors/outcomes, not on logger output strings** — "relying on logs is a bit of weak verification"; log-string assertion batches that duplicate outcome coverage get removed. (@chennn1990, PR #294653, author agreed, `engine/run_relationship_maintainer.test.ts`)
- **Scout maintainer API suites must call `waitForEntityStoreRunning` after install and set `apiTest.setTimeout(180_000)`** — The `running` status flips before the latest alias is ready, so jumping from the install 200/201 straight to seeding races entity-store initialization; and the default 60s Playwright timeout is too short for suites that issue `triggerMaintainerRun(..., { sync: true })` plus `waitForRelationshipIds` polling. (@MadameSheema, @github-actions (Claude Reviewer), [PR #274261](https://github.com/elastic/kibana/pull/274261), `test/scout/.../maintainers/supervises_okta_maintainer.spec.ts`)
- **Pre-install cleanup in `beforeAll` must use `clearEntityStoreIndices(esClient)`, covering all three index families** — Deleting only `LATEST_INDEX` and `UPDATES_INDEX` leaks stale history snapshots into the next run and diverges from `afterAll`. (@MadameSheema, [PR #274261](https://github.com/elastic/kibana/pull/274261))
  Test-isolation policy: suites should be isolated as much as possible without impacting performance. Maintainer suites deliberately do not tear down the entire entity analytics engine, because it is too heavy to run before every suite that needs it (PR #292504 Workday, PR #295263 SailPoint). PR #305241 moved a broad `clearEntityStoreIndices` teardown to targeted cleanup after review.

## Common review patterns (learned from real PRs)

- **Omit unchanged relationship fields with `undefined`, not `{ ids: [] }`** — Setting an empty array explicitly clears the field and erases relationships observed in an earlier window but absent in the current one; `undefined` omits the field so prior data is preserved. (@tiansivive, PR #262911, `engine/update_entities.ts`)
- **Prefer `satisfies SomeType` over `as SomeType`** — `satisfies` validates the object shape without widening it; flagged on update-entity functions. (@tiansivive, PR #262911)
- **Create `esClient` and `cpsEsClient` unconditionally; let each maintainer choose** — Do not gate CPS client creation behind an `isServerless` flag at the execution layer; the decision belongs to each maintainer's data-access intent. Today only the log-index maintainers (`accesses`, `communicates_with`) pass `cpsEsClient` (`projectRouting: 'space'`); entity-index maintainers do not. (@uri-weisman, PR #269578, `x-pack/platform/plugins/shared/entity_store/server/tasks/entity_maintainers/execution.ts`)
- **Comments explain _why_, not _what_ — do not over-comment obvious decisions** — Long JSDoc blocks and inline comments that restate what the code already expresses (e.g. explaining that `user.name` is the identity field when the constant is already named `HOST_SCOPED_USER_EUID_FIELD`) get flagged as verbosity. Keep comments for non-obvious constraints and rejected alternatives; "future work" comments must link a ticket. (@romulets, [PR #281804](https://github.com/elastic/kibana/pull/281804), seen 2x on `entity_store/common/domain/euid/esql.ts`; @maxcold, PR #272948, `administers/configs.ts`)
- **When a union-based raw_identifiers EUID resolution is deliberate, say so in code** — Reviewers default to assuming a ranked pick (email → id → name) matching extraction's EUID ranking, and will flag unioning as producing dangling id-form EUIDs. State explicitly that unioning is intentional because you cannot know which field generated the entity's EUID, and that `validateTargetIds` drops non-matching EUIDs. (@github-actions (Claude Reviewer), [PR #274261](https://github.com/elastic/kibana/pull/274261), `maintainers/supervises/configs.ts`)
- **Scout fixtures: export only what the specs consume** — A 500-line `helpers.ts` largely copied from `entity_store/test/scout/api/fixtures/helpers.ts`, with functions no spec imports, was flagged as dead code plus a parallel copy to maintain. Trim to consumed symbols and lift genuinely shared pieces into `@kbn/scout-security`. Same applies to `ENTITY_STORE_ROUTES`: unused keys (`FORCE_CCS_EXTRACT_TO_UPDATES`, `CHECK_PRIVILEGES`, `CRUD_*`, `RESOLUTION_*`) had incorrect URL paths that would 404 if anyone used them. (@github-actions (Claude Reviewer), [PR #274261](https://github.com/elastic/kibana/pull/274261), `test/scout/entity_analytics/api/fixtures/maintainers/helpers.ts`, `.../constants.ts`)
- **One registry map with typed `task` / `lifecycle` sub-properties — not two separate maps** — (@chennn1990, PR #262317, `entity_maintainers_registry.ts`)
- **Fail fast on a missing namespace; do not fall back to `""`** — Keep the `currentStatus?.namespace || currentStatus?.metadata?.namespace` lookup chain and let it surface early. (@chennn1990, PR #262317, `execution.ts`)
- **`autoStart` defaults to `true`; `autoStart: false` is the exceptional, test-only path** — Renamed from a no-default `enabled` flag; `POST /entity_maintainers/init` body is `{ autoStart?: boolean }`. (@chennn1990, PR #262317, `routes/apis/entity_maintainers/utils/validator.ts`)
- **`extends` an existing interface instead of re-declaring its fields** — (@chennn1990, PR #262317, `entity_maintainers_client.ts`)
- **Deduplicate lookback-filter construction into the shared `buildLookbackFilter`** — Used in both `run_relationship_maintainer.ts` and `build_actor_discovery_query.ts`. (@maxcold, PR #272948)
- **Log a run/skip decision once, at the point of decision — not again in the outer loop** — (@alexreal1314, PR #269578, `engine/run_relationship_maintainer.ts`)
- **Keep synchronous-run API execution separate from Task Manager task code** — `executeMaintainerRun` / `runSync` live in `execution.ts`; the API route (`POST /entity_maintainers/run/{id}?sync=true`) calls it directly through `EntityMaintainersClient.runSync` rather than through the scheduled Task Manager task. `runSync` still checks the maintainer's registered minimum license (`canRunMaintainerWithLicense`, `entity_maintainers_client.ts:204-212`) and skips the run when it is invalid, keeping sync behavior aligned with task execution — keep that check. (@chennn1990, PR #262317, `x-pack/platform/plugins/shared/entity_store/server/tasks/entity_maintainers/index.ts`)
- **Use `esClient.helpers.bulk` for high-fan-out metadata bulk writes** — Raw `esClient.bulk` materializes the entire operations array; the helper chunks by `flushBytes`, streams via a generator, retries 429s, and supports an `onDrop` callback for drop-reason logging. (@opauloh, PR #271806, `infra/elasticsearch/entity_metadata.ts`)
- **Aggregate bulk drop errors instead of logging per document** — Use `infra/elasticsearch/bulk_drop_aggregator.ts` / `formatBulkDropSummary` so a large failed bulk produces one summary, not thousands of log lines. ([PR #276316](https://github.com/elastic/kibana/pull/276316))
- **Keep maintainer relationship writes going through entity-store exported write functions** — `bulkUpdateEntity`, `EntityMetadataClient`, and `RelationshipsClient.clearRelationshipIds` (Painless `update_by_query` in `infra/elasticsearch/entity_relationships.ts`). A reviewer argued the reset code is a domain flow rather than infra; the author kept it to match the existing pattern and the reviewer accepted ("Up to you"). (@chennn1990, PR #292504 — preference, not a hard rule)
- **Do not expose index-name helpers for the metadata datastream** — Metadata lives in a datastream/write alias, not a concrete index; dead `getEntityMetadataIndexName` helpers and "index" naming mislead callers. (@romulets, PR #271806, `entity_store/common/domain/entity_index.ts`)
- **Do not leak internal implementation details into customer-facing copy** — Fold internal artifacts (e.g. "entity relationship history") under existing customer concepts ("Security Entity store records"). (@romulets, PR #271806, `public/entity_analytics/.../clear_entity_data_button.tsx`)
- **IDP user EUIDs are namespace-suffixed; host targets are namespace-less** — User actors use `CONCAT("user:", <value>, "@<namespace>")` (e.g. `user:<id>@okta`, `@entra_id`, `@sailpoint_identity_sc`); host targets use `host:<name>`. Null-safe `MV_APPEND` guards are required because `MV_APPEND(null, x)` returns null. ([PR #274261](https://github.com/elastic/kibana/pull/274261), `maintainers/supervises/configs.ts`, `maintainers/administers/configs.ts`)
- **New entity-index IDP sources for `supervises` go through the shared `buildSupervisesConfig` / `SUPERVISES_SOURCES` list, not a copied config** — Okta, Entra ID and SailPoint share one builder (`supervises/configs.ts:39`); only Workday, a log-index source with reset semantics, is a hand-written override. (PR #295263)
  Adding a row to `SUPERVISES_SOURCES` is not a must: use it only when the new source's config is very similar to the shared builder.
- **Give a new maintainer or source a Scout spec named for what it tests when it needs a distinct suite** — `scout_max_one_describe` limits a file to one root `describe`; it does not limit how many sources or cases a suite covers. Add the source to an existing suite when the setup is shared (as `accesses` / `communicates_with` do), and add a new spec file only when the source needs its own setup, so a shared parameterized suite never has a second caller. Spec files are named for what they test (`administers_maintainer.spec.ts`, `supervises_okta_maintainer.spec.ts`, `entra_id_owns_maintainer.spec.ts`, `workday_supervises_maintainer.spec.ts`, `sailpoint_supervises_maintainer.spec.ts`), and the category lives in the describe title where it shows up in test output. Category-named files with single-caller `register*Suite` factories were removed for advertising reuse the lint rule forbids — do not reintroduce them, and do not add "add a new entry here" comments (flagged as actively misleading). `accesses` / `communicates_with` integrations are covered by `scout_cps_local/.../maintainers/{accesses,communicates_with}.spec.ts` plus config snapshots, not per-integration specs. (@MadameSheema, [PR #274261](https://github.com/elastic/kibana/pull/274261); renamed in [PR #292504](https://github.com/elastic/kibana/pull/292504))
- **`customActor.fields` must not include high-cardinality identifiers that vary per host** — For entity-index sources (`administers`, `owns`/Okta, `supervises` IDP sources) the actor is discovered by `entity.id`; for log-index maintainers (`communicates_with`, `accesses`) by identity fields. Including `user.id` in `customActor.fields` for `system_auth` was the root cause of the bucket-explosion bug fixed in [PR #278471](https://github.com/elastic/kibana/pull/278471) — `user.id` varies across hosts, so the same username appeared with dozens of distinct IDs.
- **Entity-store Task Manager task conventions (from the latest-index mapping migration task, PR #305241, @darnautov)** — set an explicit `description` and `cost` (e.g. `TaskCost.Normal`) "so it reads as a deliberate choice rather than the default"; classify retry vs unrecoverable by status code / error type, never by message text ("a wording change silently turns this into a retry"); throw `throwUnrecoverableError` when all failures are permanent (400/403) instead of burning all retries with error logs on every Kibana start; import `RunContext` from `@kbn/task-manager-plugin/server`, not a `/server/task` subpath. These apply to `entity_store/server/tasks/**`; maintainer registration still does not expose `cost` (see Performance).
  Not every ES 403 is a permission failure (e.g. `cluster_block_exception` on a read-only index, flagged by the Libra reviewer); such errors could be retryable in entity-store tasks.
- **Task execution context names: maintainers inherit theirs from the wrapper; standalone tasks set their own** — Execution context is propagated through Entity Analytics / entity_store tasks (`coreStart.executionContext.withContext`; PRs #291946, #292022). The scheduled maintainer wrapper (`entity_store/server/tasks/entity_maintainers/index.ts`) derives `entity_analytics:entity_maintainers_task:<registered maintainer id>` through `buildEaExecutionContext(EA_EXECUTION_CONTEXT_NAMES.ENTITY_MAINTAINERS_TASK, taskInstance.id, id)` ([PR #305212](https://github.com/elastic/kibana/pull/305212)), so ES slow-log / APM attribution names the maintainer; a maintainer config does not set it. Standalone entity-store tasks (extract, history snapshot, status report) supply their own name from `EA_EXECUTION_CONTEXT_NAMES` (`tasks/execution_context.ts`), and the entity-type suffix belongs to the extraction tasks only.

## Security considerations

- **Namespace validation (`assertValidNamespace`) is a correctness guard, not a security boundary** — it rejects malformed namespaces before index-pattern interpolation (`engine/validate_namespace.ts`, enforced at the top of `runRelationshipMaintainer`, `engine/run_relationship_maintainer.ts:453`), but is not relied upon as an index-pattern/injection defense.
- **Maintainer lifecycle routes are internal and privilege-gated** — All `/internal/security/entity_store/entity_maintainers` routes (`GET /`, `POST /init`, `PUT /start/{id}`, `PUT /stop/{id}`, `POST /run/{id}?sync=`) are versioned `API_VERSIONS.internal.v2`, declare `security.authz: DEFAULT_ENTITY_STORE_PERMISSIONS`, are wrapped by `wrapMiddlewares`, and validate `id` against the registry (`routes/apis/entity_maintainers/*.ts`, `utils/validator.ts`). Privileges on the lifecycle routes were tightened in [PR #281454](https://github.com/elastic/kibana/pull/281454), and privilege checks before installing/initializing Entity Store V2 were added in [PR #280251](https://github.com/elastic/kibana/pull/280251). A new mutating maintainer route must keep both gates: the route-level `DEFAULT_ENTITY_STORE_PERMISSIONS` (`requiredPrivileges: ['securitySolution']`) and `enforceEntityStorePrivileges(assetManagerClient, req, res)` (`routes/apis/utils/check_entity_store_privileges.ts`), which checks the Kibana, Elasticsearch cluster and index privileges returned by `AssetManagerClient.getPrivileges`. `init`, `start`, `stop` and `run` apply the second gate (`run` before choosing sync or async); `GET /` does not.
  PR #281454 made sure unprivileged users cannot run maintainers. A sync run (`?sync=true`) is covered by the same two gates, because `run` enforces them before branching to `runSync`.
- **Reads run as the task's scoped user; metadata writes run as the internal user** — `execution.ts` builds `esClient` from `asScoped(request).asCurrentUser` (and `cpsEsClient` with `projectRouting: 'space'`), while `EntityMetadataClient` is built on `asInternalUser` (also in the sync path, `entity_maintainers_client.ts:330-376`). Moving any source read onto the internal-user client would bypass the scoped user's index privileges.
  The `asInternalUser` metadata client is intentional.
- **Account-exclusion filters differ per source — preserve the ones that exist** — Non-human and machine-to-machine identities are a data-quality concern (not security-enforced), and each source filters them differently (`accesses` and `communicates_with` use the same clauses unless noted). Elastic Defend: `process.Ext.session_info.logon_type IN ("RemoteInteractive", "Interactive", "Network")`, so network logons are included, with no account-name exclusion. System Security: `winlog.logon.type IN ("Interactive", "RemoteInteractive", "CachedInteractive")` (network logons excluded) plus `NOT user.name IN ("SYSTEM", "LOCAL SERVICE", "NETWORK SERVICE", "ANONYMOUS LOGON")`, with no machine-account (`$`) filter. CrowdStrike FDR: excludes `LogonType` 3, 4, 5 and 8 (NULL tolerated), the same account-name list, and names ending in `$`. System Auth: only successful `ssh_login` events, with no account-name list. AWS CloudTrail: `accesses` is limited to successful `StartSession` / `SendSSHPublicKey`, and `communicates_with` applies a human IAM identity-type filter. Jamf Pro: `UserLogin` events with `user.name` present. (PR #255418, @niros1; per-source clauses from `accesses/configs.ts` and `communicates_with/configs.ts`)
  Machine/service account exclusion is at each integration's discretion, not a hard requirement.
- **Scout maintainer install routes require `securitySolution` + entity-analytics privileges that lower test roles lack** — Tests calling the entity-maintainers init/run routes must use `asInteractiveUser('admin')`; omitting the reason in test comments hides why elevated privileges are required. The reviewer asked for an inline comment; the author explained in the PR thread but did not add one. (@MadameSheema, [PR #274261](https://github.com/elastic/kibana/pull/274261))
- **License is checked per run via `licensing.getLicense()` before any ES work** — `DEFAULT_ENTITY_MAINTAINER_MIN_LICENSE = 'basic'` unless a maintainer overrides it (`canRunMaintainerWithLicense`, `x-pack/platform/plugins/shared/entity_store/server/tasks/entity_maintainers/execution.ts:56`). A maintainer requiring a higher tier must declare it at registration; the framework will not infer it.
  All maintainers should require similar privileges.

## Performance constraints

- **Each query should run in a few seconds, otherwise it's not scalable when running multiple integrations for each maintainer.** This is the governing budget: every Step 1 composite-aggregation page and every Step 2 ES|QL query is one of many issued per run, across every integration a maintainer is configured with. A query that takes tens of seconds does not just slow one run — it multiplies across integrations and makes the maintainer unschedulable. Integrations per maintainer have grown (accesses 5, communicates_with 6, supervises 4), so this budget compounds.
- **Step 1 pages actors via composite aggregation at `COMPOSITE_PAGE_SIZE = 3500` per page, capped at `MAX_ITERATIONS = 1000` pages** (`engine/constants.ts`, `engine/build_actor_discovery_query.ts`); each page becomes an OR-of-`terms` DSL filter (`buildActorPageFilter`) narrowing the Step 2 ES|QL query. Adding actor fields or relaxing actor-presence filters widens the candidate set and increases ES|QL load per page. `COMPOSITE_PAGE_SIZE` is tuned against source **log** volume (typically higher than entity count), not a fixed entity-count ceiling — large customers reach on the order of ~1M entities, usually fewer.
- **An ES|QL or write failure for one integration does NOT stop the entire maintainer run** — `runIntegration` catches throws from its four wrapped stages (`fetch-actors | fetch-targets | entity-write | metadata-write`) and returns `outcome: 'error'` with accumulated counters and a failing-stage label. The pre-run reset runs before that wrapper: a failed `preRunReset` (e.g. Workday's relationship clear) returns `outcome: 'error'` with no `failedStage`, so a missing stage does not rule out a reset failure. The outer loop in `runRelationshipMaintainer` (`engine/run_relationship_maintainer.ts:549`) continues to the next integration. Per-integration isolation is fully in effect. An abort signal between integrations does stop the run (remaining integrations are skipped).
- **Full-scan maintainers over 160M+ docs require explicit `timeout: '1h'` (or similar) — not the 5m TM default** — A timed-out first run leaves the watermark unchanged, causing repeated full re-scans of the same window on every daily schedule. (@darnautov, [PR #274261](https://github.com/elastic/kibana/pull/274261))
- **Incremental raw-identifiers maintainers advance `lastProcessedTimestamp` only on successful completion** — Watermark-based incremental processing via `entity.lifecycle.last_seen > lastProcessedTimestamp` (`engine/build_raw_identifiers_query.ts`, `administers/index.ts`) avoids re-processing the entire entity index each run; a failed or timed-out run must not advance the watermark.
- **The watermark is per-maintainer, not per-integration** — When one maintainer runs multiple integration configs (`supervises` now runs Okta, Entra ID, SailPoint and Workday), they share a single `lastProcessedTimestamp`. If one integration's scan is slow, the watermark does not advance until all complete. (@maxcold, PR #272948, raised as a future scaling concern)
  Workday does receive the shared `supervises` `lastProcessedTimestamp`, but only as a first-run vs incremental switch: when it is present, the ES|QL adds a fixed `event.ingested >= NOW() - 30 day` window (and the DSL step a `now-30d` range) rather than `> lastProcessedTimestamp`, so a delayed or skipped run does not open a gap — as long as the last eligible ingestion is still inside that 30-day window. Once it ages out, both the `hasRepopulatableSource` probe (built from the same Step 1 filters) and the scan miss it, and `preRunReset` skips (outcome `empty`) instead of rebuilding from older records (`supervises/configs.ts:144-146,233-237,299-301`, `engine/pre_run_reset.ts`). The Okta / Entra ID / SailPoint sources use the watermark as a `last_seen > lastProcessedTimestamp` bound.
- **Workday `supervises` collapses to the latest snapshot (`LAST`) after the actor-page filter** — The page filter (`Manager_Email IN (…) OR Manager_ID IN (…)`) is applied at the source, before the `LAST(managerKey, event.ingested) BY targetEntityId` stage, so a worker who moved between managers on different composite pages can be attributed to the old manager on that manager's page until the old snapshot leaves the `event.ingested` window (`resetRelationshipsBeforeRun` bounds the staleness to that window). The author accepted this as unlikely (all reports of a manager usually fit in one page). The ~7,000 figure is not a reports-per-manager limit: `WORKDAY_ESQL_LIMIT` is `COMPOSITE_PAGE_SIZE` (3,500) × 2 manager identifiers and caps manager *result rows per page* (`supervises/configs.ts:137-138`). (@alexreal1314 reply on PR #292504; raised by an automated reviewer)
- **Metadata bulk append uses `refresh: false` by default** — Background-written append-only datastream records do not require synchronous refresh; adding refresh waits would multiply write latency across high-fan-out actor→target pairs. (@romulets, PR #271806)
- **High-fan-out metadata writes should use `esClient.helpers.bulk` with `flushBytes` chunking** — Prevents exceeding `http.max_content_length` on large maintainer runs. (@opauloh, PR #271806)
- **`disableLookbackWindow` is fully wired into both the composite-agg and ES|QL query builders** (as of follow-up PR #272948) — raw-identifiers maintainers gate out the lookback-window time filter in the actual queries, not only in the `Maintainer.lookback_window` metadata field.
- **`matchExistingTargetIds` validates targets with a `terms` query on `entity.id` against the latest alias in chunks of 5,000** (`engine/update_entities.ts:87`) — the earlier single unbounded `search` that risked `max_terms_count` (raised by @github-actions (Claude Reviewer) on PR #272948) is now chunked. Keep the chunking when touching validation; pruned targets are reported as `targetIdsNotInStore` (PR #288089).
- **Known framework-level gaps raised by @darnautov (PR #272948) and not yet closed:** maintainer configs do not expose Task Manager `cost` / `priority`, so a daily composite-agg + bulk-write task registers as `TaskCost.Normal` when it likely warrants `TaskCost.ExtraLarge`; there is no `stateSchemaByVersion` on task registration even though non-empty state persists between runs; and `runEntityMaintainerTask` always returns normally, so `throwUnrecoverableError` / `throwRetryableError` are never reached and transient ES failures do not trigger TM retries. (Contrast: the entity-store latest-index mapping migration task in PR #305241 was required to set `cost` explicitly and to classify unrecoverable errors.)
  These gaps are not tracked anywhere, but reviewers should check them on new maintainers.

## Historical catches

- [PR #266159](https://github.com/elastic/kibana/pull/266159) — Reviewer caught that an abort-signal error during `esClient.search` fell through to the generic error handler and crashed the maintainer — A generic reviewer would not know abort must be matched _before_ `isIndexNotFound` and treated as a clean exit, not a failure.
- [PR #266159](https://github.com/elastic/kibana/pull/266159) — Reviewer caught that `break`-on-ES|QL-failure wrote already-collected records while returning success metrics — A generic reviewer would not realize the function reports success with no signal that the write was partial.
- [PR #262345](https://github.com/elastic/kibana/pull/262345) — Reviewer caught that an empty UPN produced an invalid `"user:@entra_id"` target ID because the empty-field guard covered only `Device`, not `User` — A generic reviewer would not know each entity-type branch needs its own empty-field guard in the ES|QL WHERE clause.
- [PR #262317](https://github.com/elastic/kibana/pull/262317) — Reviewer held firm that the maintainer registry must throw on an unknown ID rather than return `undefined` — A generic reviewer would not see why distinguishing "not registered" from "not yet initialised" matters for this lifecycle.
- [PR #281804](https://github.com/elastic/kibana/pull/281804) — @romulets caught that `COALESCE(user.name, user.email)` in the host-scoped user EUID would emit `user:alice@corp.com@h1@local` for documents extraction classifies as IDP users, referencing an EUID that does not exist and 404-ing on write — A generic reviewer would not know that extraction's classification rules decide which identifier field is legal in which EUID form, so the maintainer's gate and its `CONCAT` expression must diverge deliberately.
