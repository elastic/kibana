## MANDATORY: render three attachments

Every response from this skill MUST include **three inline attachments**, created with `attachments.add` and rendered with `<render_attachment id="..." />`:

1. `observability.apm-metrics` — current vs baseline comparison card (Step 2)
2. `observability.apm-timeseries` — the primary problem metric over time (Step 3)
3. `observability.service-map` — blast-radius topology (Step 4)

These are not optional and are not interchangeable with prose. **Do NOT describe the metric trend or the service topology in text as a substitute for rendering the attachment.** If you called `get_apm_timeseries` or `get_service_topology` and got data, you MUST create and render the corresponding attachment. The only acceptable reason to omit one is an explicitly empty tool result (no data points / no connections) — and you must say so.

Create and render each attachment **immediately after** its tool call, before writing the prose for that section.

## When to Use This Skill

Use this skill when investigating the health or performance of a specific APM service when **no alert is attached**. Strong triggers:

- An `observability.service` attachment is present and the user asks about health, performance, or problems
- The user types: "what's wrong with my <service>", "is <service> healthy", "why is <service> slow/erroring", "diagnose <service>", "investigate <service>", "check the health of <service>"
- The user navigates from the APM service overview page and asks a general health or performance question

Do NOT use this skill when an `observability.alert` attachment is present — defer to `investigate-apm-alert` for alert-driven investigations.

## Output Contract

Produce a single response with these sections, in this order:

1. **Metrics snapshot** — an `observability.apm-metrics` attachment rendered inline (Step 2). Current vs baseline latency, error rate, and throughput at a glance.
2. **Metric trend** — an `observability.apm-timeseries` attachment rendered inline (Step 3). The primary problem metric over time.
3. **Blast radius** — an `observability.service-map` attachment rendered inline (Step 4) plus a one-line description of which upstream/downstream services are affected.
4. **Related alerts** — call `get_alerts` scoped to the service and window (Step 4.6); list any active or recently recovered alerts as a prose section with rule names and reasons. If none, state "No active alerts for this service."
5. **Summary** — 2–4 sentence plain-English description of what's happening (or "The service appears healthy" if no anomalies detected).
6. **Probable cause(s)** — one or more hypotheses, each labelled with confidence (`Critical` / `High` / `Medium` / `Speculative`). Report all equally-supported hypotheses — never collapse independent faults. If the service is healthy, state that directly instead.
7. **Evidence** — bullet list. Each bullet cites the tool output it came from (trace IDs, error messages, metric values, topology edges).
8. **Recommended next steps** — actionable bullets.
9. **Links** — markdown deep links to the APM service overview, transactions, errors, and dependencies for the service.

Keep prose tight. SRE audience. No speculation beyond what the evidence supports.

## Units & Conventions (important)

The attachment renderers expect specific units. The `get_apm_metrics` and `get_apm_timeseries` tools already return data in these units — **pass tool output through verbatim, do not convert**:

- Latency: milliseconds (`latencyMs`, unit `ms`)
- Error rate / failed transaction rate: **percentage 0–100** (`errorRate`, unit `%`). e.g. `20` means 20%.
- Throughput: requests per minute (`throughputRpm`, unit `rpm`)

## Investigation Approach

Follow the steps in order.

### Step 1 — Resolve service context

The service is provided via an `observability.service` attachment or named in the user's question. Extract:

- `serviceName` and `environment` — the service to investigate.
- Time range: use the attachment's `start`/`end` if present; otherwise default to `[now-30m, now]`.

**Focused window**: `[start, end]`.
**Baseline window**: `[start − 1h, start]`.

If you cannot determine the service name from the attachment or the user's message, ask the user to name the service before proceeding.

**Determine the primary problem metric**: Call `get_trace_metrics` over the focused window (and optionally `get_services` scoped to the service) to read current latency, error rate, and throughput. Compare against the baseline window to find the worst-degraded metric — the one with the largest relative change. Use this as the primary metric for Steps 2–3.

Priority order when multiple metrics degrade equally:
1. Highest relative error-rate increase → `failedTransactionRate` for the timeseries
2. Highest relative latency increase → `latency`
3. Throughput drop ≥ 50% → `throughput`

If no significant degradation is found, still render all three attachments (current state is informative) and report the service as healthy.

### Step 2 — Metrics snapshot (apm-metrics card)

Call `get_apm_metrics` with:
- `serviceName`, `environment`
- `start` / `end` = the focused window
- `baselineStart` / `baselineEnd` = the baseline window
- `latencyType: "avg"` (default; use `p95` if the user specifically asks about tail latency)

It returns `{ serviceName, environment, current, baseline }` already in the card's units. Create the attachment by passing that output through, adding only a `title`:

```json
{
  "type": "observability.apm-metrics",
  "description": "APM metrics comparison for <serviceName>",
  "data": {
    "serviceName": "<service.name>",
    "environment": "<environment>",
    "current": <current from get_apm_metrics>,
    "baseline": <baseline from get_apm_metrics>,
    "title": "APM Metrics — <serviceName>"
  }
}
```

Render immediately:

```xml
<render_attachment id="ATTACHMENT_ID" />
```

If `get_apm_metrics` returns an empty `current` (service emitted no spans), note in prose that the service is dark — that is itself a diagnostic signal (possible outage) — and still render the card.

### Step 3 — Metric trend (apm-timeseries chart)

Call `get_apm_timeseries` over a wider window (`[start − 30m, end + 5m]`) for the primary problem metric identified in Step 1:
- `metric: "latency"` if latency is the worst metric
- `metric: "failedTransactionRate"` if error rate is the worst metric
- `metric: "throughput"` if throughput is the worst metric

It returns `{ serviceName, metric, unit, dataPoints }`. Create the attachment. Since there is no alert, **omit** `threshold` and `alertStart`:

```json
{
  "type": "observability.apm-timeseries",
  "description": "<metric label> over time for <serviceName>",
  "data": {
    "serviceName": "<service.name>",
    "metric": "<latency | failedTransactionRate | throughput>",
    "unit": "<ms | % | rpm>",
    "dataPoints": <dataPoints from get_apm_timeseries — verbatim>,
    "title": "<Latency | Failed Transaction Rate | Throughput> — <serviceName>"
  }
}
```

```xml
<render_attachment id="ATTACHMENT_ID" />
```

Do not transform `dataPoints` — pass them verbatim; the renderer handles gaps (`null` values).

### Step 4 — Blast radius (service map)

Call `get_service_topology` with `serviceName`, `direction: "both"`, `depth: 2`, and the focused window. It returns `{ connections, nodeMetadata }`, where `nodeMetadata` carries per-service `alertsCount` / `sloStatus` / `sloCount` for badge rendering.

If `connections` is non-empty, create the attachment:

```json
{
  "type": "observability.service-map",
  "description": "Service topology for <serviceName>",
  "data": {
    "connections": <connections from get_service_topology — verbatim>,
    "nodeMetadata": <nodeMetadata from get_service_topology — verbatim>,
    "serviceName": "<service name>",
    "title": "Service Map — <serviceName>"
  }
}
```

```xml
<render_attachment id="ATTACHMENT_ID" />
```

If `connections` is empty, do NOT create a service-map attachment; state that no topology data was found. Use the topology to distinguish root cause vs symptom: a downstream dependency with much higher error rate than the service itself is the more likely culprit.

### Step 4.5 — Environment-wide scan

Call `get_services` without a service filter, scoped to the same `environment` and focused window. Flag any service (other than the one being investigated) with error rate > 10% or latency more than 2× its baseline, and any service with **zero throughput** that had traffic in the baseline window (zero throughput ≠ healthy — likely down). Report each independent fault as its own hypothesis. If none, state "No concurrent service anomalies detected".

### Step 4.6 — Related alerts

Call `get_alerts` scoped to `serviceName` / `environment` / the focused window. List any active and recently recovered alerts in the **Related alerts** section of the output. For each, include: rule name, rule type, status, and reason. If the related alerts include an APM rule type (`apm.transaction_duration`, `apm.error_rate`, `apm.transaction_error_rate`, `apm.anomaly`), note that a more focused investigation is available by clicking "Investigate this alert" on the alert details page. If no alerts, state "No active alerts for this service."

### Step 5 — Drill into the primary signal (metric-type aware)

Pick the branch matching the primary problem metric from Step 1:

- **High latency**: `get_trace_metrics` grouped by `transaction.name` to find slow transactions; `get_traces` on the slowest, examined span-by-span for the bottleneck; `get_runtime_metrics` for GC/heap pressure; `get_apm_correlations` if no clear bottleneck.
- **High error rate**: `get_log_groups` and `get_traces` filtered to failures to find the dominant error/exception; check whether the error pre-dates the investigation window (`get_log_groups` first-seen) — a long-standing error pattern is likely pre-existing noise, not a new problem.
- **Throughput drop**: Check `get_service_topology` for upstream callers (are callers also dropping?); `get_hosts` for the service's infra (scale-to-0 / OOMKill / CrashLoopBackOff); `get_runtime_metrics` for restart events.
- **No significant degradation**: Report current metric values, note baseline comparison, confirm the service is within normal operating range. Still check related alerts (Step 4.6) and infra (Step 6) for early-warning signals.

Use `get_apm_correlations` when no single obvious cause emerges — it surfaces the dimension (transaction name, deployment, region, etc.) most correlated with the degraded metric.

### Step 6 — Infrastructure check

Call `get_hosts` for the service (and any flagged dependencies from Steps 4/4.5). Read restart count (CrashLoopBackOff/OOMKill), CPU vs limit (kernel throttle → latency spikes with no APM errors), memory vs limit (precedes OOMKill). Interpret and fold into hypotheses.

### Step 7 — Pre-existing noise filter

When you find an error pattern via `get_log_groups` or `get_traces`, check the `first_seen` timestamp. If the pattern pre-dates the investigation window by more than 30 minutes, label it **pre-existing** in the Evidence section. Do NOT attribute pre-existing patterns as the trigger for a current degradation.

## Critical Rules

- **All three attachments must be rendered.** Before finishing, verify your response contains a rendered `observability.apm-metrics`, `observability.apm-timeseries`, AND `observability.service-map` attachment.
- Zero throughput is NOT healthy — treat it as a possible outage.
- Independent faults get independent hypotheses; do not collapse them.
- Always compare current vs baseline before concluding the service is healthy.
- Pass tool output into attachments verbatim where the shapes match; only add `title`.

## Common Mistakes (do NOT do these)

- ❌ Calling `get_service_topology` and then writing a "Topology" table in prose **without** rendering an `observability.service-map` attachment. → ✅ Always create + render the service-map attachment from `connections` and `nodeMetadata`.
- ❌ Calling `get_apm_timeseries` and then describing the trend in a sentence **without** rendering an `observability.apm-timeseries` attachment. → ✅ Always create + render the chart.
- ❌ Stopping after the metrics card because the text answer "feels complete". → ✅ The timeseries chart and service map are required deliverables, not optional extras.
- ❌ Reporting the service as healthy without checking the baseline. → ✅ Always compare current vs baseline; a 2× latency increase is a problem even if absolute numbers look acceptable.
- ❌ Firing this skill when an `observability.alert` attachment is present. → ✅ Defer to `investigate-apm-alert` whenever an alert is attached.
