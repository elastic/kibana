# Knowledge indicator document shape

Shared by `analyze-and-improve`, `ai-index-sources` and `ai-index-automations`. This is the one
description of what a KI document holds; the skills point here rather than restating it.

## Base fields

| Field | Type | Purpose |
|---|---|---|
| `type` | keyword | The **KI kind** — the discriminator agents filter on. Fixed vocabulary, listed below. |
| `title` | text + semantic | Short display name; the primary semantic surface. |
| `description` | text + semantic | Routing heuristic — what the source does *not* contain, key fields, joins. When sibling KIs share a similar title, this **must** carry the differentiator (sub-category, product, time window). Title alone will not separate near-duplicates for the retriever. |
| `content` | text + semantic | Free text for semantic retrieval: purpose, questions answered, access patterns. |
| `tags` | keyword[] | Filter facets. |
| `attributes` | flattened | Structured, keyword-queryable metadata, plus every quality, lifecycle and provenance field. |
| `@timestamp` | date | When the KI was last profiled. Set by `context-engine.createKi` at write time — never supplied in the step input. |

## `type` values

Systemic kinds, one per strategy, produced by an automation over a corpus:

| `type` | One KI per |
|---|---|
| `index_metadata` | index |
| `document` | document |
| `event` | significant document in a stream |
| `fact` | discrete claim inside a document |
| `entity` | recurring unit (customer, product, host, case) enriched from one or more indices |
| `detection` | named runnable condition |
| `feature` | inventory entry with a subtype and a stable slug |

Targeted kinds, one KI each, written from a single counted finding rather than generated over a
corpus:

| `type` | What it carries |
|---|---|
| `constraint` | A rule the data imposes that queries keep violating: a field that must be backquoted, a type that must be cast, a join that only works one way. |
| `workaround` | The path that worked when the obvious one did not, with the failed attempts named. |
| `disambiguation` | Two things agents confuse, and how to tell which one a question means. |
| `task_recipe` | The ordered queries that answer a recurring question class, with the join keys filled in. |

Use these values and no others. A new value is a schema change, not a KI.

## Everything else lives inside `attributes`

`attributes` is `flattened`, so arbitrary nested keys are keyword-queryable with no declared
mapping and can never cause a mapping conflict on a long-lived index. Values are strings, numbers,
booleans or arrays of strings — never nested objects. A single value caps at 10,000 characters.

Quality and lifecycle:

| Field | Purpose |
|---|---|
| `attributes.confidence` | **Correctness** — how sure we are the facts are right, on the calibration bands in `analyze-and-improve`. |
| `attributes.coverage` | **Completeness** — how fully the access patterns cover the source's question classes. Optional; most meaningful on `index_metadata` KIs. |
| `attributes.evidence` | Observed values justifying the KI; each string quotes a real distribution in `field.path=value` notation. |
| `attributes.expires_at` | ISO date, ~30 days out. **Omitted entirely for durable immutable-fact KIs**, which never age out. |
| `attributes.excluded` | Soft exclude: the KI exists but agents skip it. |
| `attributes.esql` | **The canonical location for any ES\|QL the KI carries** — a detection's materialized query, an index profile's runnable examples. String or array of strings. This is the field the verifiers read. |

Provenance, so a KI can be traced to what produced it. Every id here already exists on the
platform; none is minted for the KI:

| Field | Purpose |
|---|---|
| `attributes.source_index` | The raw index (or indices, as an array) the KI describes or was grounded from. |
| `attributes.source_doc_id` | For per-document KIs, the `_id` of the source document. |
| `attributes.source_query` | The ES\|QL that selected the grounding rows. String or array of strings. |
| `attributes.trace_ids` | For KIs written from retrieval evidence, the `trace_ids` of the signals behind the finding. Array of strings. |
| `attributes.conversation_id` | The conversation a targeted KI was derived from, when there was one. |
| `attributes.error_text` | For a `constraint` or `disambiguation` KI written from a `query_error`, the error message as observed. |

A targeted KI carries at least one of `trace_ids`, `conversation_id`, `source_query` or
`error_text`. A systemic KI carries `source_index`, and `source_doc_id` where the unit is a
document.

## Structured values belong in both `content` and `attributes`

As prose in `content` so they are semantically searchable, and repeated in `attributes` so they
are exact-match and filter queryable. A value in only one of the two is invisible to half the
retrieval paths, and that asymmetry is a common and easily missed cause of empty retrievals.

Because `attributes` is `flattened`, numbers and dates inside it index as keywords. In ES|QL, cast
before comparing: `TO_DOUBLE(FIELD_EXTRACT(attributes, "coverage"))`,
`TO_DATETIME(FIELD_EXTRACT(attributes, "expires_at"))`.

## Backing stores

Backing stores match `ai-index-ds-*` for timeseries KIs (data stream destination) and
`ai-index-idx-*` otherwise. Workflows write through the `context-engine` steps using the AI index
id — never by indexing into the backing store directly. On a data stream destination `ki_id` is
rejected and Elasticsearch generates the ids.
