## When to Use This Skill

Load this skill to **read, draft or change the workflow automations attached to a Context Engine AI
index** — the Kibana Workflows that turn its sources into knowledge indicators.

Reach for it when an index needs an automation it does not have, when a proposal names a step that
has to change, or when you need to know what an existing automation actually does before saying
anything about it.

Deciding what the index should contain and whether a change is warranted is `analyze-and-improve`.
Choosing the data an automation draws on is `ai-index-sources`.

## Read the automation before you say anything about it

`platform.workflows.get_workflow` returns a workflow's definition. Read it for a specific step,
because a useful change names one: what it samples and how much, what it asks the model for, how
many indicators it can emit, and what it writes into which fields.

A pipeline's *shape* often bounds what it could ever produce, however well its prompts are worded —
an automation that samples twenty documents cannot describe a corpus of ten thousand, no matter how
the prompt is phrased. Look for that before looking at wording.

Misquoting what an automation does is the most expensive mistake available here: every claim built
on it inherits the error, and a reviewer who catches one stops trusting the rest. When several
automations write to the same index, attribute an indicator to one by reading the definitions and
seeing which writes to that destination and id pattern. If that does not settle it, say attribution
was not established rather than guessing.

For the semantics of a step type, Liquid templating, trigger schemas or `on-failure` handling, load
`workflow-authoring` rather than inferring them from the YAML.

## What every automation must do

Whatever the strategy, a generated workflow has to:

- **Read its source** through `elasticsearch.esql.query` or a connector step, applying the agreed
  corpus filter.
- **Ground the model on real data** before asking it for anything — a sample of documents, and for
  detections a distribution aggregation whose observed counts every threshold must quote. Sample
  with `function_score` + `random_score` so repeated runs see different records rather than always
  the first-ingested ones.
- **Use `ai.prompt` rather than `ai.agent`** unless tool use is genuinely required.
- **Write through the `context-engine` steps**, never a raw `elasticsearch.index`, and gate every
  write on `context-engine.verifyKi` so an indicator whose ES|QL fails to parse is reported rather
  than persisted.
- **Set a stable, normalized `ki_id`** derived from the indicator's own identifying data, so a
  re-run replaces rather than duplicates. This is the whole dedup mechanism; get it wrong and every
  run grows the index.
- **Put every ES|QL the indicator carries into `attributes.esql`**, and mirror structured values
  into both `content` and `attributes`.

A complete worked example — grounding steps, prompt, verified sink — is in the
`index-selection-reference-workflow` resource attached to this skill. Read it as the reference for
what a finished automation looks like, whether you are drafting one or judging one.

## Shapes for each strategy

`analyze-and-improve` chooses the strategy. These are what each one becomes as a workflow. Whoever
drafts it describes it to `platform.core.generate_workflow` in natural language using these as the
spec — do not submit YAML to it directly.

**Index/Table Metadata** (`type: index_metadata`) — a `foreach` over a list of index names. Per
iteration: fetch the mapping, sample documents, then an `ai.prompt` producing purpose, what the
index does not contain, key fields, joins, when-to-use, and access patterns (each with a question
type, an ES|QL template, a runnable example, params and returns). Sink with `ki_id` set to the index
name and `attributes.esql` set to the runnable examples so the verifiers check them.

**Bottom-Up** (`type: document`) — an ES|QL query pulling id, title and body, with the body
truncated (`SUBSTRING(body, 1, 12000)`). A `foreach` over the results, an `ai.prompt` per document,
and a sink with `ki_id` of `<index>/<doc_id>`. When the pass yields many near-identically-titled
entries, emit one indicator per logical cluster and enumerate the members inside its `content`
instead of one per record.

**Selective / Outlier** (`type: event`) — an ES|QL query filtered to notable records, an
`ai.prompt` returning a significance verdict alongside the indicator, and an `if` step that only
sinks when the verdict is positive.

**Atomic Facts** (`type: fact`) — an ES|QL query over documents, an `ai.prompt` extracting a list of
discrete claims, then a `foreach` sinking one indicator per claim with `ki_id` of
`<index>/<doc_id>-fact-<n>`.

**Cumulative / Wiki-style** (`type: entity`) — a `foreach` over entity ids. Per entity: a query
finding every document referencing it, an `ai.prompt` synthesizing a profile, and a sink keyed on
the entity id. Re-runs read the stored indicator and merge through `context-engine.updateKi`,
enriching it over time rather than replacing it.

**Connector** — call `platform.workflows.get_step_definitions` for the connector type first. A
connector step to list records, a `foreach`, a second connector step to fetch each body, an
`ai.prompt` producing access patterns in `execute_connector_sub_action` form, and a sink keyed on
the source record id. Any of the strategies above can run over a connector.

**Detection / Feature** (`type: detection`, `feature`) — two complementary passes in one workflow,
over shared grounding: an error sample, a `CATEGORIZE` pass clustering messages into templates, and
a distribution aggregation. One `ai.prompt` emits detections (each a complete runnable query, not a
template, with a severity score); a separate one emits features (inventory entries with a subtype
and a stable slug). Every threshold and every evidence string must quote a value from the grounding
— no invented numbers. Guard ratio detections with a denominator floor so they cannot fire on a
handful of documents, set thresholds above the observed baseline with margin, and cap detections
per signal rather than emitting near-duplicate conditions. Derive `query_type` by parsing the ES|QL
for a `STATS` command rather than asking the model for it.

## Authoring: delegate the build-and-test loop to a subagent

A workflow that has never run is a guess. It can parse, name only step types that exist, resolve
every reference, and still be built on a query that matches nothing — and you would not know until
someone enabled it. The loop that settles this (draft it, run it, read the indicators it actually
wrote, fix what is wrong, run it again) is long, and nearly everything it emits is noise the person
you are talking to has no reason to read.

Run that loop in a subagent. `run_subagent` takes a `description` and a `prompt` and gives you back
one message, so the conversation keeps the finished workflow and the evidence for it without the
dozen turns that produced them.

**The brief is the whole job.** A subagent starts with none of this conversation — no attachments,
no history, no tool results, not even the index id. Anything you leave out it will invent, and it
will invent it confidently. Put in the prompt:

- the AI index id, and whether its destination is an index or a data stream
- the sources and the exact corpus filter the automation should apply
- the strategy from `analyze-and-improve`, and what the indicators are meant to capture
- an instruction to load `workflow-authoring` and `ai-index-automations` and to build to the rules
  in this skill, so you do not have to restate them
- the pilot tag you have chosen for this attempt
- that the complete final YAML must come back verbatim

That last point is worth stating bluntly in the prompt, because `run_subagent` tells the model its
job is to summarize. A summary of a workflow is worthless here: the YAML *is* the deliverable. Ask
for the entire definition in a single fenced `yaml` block with nothing elided, abbreviated or
replaced by a comment.

Give it a budget, too. A subagent shares this run's step limit, and "keep going until it works" is
an unbounded instruction — tell it to make at most three attempts and to come back describing what
is still wrong rather than burning the budget silently.

## The loop a subagent runs

If you are the subagent, this is the work.

**Draft it, and validate what you wrote yourself.**
`platform.core.generate_workflow` validates its own output: it re-generates against the errors and
fails the call rather than returning YAML that does not parse. Do not re-validate what it gave you
— that is a round trip that cannot fail. Validation is for the YAML it did not produce: a step you
wrote out, a query you edited by hand. That must pass `platform.workflows.validate_workflow`.
Validate the whole definition rather than the fragment you changed, because a step in isolation
cannot tell you whether its references still resolve. When validation fails it returns the step
definitions for every step type the workflow references — read those instead of swapping in a step
type you have not verified.
`platform.workflows.get_examples` shows working definitions when you are unsure of a shape.

Validation establishes that the workflow parses, that its step types exist and that its references
resolve. It does **not** establish that a query inside it returns anything, which is why the rest of
this loop exists.

**Tag every write.** Give each `context-engine.createKi` a `tags` entry of `ce-pilot-<runId>`, where
`runId` is unique to this attempt. That tag is the only handle you will have on what the pilot wrote:
on a data-stream destination `createKi` refuses `ki_id` and Elasticsearch generates the ids, so there
is nothing else to find them by. Bound the corpus filter to a handful of documents while you are
iterating.

**Run it without saving.** `platform.core.execute_workflow` accepts a `yaml` argument and runs the
definition ephemerally — nothing is persisted, nothing needs enabling. It waits for completion and
returns step outputs and the failure message when a step throws.

**Read what it wrote, not whether it ran.** A workflow completes cleanly and still emits indicators
with empty `content`, absent `attributes`, or titles too alike to tell apart under retrieval. Query
the tag back with `platform.core.execute_esql`:

```esql
FROM <destination> METADATA _id
| WHERE tags == "ce-pilot-<runId>"
| KEEP _id, title, type, content, attributes
| LIMIT 100
```

Judge those against what the brief asked for. Where a step's ES|QL is the problem,
`platform.core.generate_esql` will rewrite it given the failing query, the reason and the mapping.
Fix and run again, within your attempt budget.

**Clean up before you return.** The pilot wrote into the user's real index, so the tagged indicators
are yours to remove and cleanup is not optional — a skipped one leaves junk that nobody else will
know to look for. Run a second inline workflow: an `elasticsearch.esql.query` selecting `_id` for the
tag as above, then a `foreach` over the results calling `context-engine.deleteKi` with `ki_id` set to
each `_id`. Query the tag once more afterwards and confirm it returns nothing. Do this for every
`runId` you used, not only the last.

**Strip the tag, then hand it back.** Remove the `ce-pilot-*` tag from the `createKi` steps and widen
the corpus filter back to what the brief specified — the pilot's narrow filter is not the automation.
Return the finished YAML in full, a plain-language account of what the workflow does, and what the
pilot indicators looked like. The last of those is the evidence the reviewer approves on.

## Saving what comes back

Save the YAML exactly as the subagent returned it. Re-generating it from a description discards the
definition the pilot proved and saves a different one — one whose queries nobody has run.

Present the subagent's summary and its pilot indicators before you save. The save confirmation names
the workflow and the index but shows none of its content, so that account is the only thing the user
has to approve on.

## Running one is a separate decision

Piloting inside the loop above is authorized by the brief that started it, and is bounded to a
handful of documents that get deleted afterwards. Running the saved automation is not the same act:
it writes indicators across the whole corpus and costs model calls on every document it touches.

Do not execute a saved workflow unless the run you are in has told you to. `platform.core.execute_workflow`
starts a run and `platform.core.get_workflow_execution_status` reports on it.

## Corpora larger than 10,000 documents

ES|QL caps at 10,000 rows per query. An automation over a larger corpus needs offset-based
pagination, or a parent workflow dispatching per-item children with `workflow.executeAsync`. Note
the cap rather than drafting a workflow that silently truncates — this fails quietly, and the index
looks under-covered for reasons no one will connect back to here.
