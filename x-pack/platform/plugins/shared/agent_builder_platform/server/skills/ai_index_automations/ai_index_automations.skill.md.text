## When to Use This Skill

Load this skill to **read, draft or change the workflow automations attached to a Context Engine AI
index** — the Kibana Workflows that turn its sources into knowledge indicators.

Reach for it when an index needs an automation it does not have, when a proposal names a step that
has to change, or when you need to know what an existing automation actually does before saying
anything about it.

Deciding what the index should contain and whether a change is warranted is `analyze-and-improve`.
Choosing the data an automation draws on is `ai-index-sources`.

## Read the automation before you say anything about it

`platform.workflows.get_workflow` returns a workflow's definition. Read it for a specific step,
because a useful change names one: what it samples and how much, what it asks the model for, how
many indicators it can emit, and what it writes into which fields.

A pipeline's *shape* often bounds what it could ever produce, however well its prompts are worded —
an automation that samples twenty documents cannot describe a corpus of ten thousand, no matter how
the prompt is phrased. Look for that before looking at wording.

Misquoting what an automation does is the most expensive mistake available here: every claim built
on it inherits the error, and a reviewer who catches one stops trusting the rest. When several
automations write to the same index, attribute an indicator to one by its
`governance.provenance.created_by.uri`, which the steps stamp as `workflow://<workflow id>`, and
confirm against the definition that writes to that destination and id pattern. Name that field in
`KEEP`: `platform.context_engine.query_ai_indices` drops `governance` from any query that does not.
If that does not settle it, say attribution was not established rather than guessing.

The syntax these automations need — Liquid templating, `on-failure` handling, `if` conditions — is
written out below, alongside the `context-engine` step contracts that no other skill or tool
describes. Between that and the templates, there is nothing here that needs a second skill loaded
to read or to write.

`workflow-authoring` covers the workflow engine in general and teaches a generate-first flow this
conversation does not use: the four templates replace it, and `platform.core.generate_workflow` is
not a tool to call here. Do not load `workflow-authoring` to author or change one of these
automations: it is more specific and more recently read than this skill, so it would win the
argument by default if loaded anyway.

## What every automation must do

Whatever the strategy, a generated workflow has to:

- **Read its source** through `elasticsearch.esql.query` or a connector step, applying the agreed
  corpus filter.
- **Ground the model on real data** before asking it for anything — a sample of documents, and for
  detections a distribution aggregation whose observed counts every threshold must quote. Sample
  with `function_score` + `random_score` so repeated runs see different records rather than always
  the first-ingested ones.
- **Use `ai.prompt` rather than `ai.agent`** unless tool use is genuinely required, and set its
  `connector-id` to `.google-gemini-3.5-flash-chat_completion`. That is the default model for
  every prompt step in every automation this skill produces: the templates carry it, and a
  workflow you assemble outside the templates carries it too, on each `ai.prompt` and `ai.agent`
  step. Use a different connector only when the user names one; they can change it after the save,
  in the workflow editor, without your involvement.
- **Retry `ai.prompt` outside a `parallel` branch**: `on-failure.retry` with three attempts,
  exponential delay and jitter. Rate limits, transient connector errors and a structured output
  that failed to parse once are the ordinary failures of a model call, and without the retry each
  one costs the unit it was profiling. A `parallel` branch cannot hold `on-failure`. The templates'
  loops are all `parallel`, so they run their model calls without it: a failed call costs that one
  item until the next run, and a pilot that wrote fewer KIs than it covered shows it.
- **Write through the `context-engine` steps**, never a raw `elasticsearch.index`, and pass
  `verifiers` to every `context-engine.createKi` so an indicator whose ES|QL fails to parse is
  reported rather than persisted.
- **Set a stable, normalized `ki_id`** derived from the indicator's own identifying data, so a
  re-run replaces rather than duplicates. This is the whole dedup mechanism; get it wrong and every
  run grows the index.
- **Put every ES|QL the indicator carries into `attributes.esql`**, and mirror structured values
  into both `content` and `attributes`. An indicator with no runnable query omits the key rather
  than writing an empty list.

Index metadata, bottom-up document, unit profile and targeted-ki-writer automations are all
installed by `platform.context_engine.install_automation_template`. Every install takes a `name`:
installing the same template with the same `name` replaces that automation in place, and a
different `name` adds another automation to the AI index. `targeted-ki-writer` is installed with
`template: targeted_ki_writer` — the same tool, same pattern as the others.

Two more references are attached and shared with `analyze-and-improve`: `ki_shapes`, the KI
document shape with the fixed `type` vocabulary and the provenance references, and `strategy_catalog`,
the three strategy choices and their worked examples. `analyze-and-improve`'s proposal is written in
that vocabulary, and the `consts` of the templates are the same three choices, so read them when the
proposal names something the template does not spell out.

## The `context-engine` step contracts

These four steps come from the Context Engine plugin rather than the workflow engine's own catalog,
and no discovery tool can see them: `platform.workflows.get_step_definitions` reads the built-in and
connector registries only, and the definitions that validation attaches to a failure come from those
same registries. Nothing will correct a mistake in one of these except a failing run, so they are
written out here — this skill is the only place they exist.

**`context-engine.createKi`** writes a new indicator and outputs `id`, the document id it wrote.

```yaml
- name: write_ki
  type: context-engine.createKi
  with:
    ai_index_id: 'my-ai-index' # required
    ki_id: 'logs-index-profile' # optional, generated when omitted
    ki: # required
      type: 'index_metadata' # required
      title: 'logs-* index profile' # required
      description: '...' # optional, <= 2048 chars
      content: '...' # optional, <= 65536 chars
      tags: ['logs'] # optional, <= 100 entries
      references: # optional, <= 100 entries
        - uri: 'index://logs-*'
          relation: 'derived_from' # derived_from | relates_to | supersedes
          description: 'The indices this profile describes'
      expires_at: '2026-10-22T00:00:00Z' # optional; unset never expires
      attributes: # optional, <= 100 keys
        esql: 'FROM logs-* | LIMIT 10'
```

Passing the same `ki_id` again is the whole of what makes a re-run idempotent rather than
duplicative. On an index the same `ki_id` replaces the indicator; on a data stream it appends a new
revision, and the newest revision is the current one. `references` records what the indicator was
derived from, in the URI schemes `ki_shapes` lists.
`id`, `updated_at` and `governance.provenance` are stamped by the step; never supply them.

**`context-engine.updateKi`** takes `ai_index_id` and `ki_id` plus a `ki` carrying only the fields to
change, and outputs `id` and `result` (`updated` or `noop`). Arrays are replaced, a null
`expires_at` clears the expiry, and `lifecycle: { status: active | deleted }` sets the lifecycle
status. It fails when the indicator does not exist, or is deleted unless `force: true` is set, so
it belongs to the cumulative strategy that reads before it merges — it is not a substitute for
`createKi`.

**`context-engine.deleteKi`** takes `ai_index_id` and `ki_id` and outputs `id`.
On an index `deleteKi` removes the document; on a data stream it appends a revision with
`governance.lifecycle.status: deleted`, so the earlier revisions stay in the backing store and
`platform.context_engine.query_ai_indices` hides the indicator. It fails when the indicator does
not exist.

**Verification rides on `createKi`.** Its `verifiers` list is non-empty and duplicate-free, and the
step runs each entry in order before it writes. The two built-in verifier ids are
`esql-valid-syntax`, which parses each query the indicator carries without touching the cluster,
and `esql-valid-runtime`, which executes it against live data bounded to a single row. An entry can
also be a custom verifier workflow, `{ workflow_id }`, with an optional `timeout_sec` and
`applies_to`; the templates use the two built-ins. An unknown id fails the step. When any verifier
fails, nothing is written, the output carries no `id`, and `verification.results` names the
verifier and the reason. Pass `verifiers` on every write: an indicator carrying ES|QL that does not
run is worse than a missing one, because retrieval surfaces it as though it worked.

`attributes` values are strings, numbers, booleans or arrays of strings — never nested objects. A
single value caps at 10,000 characters, which is what bounds the ES|QL an indicator can carry. A
`null` value omits the attribute: `esql: "${{ patterns | map: 'esql_example' | default: nil }}"`
leaves `attributes.esql` out when the list is empty, and the verifiers skip an indicator without it.
Never write an empty list or an empty string there; both fail verification. What the fields mean,
which `type` values exist, and which provenance goes in `references` is `ki_shapes`; this
section is only the step's input contract.

## Two shapes that produce the wrong thing without failing

Both of these parse, validate and run. Nothing reports them. They simply write indicators with the
wrong contents, which is why they are worth knowing before you draft rather than after.

**Anything that is not a string needs `${{ }}`, not `{{ }}`.** A plain `{{ }}` renders its value into
a string: an object arrives as `[object Object]`, and `false` arrives as the string `"false"`, which
is truthy and will pass an `if`. `${{ }}` evaluates the expression and preserves the type. Wherever a
whole object, a number or a boolean is passed — a `foreach.item` handed to a step, a condition, a
document body — it is `${{ }}`:

```yaml
- name: write_report
  type: elasticsearch.index
  with:
    document: '${{ foreach.item }}'
```

**An `ai.prompt` result is nested under `output.content`.** The step outputs `{ content, metadata }`,
so the model's answer is at `steps.<name>.output.content`, and when the step declares a `schema` every
field of the structured result is at `steps.<name>.output.content.<field>`. It is never
`steps.<name>.output.<field>`. Referencing the flat path interpolates nothing, and the run completes
having written indicators whose fields are empty.

## The rest of the syntax these automations use

Everything an automation of this kind needs is here or in a template. The general workflow-engine
reference is `workflow-authoring`, and it is worth loading for a validation error you cannot place
— but not for authoring, for the reason given at the top.

**An `if` condition is KQL, not Liquid.** `condition:` is the one place in a workflow where `{{ }}`
does not apply. A gate on a step's output reads `condition: "steps.set_flag.output.ready : true"`
— a KQL field match, with the colon, not `==` and not an interpolation. KQL cannot evaluate
filters, so anything computed goes through a `data.set` first and the condition reads that step's
output:

```yaml
- name: set_count
  type: data.set
  with:
    count: '{{ steps.query.output.values | size }}'
- name: check
  type: if
  condition: 'steps.set_count.output.count > 0'
```

**Every step takes the same optional properties**, whatever its type: `if:` to skip it, `timeout:`,
and `on-failure:` for error handling. A `foreach` additionally takes `iteration-on-failure`, which
is what keeps one bad record from ending a batch — worth setting on a loop that writes one
indicator per document, where the alternative is losing every indicator after the first failure.

```yaml
- name: loop_documents
  type: foreach
  foreach: '{{ steps.discover_documents.output.values | json }}'
  steps: [] # ...
  iteration-on-failure:
    continue: true
```

**`parallel` is that same loop with its items run concurrently**, and it is what the per-record
templates use: a model call per record run end to end is the slowest thing these workflows do. It
takes the same `foreach` expression and the same `steps` body, and swaps `iteration-on-failure` for
`mode: settled`, which likewise runs every branch to a terminal state instead of stopping at the
first failure. `concurrency` defaults to 5 and is capped at 20; the fan-out is capped at 100 items,
so corpora larger than 100 records must be split into batches with `chunk: 100` before entering
`parallel`. The per-record templates do this with an outer `foreach` over the chunks, so they
handle any corpus size up to the ES|QL row cap:

```yaml
- name: loop_batches
  type: foreach
  foreach: '{{ steps.discover_documents.output.values | chunk: 100 | json }}'
  iteration-on-failure:
    continue: true
  steps:
    - name: loop_documents
      type: parallel
      foreach: '{{ foreach.item | json }}'
      concurrency: 5
      mode: settled
      steps: [] # ...
```

A branch reads `{{ foreach.item }}` and its own earlier steps exactly as a sequential iteration
does. A branch cannot hold a step-level `timeout:` or `on-failure`, an `if`, a nested `foreach`,
`while` or `switch`, or a step that waits on a human: each is a compile-time error rather than a
surprise at runtime. Verify inside `context-engine.createKi` with `verifiers` rather than gating
the write with an `if`.

Outside a branch, any step can carry `on-failure` with a retry, a fallback and `continue`:

```yaml
on-failure:
  retry:
    max-attempts: 3
    delay: '5s'
  fallback:
    - name: handle_error
      type: console
      with:
        message: 'Step failed'
  continue: true
```

**Liquid references and the filters the templates rely on.** `{{ steps.<name>.output.<field> }}`
reads a step's output — only `output` is reachable, never a step's inputs. `{{ consts.<name> }}`,
`{{ inputs.<name> }}`, `{{ foreach.item }}` and `{{ event }}` reach the
rest. `{%- for x in ... -%}` loops build the `content` block, and `{%- assign x = ... -%}` with
`{%- if ... -%}` computes a value a `data.set` stores for a condition to read.

| Filter | Use |
|---|---|
| `json` | Serialise a value — how a whole step output reaches a prompt, and how a list reaches `foreach` |
| `chunk: 100` | Split a list into batches. A parallel `foreach` throws above 100 items, so the document orchestration chunks the corpus at that ceiling |
| `json_parse` | Turn a JSON string back into a value; how the unit template's `references`, built as a string with a conditional entry, reach the KI as a list |
| `map: 'field'` | Pull one field out of a list of objects; how `attributes.esql` collects the runnable examples |
| `default: 'value'` | Fall back when a field is missing |
| ``remove: '`'`` | Drop the backticks from a backquoted field-name const, so it can sit inside a column name the unit template backquotes itself |
| `replace: '\\', '\\\\' \| replace: '"', '\\"'` | Escape a value being interpolated into an ES\|QL string literal: backslashes first, then quotes |

**Field names with spaces or capitals are backquoted inside the const**, not in the query: a const
`unit_key: "`Product Key`"` is pasted into every `WHERE`, `STATS ... BY` and `KEEP` as written, so
the query is right everywhere the const is used. An "Unknown column" error on a name copied from
the mapping is almost always a missing backtick.

Escaping matters more than it looks: an entity value interpolated raw into
`WHERE field == "{{ ... }}"` breaks the query the moment a value contains a quote, and the failure
lands on whichever entity happens to carry one. The unit template runs every unit key through
`replace: '\\', '\\\\' | replace: '"', '\\"'` before it reaches a query, and hands the prompt the
escaped key for the example queries it writes. Write the arguments exactly so: LiquidJS reads backslash escapes inside a quoted argument,
so `'\"'` is a bare quote and a `replace` written with it does nothing.

## Templates and shapes for each strategy

`analyze-and-improve` chooses the strategy and states it as three answers — the unit (what one KI
is about), what one KI carries, and how units are found and refreshed — with the named strategies
in `strategy_catalog` as worked examples. These are what each one becomes as a workflow.

Index metadata, bottom-up document, unit profile and targeted-ki-writer automations are installed by
`platform.context_engine.install_automation_template`. Do not write their YAML. Installing the same
template with the same `name` replaces that automation in place; a different `name` adds another.

Outlier, atomic facts, detection and connector automations have no template, and this conversation
does not author or run a workflow outside the templates above. When the strategy that fits an index
is one of these, say so and tell the user to build the workflow in the Workflow editor; once it is
saved there, `platform.context_engine.save_automation` with its `workflowId` attaches it to the AI
index as an automation, and `platform.context_engine.run_automation` runs it.

**Index/Table Metadata** (`type: index_metadata`) — call
`platform.context_engine.install_automation_template` with `template: index_metadata`. Pass
`sources`, one `{ index, categoryField }` per source of the AI index, where `categoryField` is the
keyword field an analyst would group that index by. List every source the profile should cover:
one install and one run write one KI per source, so do not install the template once per index.
The AI index is the one attached to the conversation. The tool fills the consts and attaches the
workflow. Do not write the YAML. Each KI's id is `<name>/<index>`, so
reinstalling an index-metadata automation from before `sources` existed, whose single KI has the id
`<name>`, leaves that old KI in place: tell the user it is now stale.

**Bottom-Up** (`type: document`) — call `platform.context_engine.install_automation_template` with
`template: document_orchestration`. Pass `sourceIndex`, `titleField` and `bodyField`. The AI index
is the one attached to the conversation.
Pass `corpusFilter`, `maxDocuments` and `bodyMaxChars` when the corpus needs a bound; they default
to an empty filter, 50 documents and 12000 characters. Keep `maxDocuments` within the KI budget
(`strategy_catalog`, "The KI budget"). `corpusFilter` is inserted after `FROM`.
A `WHERE` line may omit the leading `|`; the tool adds it. The tool attaches only the orchestration.
Each parallel branch summarizes one document and writes it through `context-engine.createKi` with its
verifiers. Do not save it. When the pass yields many near-identically-titled entries, say so: the installed
summary writes one indicator per document, and clustering them needs a workflow built outside this
conversation, in the Workflow editor.

**Cumulative / Wiki-style** (`type: entity`) — call
`platform.context_engine.install_automation_template` with `template: unit_profile`. Pass
`sourceIndex`, `unitKey` — the keyword field one profile is written per distinct value of —
`activityField`, a date field whose per-unit range bounds the unit's activity, and
`breakdownField`, a second field whose per-unit distribution characterises it. The AI index is the
one attached to the conversation. Do not write the YAML.
The unit key is what each indicator is titled by, so when the index carries both an id and a name
for the unit and they map one to one, prefer a human-readable field such as `product_name` over
`product_id`: an indicator titled by an opaque id is one no question will find.
**Pass `metricFields`.** Sibling unit indicators are near-identical to a retriever unless their
descriptions carry numbers that separate them, and `metricFields` is what puts those numbers
there: each one is averaged per unit and written into the profile. Choose up to ten fields an
analyst would compare these units on, each numeric in the mapping: `AVG` over any other type fails
the query for every unit.
Pass `corpusFilter`, a `WHERE` line, to profile only some units: it bounds both which units are
found and which of their rows the figures describe. It defaults to taking every row.
`maxUnits` bounds the run: one KI and one model call per unit. It defaults to 100, the KI budget;
keep it within that budget (`strategy_catalog`, "The KI budget").
Units are found by one ranked query capped at `maxUnits`, most active first, and
a re-run regenerates every unit and replaces its indicator.
The template reads one index. A unit that needs data from a second index — a customer's profile
plus what they bought from a products index, an incident header plus its events — needs a workflow
built outside this conversation, in the Workflow editor, starting from this template's shape.
To accumulate across runs rather than replace, read the stored indicator and merge through
`context-engine.updateKi` — that likewise needs a workflow built outside this conversation.

**Targeted KIs** (`type: constraint`, `workaround`, `disambiguation`, `task_recipe`) — call
`platform.context_engine.install_automation_template` with `template: targeted_ki_writer`. No model
call: the KIs are written verbatim from the `kis` array passed to the install, each through
`createKi` with its verifiers and a stable `ki_id`. Run it with `platform.core.execute_workflow`.
The content comes from the counted
finding in `analyze-and-improve`'s proposal, and so does the provenance — `trace_ids`,
`conversation_id`, `error_text`, `source_index` — from ids that already exist. Any ES|QL the KI recommends goes in `attributes.esql`
as well as `content`, so the verifiers run it; a KI with none leaves the key out. This is the shape
for a rule agents keep breaking or a recipe they keep rediscovering, when no systemic family would
carry it.

**Selective / Outlier** (`type: event`), **Atomic Facts** (`type: fact`), **Connector**, and
**Detection / Feature** (`type: detection`, `feature`) have no template. Do not call
`platform.context_engine.install_automation_template` for them and do not draft a workflow for them
yourself, through this tool or any other: tell the user to build it in the Workflow editor, as
described above.

## Projecting a full run from a pilot

**State the time estimate from the pilot in the same message.** The run dialog approves the full run
over the filtered corpus, so the cost of that run has to be on the table before it opens. Take the pilot's
duration and the number of units it wrote, divide to get a per-unit time, and multiply by the
number of units the saved run will write: the unit count from the proposal's Unit section
(units, not rows — a unit profile over 62,884 sales rows may have 2,517 units), or the
automation's own bound when that is lower: "the pilot wrote 5 indicators in 80 seconds; the full run writes 100
units, so expect roughly 27 minutes". When the pilot wrote fewer indicators than the batch it
covered, say how many and do not project: the others failed or did not pass verification. Say *roughly*: rate limits and the pause between batches can
slow a full run, and fixed costs the pilot paid once can speed it up, so the projection is neither a
floor nor a ceiling. Show the three numbers, not only the result, so the reader can see what was
assumed.

**When the projection exceeds one hour, put the estimate in bold between 🚨 markers** so it
cannot be skimmed past: "🚨 **The full run over 100 units will take roughly 80 minutes** 🚨".
Under an hour, write it in plain text. A projection that comes out in hours is a finding of its
own, and the answer is usually a narrower corpus filter or a cheaper unit rather than a shrug, so
follow the warning with the option you would take. Report token usage only when the execution
result carries it; the workflow engine records it per `ai.*` step where the connector reports it,
and where it did not, say the token count was not measured rather than estimating one.

## Running one is a separate decision

Piloting and running are not the same act. `run_automation`'s `pilotSize` runs the automation over a
handful of items and nothing more; running the saved automation in full writes indicators across the
whole corpus and costs model calls on every document it touches.

Saving an automation and running it are two separate operations, each with its own confirmation
dialog: `save_automation` confirms the save and `run_automation` confirms the run. The install tool
is neither: it does not confirm and it does not start a run.

**Index metadata, bottom-up document, unit profile and targeted-ki-writer** — call
`platform.context_engine.install_automation_template` once. Pass `template: index_metadata`,
`template: document_orchestration`, `template: unit_profile` or `template: targeted_ki_writer` and
the consts it asks for. Do not write the YAML and do not call
`platform.context_engine.save_automation` for these. Installing the same template with the same
`name` replaces that automation in place and keeps its workflow id, and the result says `replaced: true`; a different
`name` adds another automation. The install does not start a run.

**A workflow built in the Workflow editor** — once the user has saved it there, call
`platform.context_engine.save_automation` with its `workflowId` to attach it to the AI index as an
automation. Nothing here authors or edits that definition; the tool only registers the already-saved
workflow.

**Running** — call `platform.context_engine.run_automation` with the `workflowId` returned by the
install or save tool. It asks the user for confirmation and enables the workflow if it is disabled.
A full run returns immediately with `executionId` and `workflowUrl` — the run continues after the
call returns. Tell the user it has started and that they can ask for a progress update at any time.

**Pilot a template install that writes more than 5 items before its full run.** The install tool
does not run anything, so nothing has measured the automation, and the full-run dialog needs a time
estimate. A Targeted KI writer has no pilot: it makes no model call, and it runs through
`platform.core.execute_workflow` as described above. Count the items the full run writes: documents
(up to `maxDocuments`), units (up to `maxUnits`) or sources for Index/Table Metadata. For documents
and units, take the count from the Unit section of the proposal, or from a count query with the
corpus filter when there is no proposal; for Index/Table Metadata, the number of `sources`, or 1 for
`sourceIndex` with `categoryField`. When there are more than 5, call `run_automation` with
`pilotSize: 5` first. Every template's loop runs five items at a time, so a pilot of 5 is one
batch of the full run, and the per-unit arithmetic above holds. The pilot runs the automation over
the first five documents, the five most active units, or the first five sources of the same list the
full run uses, waits for it, and returns `status`, `durationMs` and `kisWritten`. When the pilot
ended with any `status` other than `completed`, report `errorMessage` and stop: there is no duration
to project from, and a failed pilot means the full run would fail the same way. When it is still
`running`, say the time is not yet measured, and check it with
`platform.core.get_workflow_execution_status` before you start the full run. Project only when
`kisWritten` equals the pilot size. When it is lower, say how many of the pilot's items wrote a KI and stop: the others failed or
did not pass verification, and the full run would lose the same share. Then project the full run
from `durationMs` and `kisWritten` as the time estimate above lays out — the full run writes the
item count counted above — and state it. When it
exceeds an hour, give the 🚨 warning and the cheaper option you would take in the same message. Then
call `run_automation` again without `pilotSize`; its dialog asks for the full run. The full run
replaces the pilot's indicators, since they share ids; on an AI index backed by a data stream it
adds a newer revision of each instead. If the user declines it, the pilot's indicators stay in the
index: say so.

**With 5 items or fewer, skip the pilot**: it would be the full run. Say the run covers only that
many items, so there is no time estimate, and start it.

## Corpora larger than 10,000 documents

ES|QL caps at 10,000 rows per query. The templates stay under it by design: each discovery query
keeps the top `max_units` or `max_documents`, at or under the cap. A custom automation that must
walk a larger corpus needs cursor pagination — a `while` over a keyword cursor around its discovery
query and `foreach` — or a parent workflow dispatching per-item children with
`workflow.executeAsync`. Note
the cap rather than drafting a workflow that silently truncates — this fails quietly, and the index
looks under-covered for reasons no one will connect back to here.
