# Saved object audit diff: performance and memory results

Measurements for the opt-in field-level diff added to saved object audit events
(elastic/kibana#281571). Two parts:

- **Part A** isolates the cost of the diff computation itself (`computeJsonPatch`)
  per object shape, using `@kbn/bench`.
- **Part B** measures a running Kibana under a capped heap, with the feature on and
  off, driving identical write workloads through the public saved objects API and
  sampling Kibana's own process metrics.

Both were run on 2026-09-09 against branch head `213f26666d55` (Kibana 9.6.0).

## Part A: cost of the diff computation

### Setup

`@kbn/bench` module benchmarks call `computeJsonPatch({ a, b, fieldSizeLimit })`
directly, in-process. Each scenario runs a fixed number of iterations after a
warm-up call and reports:

- **ms per call**: wall time averaged over the iterations.
- **ops / noOps**: entries in the resulting patch.
- **event size**: bytes of `JSON.stringify(patch)`, i.e. the `kibana.diff` payload.
- **heap allocated**: heap growth of one call measured before GC (transient garbage).
- **retained**: heap still held after a forced GC while the result object is alive.

Memory columns require `NODE_OPTIONS=--expose-gc`. Three runs per scenario; the
table shows averages. Std dev on timing was under 20% in every scenario.

Object shapes:

- **Nested**: `panels.pN = { title, vis: { type, params: { buckets, label, enabled } } }`,
  about 5 leaves per panel. Mirrors the OOM Scout suite. 200 / 2000 / 20000
  panels give roughly 1k / 10k / 100k leaves.
- **Array of objects**: a `panels` array of 2000 `{ id, type, version, gridData }`
  elements, where `b` has every element's keys in a different order but equal values.
- **Lens-like**: 50 form-based layers with three columns each (about 560 leaves)
  plus a 200 KB string attribute that exceeds `fieldSizeLimit`.

### Results

| Scenario | Leaves | ms / call | ops | noOps | Event size | Heap allocated / call | Retained by result |
|---|---|---|---|---|---|---|---|
| Nested, 1 leaf changed | 1k | 1 | 1 | 1k | 36.7 KB | 1.6 MB | 33 KB |
| Nested, 1 leaf changed | 10k | 14 | 1 | 10k | 375.6 KB | 15.6 MB | 391 KB |
| Nested, 1 leaf changed | 100k | 224 | 1 | 100k | 3.76 MB | 89.9 MB | 3.9 MB |
| Nested create (before = `{}`) | 10k | 8 | 10k | 0 | 653.6 KB | 9.4 MB | 546 KB |
| Nested, 2k of 10k leaves changed | 10k | 16 | 2k | 8k | 496.5 KB | 15.8 MB | 461 KB |
| Array of 2k objects, keys reordered | 2 | 2 | 0 | 2 | 88 B | 2.8 MB | ~0 |
| Lens-like, 50 layers + 200 KB string | ~560 | 1 | 51 | 505 | 48.8 KB | 1.1 MB | 8 KB |

### Reading

- Cost is linear in leaf count: roughly **1.5 to 2 µs and 1 to 1.5 KB of transient
  allocation per leaf**. No superlinear behaviour between 1k and 100k leaves.
- Realistic objects are cheap. The Lens-shaped object costs 1 ms and under 50 KB.
  Dashboards are cheaper still because `panelsJSON` is a single string leaf that
  `fieldSizeLimit` clamps.
- The pathological case, a 100k-leaf nested attribute tree, blocks the event loop
  for about 224 ms per write. Very few saved object types have attributes of that
  shape, and the per-type allow-list keeps them off by default.
- Transient allocation, not retention, is the memory effect. A 10k-leaf update
  allocates about 16 MB of garbage per call; what survives GC is only the event
  payload, released once the appender writes it.
- Event size is dominated by `noOps`. A single-leaf update of a 10k-leaf object
  produces a 376 KB event, almost entirely unchanged-path entries.
- Structural array comparison (`isEqual`) is not a hot spot: 2000 reordered objects
  compare in 2 ms.

## Part B: end-to-end A/B on a capped heap

### Setup

Two Scout server config sets, identical except for the diff flags:

| | diffs off (baseline) | diffs on |
|---|---|---|
| Heap | `--max-old-space-size=1536` | same |
| Audit | enabled, file appender, JSON | same |
| `savedObjectDiff.enabled` | `false` | `true` |
| `savedObjectDiff.typesToInclude` | n/a | `["index-pattern"]` |
| `ops.interval` | 2000 ms | same |

Each mode: boot Elasticsearch and Kibana with `node scripts/scout start-server
--arch stateful --domain classic --serverConfigSet <set>`, wait for `/api/status`
to report `available`, verify the process on port 5620 belongs to this worktree,
settle 20 s, run the driver, tear down. The audit log file was deleted before each
boot.

The driver (a Node script using `fetch`, basic auth as `elastic`) runs five
workloads against `index-pattern` saved objects through the public API. Payloads
stay under the test server's 1.6 MB `server.maxPayload`.

| # | Workload | Shape |
|---|---|---|
| 1 | Sequential bulk create | 5 batches of 6 objects, 2000 nested panels each (~10k leaves, ~1.4 MB per request) |
| 2 | Sequential single update | 40 title-only updates to one 10k-leaf object |
| 3 | Sequential bulk update | 5 rounds updating 20 objects of 400 panels (~2k leaves) |
| 4 | Import with overwrite | 2 passes of a 50-object ndjson, 200 panels each (~1k leaves); the second pass overwrites, exercising before-state reads |
| 5 | Concurrent bulk create | 3 rounds of 8 parallel batches, 10 objects of 1000 panels (~5k leaves) each |

Per workload the driver records:

- **Client latency** p50 / p95 / max per request (wall time as seen by the client).
- **Event loop delay** max and p99, from `GET /api/stats?extended=true`
  (`process.event_loop_delay` and the histogram percentiles) polled every second
  during the workload plus one extra ops interval after it. Values are per
  collection interval; the table shows the worst interval observed.
- **Event loop utilization** peak, same source.
- **Heap** used before the workload, peak during it, and after an 8 s settle; **RSS** peak.
- **Audit log** growth in events (lines) and KB.

All objects were deleted after the run. One run per mode.

### Reading

- **Memory is not the concern.** Heap peak and settled heap are within 3% between
  modes in every workload, both sitting around 1.2 to 1.3 GB of the 1.5 GB cap, with
  no drift across workloads. Neither mode came close to OOM, including with 240
  objects of ~5k leaves in flight. This matches Part A: allocation is transient and
  freed once the event is written. RSS moved by hundreds of MB in both directions
  between modes and is GC and OS behaviour, not attributable to the feature.
- **The event loop is the cost, and only under concurrency.** Sequential workloads
  show a ~1% latency change, inside run-to-run noise. Eight concurrent bulk writes of
  large nested objects raise latency p50 by 37% and event loop delay p99 from 90 to
  316 ms; utilization peaks at 0.81. That is the diff computing for 80 objects of
  ~5k leaves on the request path at once, consistent with Part A's ~2 µs per leaf.
- **Audit volume is the dominant effect.** Each ~10k-leaf write produces a ~375 KB
  event, again matching Part A, and it is nearly all `noOps`. For these object
  shapes the audit log grows by three orders of magnitude. This is the documented
  trade-off of emitting unchanged paths; `fieldSizeLimit` bounds individual values,
  not entry count.
- **The tested shapes are far beyond realistic saved objects.** They were chosen as
  the stressor the review asked about. A real Lens visualization is about 500
  leaves and costs 1 ms; dashboards store panels as a single string leaf.

### Caveats

- One run per mode. Differences under about 10% should be treated as noise. The
  concurrency deltas and the audit volume deltas are well above that.
- The roughly 1 s floor on every request in both modes is Elasticsearch's write
  refresh on saved object writes, not Kibana.
- Local Apple Silicon machine, dev-mode Kibana from source. Absolute numbers will
  differ on Cloud instances; the relative deltas are the useful part.
- Audit event counts differ slightly between modes because the feature replaces
  pre-operation `unknown` events with post-operation result events, and the
  workloads include a handful of non-write events (status polls, imports' reads).
- The first attempt at the diffs-on run collided with an unrelated Scout stack from
  another worktree that was occupying the same ports. That data was discarded, the
  objects created on the foreign stack were deleted, and the run was repeated with a
  port-ownership check.

## Reproducing

These numbers came from an ad hoc driver script that was since turned into the Scout suite in
this directory. The suite runs the same five workloads and records the same metrics; see the
README one level up for local and Cloud instructions. Part A is the `benchmarks/` config next
to it. Object sizes in the suite were reduced slightly so every request also fits under the
1 MB payload limit of Cloud deployments.
