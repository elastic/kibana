# Entity Store Performance Test — 2026-09-03

## Goal

Establish how the entity store behaves as engine count scales from 11 (baseline) to ~200, and find the first bottleneck before committing to that direction.

---

## Setup

- **Cluster:** local single-node (ES + Kibana on the same machine)
- **Kibana:** `xpack.task_manager.capacity: 50` (maximum)
- **Data generator:** synthtrace scenario `entity_store_scale`
- **Spaces:** `default` + `caue`

### Synthtrace scenario (`entity_store_scale`)

New file: `src/platform/packages/shared/kbn-synthtrace/src/scenarios/entity_store_scale.ts`

Emits synthetic log documents to `logs-perf.entity-default` (matched by the default `logs-*` source pattern — no `additionalIndexPatterns` needed). Key options:

| Option | Description | Default |
|---|---|---|
| `entityTypes` | Number of perf entity types to feed (1–89) | 89 |
| `cardinality` | Distinct entity IDs per type | 2000 |
| `docsPerMinutePerType` | Raw log docs emitted per type per minute | 20000 |
| `uniqueFields` | Extra attribute fields per doc | 2 |
| `seed` | RNG seed for reproducibility | 42 |

### Synthetic entity definitions

New file: `x-pack/platform/plugins/shared/entity_store/common/domain/definitions/perf_synthetic.ts`

89 definitions `perf.entity.001`…`perf.entity.089`, bringing total engine count to 100 (11 real + 89 synthetic). Every 10th definition uses composite identity (`euidRanking`); all others use `singleField`. Field names use underscores (`perf_entity_001_id`) to satisfy the ES|QL identifier restriction (numeric-starting segments are rejected by the parser).

### T4 + high cardinality — first failure mode found

**Synthtrace:** `entityTypes=14, cardinality=15000, docsPerMinutePerType=20000`

At cardinality=15,000, each active entity type has >10,000 distinct entities, crossing the `docsLimit=10,000` threshold and triggering multi-page ES|QL extraction.

| Metric | Value |
|---|---|
| Drift p95 | 2,834 ms |
| Drift p99 | 3,004 ms |
| Extract duration p95 (max type) | 26,549 ms |
| Overdue | 0 |

Then with the machine under pressure:

```
[ERROR] Logs extraction failed for perf.entity.003: Request aborted, took 71950ms
[ERROR] Logs extraction failed for perf.entity.009: Request aborted, took 71954ms
[ERROR] Logs extraction failed for perf.entity.008: Request aborted, took 71959ms
[ERROR] Logs extraction failed for perf.entity.004: Request aborted, took 71956ms
```

**Failure chain:**
1. `cardinality=15,000` → >10,000 entities per active type
2. Multi-page ES|QL extraction required (`docsLimit=10,000` per page)
3. Total query time ~72s > task `timeout=59s`
4. Task manager kills the task; HTTP request aborted ~13s later
5. Engines for those types fall behind their extraction window
6. Next risk: `applyMaxLagCutoff` fires (skip-ahead circuit breaker) once lag exceeds `lookbackPeriod=3h`

**Result:** **First concrete ceiling found.** On a single local node, cardinality=15,000 with 20,000 docs/min is enough to cause extraction timeouts on the most active types.

## Findings

1. **100 engines on a single node is fine** — task manager at capacity=50 handles it with <500ms median drift and zero dropped windows.

2. **200 engines (2 spaces) is sustainable but hot** — load p50 hits 89%; still zero overdue after settling. The second space costs almost nothing in code, but doubles the task manager workload.

3. **The extraction timeout (59s) is the real ceiling, not engine count** — the bottleneck is not how many engines are scheduled, but how long each extraction query takes. At cardinality=15,000 (multi-page territory), active types exceed the timeout on a local machine.

4. **On a real cluster** the ES|QL queries would be much faster (dedicated ES nodes, no shared CPU with Kibana and synthtrace), so the cardinality ceiling is expected to be significantly higher.

5. **`applyMaxLagCutoff` not triggered** during this test — no windows were dropped. The timed-out engines would eventually hit it if left running, but the test was stopped first.

---

## Suggested next steps

1. **Repeat T4 on a Cloud cluster** — removes the shared-CPU constraint; the actual ceiling should be much higher.
2. **Raise `docsLimit` or `timeout`** — config knobs available today; measure the tradeoff vs ES query cost.
3. **Push `entityTypes=89` on synthtrace** — feed all 89 types simultaneously to see whether task manager drift grows when every engine has real work.
4. **3rd space (T5 = 300 engines)** — zero code, just another `POST /s/perf3/api/security/entity_store/install`.
5. **Monitor `applyMaxLagCutoff`** — intentionally let timed-out engines run long enough to trigger it and measure the recovery behaviour.
