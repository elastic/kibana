# Entity Store Performance Test — 2026-09-03

## Goal

Establish how the entity store behaves as engine count scales from 11 (baseline) to ~200, and find the first bottleneck before committing to that direction.

---

## Setup

Two environments were used: a local single-node machine and an Elastic Cloud cluster.

### Synthtrace scenario (`entity_store_scale`)

New file: `src/platform/packages/shared/kbn-synthtrace/src/scenarios/entity_store_scale.ts`

Emits synthetic log documents to `logs-perf.entity-default` (matched by the default `logs-*` source pattern — no `additionalIndexPatterns` needed). Key options:

| Option | Description |
|---|---|
| `entityTypes` | Number of perf entity types to feed (1–89) |
| `cardinality` | Distinct entity IDs per type |
| `docsPerMinutePerType` | Raw log docs emitted per type per minute |
| `seed` | RNG seed for reproducibility |

### Synthetic entity definitions

New file: `x-pack/platform/plugins/shared/entity_store/common/domain/definitions/perf_synthetic.ts`

89 definitions `perf.entity.001`…`perf.entity.089`, bringing total engine count to 100 (11 real + 89 synthetic). Every 10th definition uses composite identity (`euidRanking`); all others use `singleField`. Field names use underscores (`perf_entity_001_id`) to satisfy the ES|QL identifier restriction (numeric-starting segments are rejected by the parser).

## Local machine results (capacity=50)

**Environment:** single-node ES + Kibana + synthtrace on the same machine.

### T3 — 100 engines, 1 space

**Synthtrace:** `entityTypes=14, cardinality=2000, docsPerMinutePerType=20000`

| Metric | Value |
|---|---|
| Drift p50 / p99 | 493 ms / 2,530 ms |
| Load p50 | 22% |
| `RunningAtCapacity` | 0% |
| Overdue | 0 |
| Extract p95 (median type) | ~19,700 ms |

**Result:** Healthy. 100 engines absorbed cleanly at capacity=50.

### T4 — 200 engines, 2 spaces (capacity=50)

**Synthtrace:** `entityTypes=14, cardinality=2000, docsPerMinutePerType=20000`

| Metric | Value |
|---|---|
| Drift p50 / p99 | 299 ms / 505 ms |
| Load p50 | 89% |
| `RunningAtCapacity` | 0% (briefly 6%, settled) |
| Overdue | 0 (briefly 2, drained) |
| `avg_recurring_throughput_per_min` | 227 (~2× as expected) |

**Result:** Healthy. Running hot but stable. Second space doubles task manager workload with zero code changes.

### T4 + high cardinality — first failure (local)

**Synthtrace:** `entityTypes=14, cardinality=15000, docsPerMinutePerType=20000`

With cardinality=15,000, active types exceed `docsLimit=10,000`, triggering multi-page ES|QL extraction. On the shared local machine the queries exceeded the 59s task timeout:

```
[ERROR] Logs extraction failed for perf.entity.003: Request aborted, took 71950ms
[ERROR] Logs extraction failed for perf.entity.004: Request aborted, took 71956ms
[ERROR] Logs extraction failed for perf.entity.008: Request aborted, took 71959ms
[ERROR] Logs extraction failed for perf.entity.009: Request aborted, took 71954ms
```

**Failure chain:** cardinality=15,000 → multi-page extraction → query time ~72s > task timeout 59s → engines fall behind → `applyMaxLagCutoff` would eventually fire.

**Result:** Local machine ceiling found at cardinality=15,000 with shared CPU. Cloud test needed.

## Cloud cluster results (capacity=10, default)

**Environment:** Elastic Cloud single-node cluster (`kibana-pr-285828`). `xpack.task_manager.capacity` left at the default of 10 — intentionally, to measure out-of-the-box behaviour.

### T3 — 100 engines, 1 space, cardinality=2000

**Synthtrace:** `entityTypes=14→39→89, cardinality=2000, docsPerMinutePerType=20000`

| entityTypes | Drift p50 | Drift p99 | Load p50 | `RunningAtCapacity` | Overdue | Extract p95 max |
|---|---|---|---|---|---|---|
| 14 | 304 ms | 1,026 ms | 85% | 24% | 1 | 15,656 ms |
| 39 | 476 ms | 1,495 ms | 75% | 22% | 0 | 15,656 ms |
| 89 | 436 ms | 1,277 ms | 80% | 22% | 0 | 15,656 ms |

**Observation:** Cloud ES is ~25% faster than local for extraction queries (p95 ~15s vs ~20s). However, `RunningAtCapacity` at 22% is persistent — **capacity=10 is already stressed at 100 engines**. The p95 ceiling at ~15.6s is consistent regardless of how many types are fed, confirming the bottleneck is per-engine extraction cost, not total engine count.

### T3 — 100 engines, 1 space, cardinality=15000

**Synthtrace:** `entityTypes=89, cardinality=15000, docsPerMinutePerType=20000`

| Metric | Value |
|---|---|
| Drift p50 / p99 | 152 ms / 512 ms |
| Load p50 | 60% |
| `RunningAtCapacity` | 0% |
| Overdue | 0 |
| Extract p95 (max) | 13,275 ms |
| Entities in latest index | ~360,000 (filling toward 1.3M) |

**Observation:** Surprisingly healthy while entities were still filling up (average ~4,000/type, below docsLimit). No multi-page extraction triggered yet. `RunningAtCapacity` dropped to 0% during the fill phase. The real stress begins once all types cross 10,000 entities.

### T4 — 200 engines, 2 spaces, cardinality=15000 — **saturation**

Added `caue` space with 100 engines installed. Both spaces share the same ES data; each space has its own task set and latest index.

**Progression:**

| Check | Drift p50 | Drift p99 | Load p50 | `RunningAtCapacity` | Overdue |
|---|---|---|---|---|---|
| Immediately after | 763 ms | 23,217 ms | 100% | 32% | 92 |
| ~5 min later | **156,145 ms** | **156,146 ms** | 100% | **100%** | **225** |

**Final state:**
- Every single poll cycle is `RunningAtCapacity` — no idle cycles at all
- `NoTasksClaimed: 0%`, `PoolFilled: 0%` — capacity is fully consumed before new tasks can be claimed
- Task manager self-reported: `assumedRequiredThroughput (227/min) > capacityPerMinute (92/min)`
- Drift of **156 seconds** — engines are 2.5 full extraction cycles behind schedule
- 225 tasks overdue — more than the entire second space (100 engines + supporting tasks)

**Capacity estimation reason (verbatim):**
> Task Manager is unhealthy, the assumedAverageRecurringRequiredThroughputPerMinutePerKibana (227.58) > capacityPerMinutePerKibana (92)

## Findings

### 1. capacity=10 is the binding constraint, not engine count

At capacity=10, task manager starts showing stress at 100 engines (`RunningAtCapacity: 22%`) and completely collapses at 200 engines (`RunningAtCapacity: 100%`, 225 overdue). The required throughput (227 tasks/min) is 2.5× the available capacity (92 tasks/min). **Raising `xpack.task_manager.capacity` to 50 would absorb 200 engines cleanly**, as demonstrated on the local machine.

### 2. Cloud ES is ~25% faster than local for extraction queries

Extraction p95 (max type) was 15.6s on Cloud vs 20.5s locally. Dedicated ES nodes make a meaningful difference for the ES|QL aggregation queries. The 59s timeout is not a concern on Cloud at cardinality=2,000.

### 3. The docsLimit=10,000 threshold is the cardinality cliff

Below 10,000 entities per type: single-page extraction, fast queries, stable. Above 10,000: multi-page extraction, query time grows linearly with entity count. At cardinality=15,000 this wasn't yet a problem on Cloud (queries still completed in ~13s), but it caused timeouts on local.

### 4. `applyMaxLagCutoff` not triggered during these tests

No extraction windows were dropped. The T4 saturation state would eventually trigger it — once any engine's lag exceeds `lookbackPeriod=3h` — but the test was stopped before that point.

### 5. Space multiplication is free in code, expensive in capacity

Adding a second Kibana space requires zero code changes but doubles every task manager metric. Capacity must scale proportionally with space count.

## Capacity formula

```
required_throughput_per_min = engines_per_space × spaces × (1 / interval_minutes)
available_throughput_per_min = capacity × (interval_seconds / avg_extraction_seconds)

healthy when: required < available
```

For 100 engines, 1 space, avg 10s extraction, interval 1m, capacity 10:
```
required  = 100 × 1 × 1 = 100/min
available = 10 × (60/10) = 60/min  → STRESSED
```

For 100 engines, 1 space, capacity 50:
```
available = 50 × (60/10) = 300/min  → HEALTHY
```

## Recommended next steps

1. **Set `xpack.task_manager.capacity: 50`** on production clusters running >50 entity engines — the default of 10 is insufficient.
2. **Re-run T4 on Cloud with capacity=50** to confirm 200 engines is sustainable on dedicated hardware.
3. **Push cardinality to 50,000+** (on Cloud, capacity=50) to find the real multi-page extraction ceiling.
4. **Test T5 (300 engines, 3 spaces)** — install into a third space, observe whether capacity=50 still holds.
5. **Add a second Kibana instance** — task manager distributes work across nodes; a second Kibana should halve per-node load at T4/T5.
6. **Monitor `applyMaxLagCutoff`** — intentionally saturate a cluster and measure how long until windows start dropping and whether engines recover cleanly.
