# LOOKUP-JOIN

`LOOKUP JOIN` adds new columns to query results by finding documents in a lookup index that match rows from the current result table.

For each row that matches a document in the lookup index based on the join fields, all fields from the matching document are added as new columns. If multiple lookup documents match a single row, the output contains one row for each matching combination.

## Syntax

`FROM <source_index>
| LOOKUP JOIN <lookup_index> ON <join_condition>`

### Parameters

#### `<lookup_index>`

The name of the lookup index. This must be a specific index name or alias. Indices used for lookups must be configured with the `lookup` index mode.

In cross-cluster or cross-project queries, you can prefix the index name with `_coordinator:` to run the lookup on the coordinating node of the local cluster or origin project instead of on each remote cluster or linked project. This allows `LOOKUP JOIN` to be used after pipeline-breaking commands such as `STATS`, `LIMIT`, and `SORT`.

#### `<join_condition>`

The join condition used to match rows from the current query results with documents in the lookup index.

Can be one of the following:

- A single field name
- A comma-separated list of field names, for example `<field1>, <field2>, <field3>`
- An expression with one or more predicates linked by `AND`, for example `<left_field1> >= <lookup_field1> AND <left_field2> == <lookup_field2>`. Each predicate compares a field from the left index with a field from the lookup index using binary operators (`==`, `>=`, `<=`, `>`, `<`, `!=`). Each field name in the join condition must exist in only one of the indexes. Use `RENAME` to resolve naming conflicts.
- An expression that includes full text functions and other Lucene-pushable functions, for example `MATCH(<lookup_field>, "search term") AND <left_field> == <lookup_field>`. These functions can be combined with binary operators and logical operators (`AND`, `OR`, `NOT`) to create complex join conditions. At least one condition that relates the lookup index fields to the left side of the join fields is still required.

If using a join on a single field or a field list, the fields used must exist in both the current query results and the lookup index.

## Examples

Check source IPs against a lookup index of known malicious addresses.

```esql
FROM firewall_logs
| LOOKUP JOIN threat_list ON source.IP
```

Filter firewall logs to rows with a matching `threat_list` entry.

```esql
FROM firewall_logs
| LOOKUP JOIN threat_list ON source.IP
| WHERE threat_level IS NOT NULL
```

Add host inventory and ownership metadata to system metrics.

```esql
FROM system_metrics
| LOOKUP JOIN host_inventory ON host.name
| LOOKUP JOIN ownerships ON host.name
```

Add service owner and escalation metadata to application logs.

```esql
FROM app_logs
| LOOKUP JOIN service_owners ON service_id
```

Filter employee rows before joining language metadata.

```esql
FROM employees
| EVAL language_code = languages
| WHERE emp_no >= 10091 AND emp_no < 10094
| LOOKUP JOIN languages_lookup ON language_code
```

emp_no:integer | language_code:integer | language_name:keyword
10091 | 3 | Spanish
10092 | 1 | English
10093 | 3 | Spanish

Filter employee rows after joining language metadata; the optimizer can push the filter before the lookup when possible.

```esql
FROM employees
| EVAL language_code = languages
| LOOKUP JOIN languages_lookup ON language_code
| WHERE emp_no >= 10091 AND emp_no < 10094
```

emp_no:integer | language_code:integer | language_name:keyword
10091 | 3 | Spanish
10092 | 1 | English
10093 | 3 | Spanish

## Limitations

Wildcards and remote cluster prefixes are not supported for `<lookup_index>`. If the query source includes remote indices, the lookup index must exist on all involved clusters.

In joins on a single field or a field list, multi-valued entries do not match anything, and the added fields contain `null` for those rows.

`LOOKUP JOIN` is unavailable in Serverless Elasticsearch Vector Database projects.
