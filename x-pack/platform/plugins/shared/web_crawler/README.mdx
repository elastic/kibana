## Overview

This plugin crawls a website into an Elasticsearch index. It owns the crawl task, the index that
holds crawl state and history, the routes that start, list, stop and delete crawls, the
`webCrawl.run` workflow step, and two components a hosting plugin renders: the form that starts a
crawl and the page that manages crawls.

It does not register an application. Hosting plugins render the components inside their own app and
route. Today `elasticsearchHome` renders the form in its "Add data" section for hosts that opt in,
and `search_homepage` mounts the page and links it from the side nav under Data management.

The plugin is enabled by default, but `config/serverless.yml` sets `xpack.webCrawler.enabled: false`,
so serverless project types that crawl have to re-enable it in their own `serverless.<project>.yml`.
Today that is Elasticsearch.

## Rendering it from a host plugin

Add `webCrawler` to `requiredPlugins` or `optionalPlugins` and render the components from the start
contract. They bring their own Kibana services and query client, so they only need the host's
identity as props.

| Component | Props |
| --- | --- |
| `WebCrawlPanel` | `telemetryPrefix`, `storageKeyPrefix`, and optionally `onManageWebCrawls`, which opens the host's route for `WebCrawlsPage` and adds a link to it. |
| `WebCrawlsPage` | `telemetryPrefix`, `storageKeyPrefix`, and optionally `solutionNav`, the host's side nav under the classic chrome style, and `onNavigateHome`, for the page's back link. |

`telemetryPrefix` namespaces the `data-telemetry-id` of every element the components render.
`storageKeyPrefix` namespaces the localStorage key that remembers the last crawl started from the
panel.

## How a crawl works

The panel takes a website URL and crawls it into a `web-crawl-<host>` index, or into the index
the user names. The crawl runs as a
Task Manager task, so it survives the request, runs on background task nodes where a deployment has
them, and stays off the request path. Kibana never fetches the site itself: each page is fetched and
converted to markdown by a `document_extraction` inference endpoint, preferring the Elastic
Inference Service one, and Kibana only extracts the links from that markdown.

A crawl follows same-site links from the URL it was given. The pages listed in the site's sitemaps
(the ones `robots.txt` names, or `/sitemap.xml`) join the links of that first page, one link away.
`robots.txt` is honoured for every page, using the `Elastic-Crawler` group when the file has one and
the `*` group otherwise; a `robots.txt` that cannot be read allows everything. `robots.txt` and the
sitemaps are read through the same inference endpoint as the pages.

Each crawl takes a maximum depth (default 2, at most 5) and a maximum number of pages (default 500,
at most 1000). The page maximum caps the pages requested, so it also caps the documents indexed.
Each page is indexed once, keyed by its URL, with its markdown in `content` for full-text search and
copied into the `semantic_text` field `content_semantic`. `url_host`, `url_path` and
`url_path_dir1` to `url_path_dir3` hold the parts of the URL, for filtering by site section.

A crawl can be narrowed with path prefixes: with `includePaths` only pages under one of them are
followed, and pages under an `excludePaths` prefix never are. The URL the crawl starts from is always
crawled. Links with more than 16 path segments or more than 10 query parameters are not followed, as
those are mostly calendars and faceted listings. Each crawl counts the links it skipped because of
`robots.txt` and because of the path rules.

When `robots.txt` sets a `Crawl-delay`, requests to the site are spaced out by it, up to three
seconds: a longer pause could not fit the largest crawl into the hour the task is given.

### Several sites, one index

A crawl writes to one index. By default that is `web-crawl-<host>` for the host of its URL; a
crawl can name another one, which is how several sites end up in the same index. A crawl only
writes into an index that does not exist yet or that a crawl created, and one crawl at a time runs
into an index.

A crawl can also be given more start URLs. They may be on other sites, and every site with a start
URL is then crawled: each has its own `robots.txt`, `Crawl-delay` and sitemaps, and links are
followed within the site of the page they are on. Explicit sitemap URLs are read besides the
sitemaps the sites declare, and the pages they list are crawled when they are on one of those
sites. A start URL its site's `robots.txt` disallows is skipped; the crawl fails only when none
is allowed.

### Pages that disappear

A crawl that reads the whole site ends by deleting the documents earlier crawls indexed and it did
not find again, so pages removed from the site leave the index. Documents deeper than the crawl went,
and documents of sites the crawl had no start URL on, are left alone, so crawls of different sites
into one index do not delete each other's pages. A crawl that failed on any page, reached the page maximum or was stopped deletes
nothing, because it cannot tell a removed page from one it did not get to.

### How a crawl runs

Ten workers pull pages from a queue that always hands out the shallowest page found so far. That
keeps the crawl close to breadth-first without waiting for a whole depth level to finish, so one
slow page costs one worker rather than the level. `robots.txt` is read first; the sitemaps are read
while the first page is crawled. Indexing runs beside extraction: a bulk request goes out as soon as
there is a page and nothing in flight, and under load up to three requests run at once, each closed
at twenty pages or one megabyte of content, whichever comes first. Extraction only waits when
indexing has fallen a full set of requests behind. A rate-limited extraction is retried twice with a
backoff.

### Crawl state and history

Every crawl is one document in the `.kibana-web-crawls` index, written when the crawl starts and
updated in place until it ends, so the same index holds the crawls in progress and the history. It
is an index rather than a data stream because a running crawl rewrites its progress every few
seconds and reads a stop request back from the same document, and data streams are append-only. The
`.kibana*` prefix is already granted to the Kibana system user, so the index needs no registration
in Elasticsearch. Fields are only ever added to its schema.

Crawls into different indices run side by side. An index that is being crawled into is not crawled
into again until that crawl ends. A crawl whose task disappeared without recording an outcome, as after a restart, is
reported as failed once it has been silent for a minute.

The state index is written by the Kibana system user, so access is decided by the index a crawl
writes to: listing shows the crawls into indices the user can `read`, and stopping, deleting from
the history and crawling into an existing index need `write` on it. The task itself runs with an API
key granted from the request that started it, so the user also needs to be allowed to use the
inference endpoint and to create the index.

### Managing and scheduling crawls

`WebCrawlsPage` lists running and past crawls and starts, stops, repeats and deletes them.

Recurring crawls are workflows. With the optional `workflowsExtensions` plugin, this plugin
registers the `webCrawl.run` step, which starts a crawl as the workflow's user and waits for it to
finish, so later steps can use its outcome. The page creates a workflow with a scheduled trigger
and that step, tagged `web-crawl`, either for a website entered in the "Schedule a crawl" dialog or,
from a crawl's schedule action, for that crawl's website, index and options. Pausing, changing and deleting
a schedule happens in Workflows. Scheduling is offered to users who can create workflows.

## Public API

`public/index.ts` is the whole browser-facing surface. The components reach a host through the start
contract, so nothing needs importing to render them, and beyond the plugin initializer the barrel
exports only types: `WebCrawlerPublicStart`, `WebCrawlPanelProps` and `WebCrawlsPageProps`.

## Server

- `POST` and `GET /internal/web_crawler/crawls`, `GET` and `DELETE
  /internal/web_crawler/crawls/{id}` and `POST /internal/web_crawler/crawls/{id}/_cancel` — start,
  list, read, remove from the history and stop crawls.
- The `web_crawler:crawl` task type.
- The `webCrawl.run` workflow step, when `workflowsExtensions` is available.
