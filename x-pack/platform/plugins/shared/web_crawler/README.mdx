## Overview

This plugin will crawl a website into an Elasticsearch index. It is being built in steps, and so far
holds the crawl itself: finding the pages of a site, having each one fetched and converted to
markdown by a `document_extraction` inference endpoint, and indexing them. Nothing starts a crawl
yet.

## Enabling it

The plugin is off by default and loads where `xpack.webCrawler.enabled` is set to `true`. The
Elasticsearch and vector database serverless project types set it.

The crawler is still being built, so there everything it offers is also behind the
`webCrawler.enabled` feature flag, which is off by default. To turn it on locally:

```yaml
xpack.webCrawler.enabled: true
feature_flags.overrides:
  webCrawler.enabled: true
```

## Finding pages

A crawl follows same-site links. Links are normalized to absolute http(s) URLs without fragment or
credentials, and links to assets such as images and archives are left out. Links with more than 16
path segments or more than 10 query parameters are not followed, as those are mostly calendars and
faceted listings.

`robots.txt` is honoured using the `Elastic-Crawler` group when the file has one and the `*` group
otherwise, including its `Crawl-delay` and the sitemaps it names. A site without a `robots.txt`
allows everything; a site whose `robots.txt` request fails is left out of the crawl, and the crawl
fails when that leaves no site. Sitemaps and sitemap indexes are read within a small request budget.

A crawl can be narrowed with path prefixes: with `includePaths` only pages under one of them are
followed, and pages under an `excludePaths` prefix never are.

Links to files are not followed unless the crawl is given their extensions in `fileExtensions`. The
ones in `WEB_CRAWL_FILE_EXTENSIONS` can be asked for: PDF and Office documents, CSV and JSON files,
and images. The inference endpoint returns their text, and for an image a short description, which
is indexed like the markdown of a page.

## How a crawl runs

Kibana never fetches the site itself: each page, `robots.txt` and sitemap is fetched by a
`document_extraction` inference endpoint, preferring the Elastic Inference Service one, and Kibana
only extracts the links from the markdown that comes back.

Ten workers pull pages from a queue that always hands out the shallowest page found so far, which
keeps the crawl close to breadth-first without one slow page holding up a whole depth level. A
`Crawl-delay` in `robots.txt` spaces out the requests to that site, up to three seconds. A
rate-limited extraction is retried twice with a backoff.

A crawl starts from one or more URLs and stays on the sites those are on, each with its own
`robots.txt`, crawl delay and sitemaps. It takes a maximum depth and a maximum number of pages.

Indexing runs beside extraction. Each page is crawled and indexed once, keyed by its URL without
the scheme and a trailing slash, so the `http` and `https` URLs of a page are one document. Its
markdown is in `content` and copied into the `semantic_text` field `content_semantic`. A bulk request closes at
twenty pages or one megabyte of content, and up to three run at once. Requests and documents that
Elasticsearch turns away as too many are sent again twice, with a backoff.

A crawl that read the whole site ends by deleting the documents earlier crawls indexed and it did
not find again, on the hosts it covered and within its path rules. One that failed on a page,
reached the page maximum or another of its limits, or was stopped deletes nothing, because it cannot
tell a removed page from one it did not get to.
