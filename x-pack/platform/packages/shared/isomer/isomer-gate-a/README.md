# @kbn/isomer-gate-a

Gate A for saved object materialization: does a materialized chart match what Kibana draws? Dev-only. It compares against Kibana's own output for the corpus's Lens panels (ES|QL `metric`, `xy`, `data_table`, `pie`, `treemap`, `mosaic`, `waffle`, `heatmap`, `gauge` and `tag_cloud`, and a data view `legacy_metric`), captured from a real Kibana by lane C's corpus suite.

- **Fixtures** (`fixtures/`, one file per panel) keep only what the gate reads from a capture: the as-code config, the render context (`now`, absolute time range, `dateFormat:tz`), Kibana's inspector tables, the chart's size, and, in light and dark, Elastic Charts' `DebugState` (legend, axes, series values and paths; partition slices; heat map cells; the gauge's `Bullet`) or, where a chart reports none, the page: the metric's DOM (background, texts and their colors), the data grid's headers and cells, the legacy metric's tiles, or the tag cloud's SVG words. To add a case, copy those fields from a corpus capture.
- **Seed data** (`buildEdgeCaseDocuments`, `EDGE_CASE_MAPPINGS`, `SAMPLE_DATA_SETS`): the data the panels were captured over, which the A-data suite installs on demand.

- **Cases** (`listGateCases`): every fixture, in light and dark. `kibanaTables` gives Kibana's own inspector tables, with columns keyed by their ES|QL names as the ES|QL search returns them. `kibanaChart` gives what Kibana drew. `kibanaChartSize` gives the size it drew at.
- **A-data** (`compareTables`): our pipeline's `Datatable` against Kibana's. Columns match by id and type, and rows must match value for value in the same order. ISO and epoch dates compare as the same instant, and reordered rows are reported as such. `datatableFromChartData` rebuilds a materialized chart's table from its columns' Kibana `source`. The on-demand FTR suite in `x-pack/platform/test/isomer_gate_a` seeds the data and runs it.
- **A-visual** (`compareCharts`): one normalized shape for Elastic Charts' `DebugState` (`normalizeDebugState`), the DOM Kibana renders a metric into (`normalizeMetricReadings`), and an Isomer Scene (`normalizeScene`). The other chart kinds normalize to named lists of flat records (`src/records.ts`): slices by depth, name and value (a waffle's squares once each), heat map cells by x and y, the gauge with its bands and ticks, words by text, the table's headers and cells, the legacy metric's tiles. A list one side doesn't report, such as a legend `DebugState` leaves out, isn't compared. An Isomer engine's slice keys and heat map positions read as the values they stand for. Spec ids and keys are dropped, colors become lowercase hex, and series are grouped by mark. Labels, names, colors, values and order must match exactly. Geometry (gridlines, paths) is compared only where both sides report it, within a pixel tolerance. Each difference reads like a review comment, such as `legend item 1 color "#16c5c0" vs "#54b399"`.
- **Engines** (`runGateAVisual`): compares a case's Scene, and then what a `GateAEngine` (such as headless Elastic Charts, `createElasticChartsHeadlessEngine`) draws from it at Kibana's size, with what Kibana drew. Tables and legacy metrics are drawn by the charts pack itself, not Elastic Charts, so only their Scenes are compared.

The Lens materializer's Scene-level run is `x-pack/platform/plugins/shared/isomer/server/materialize/lens/gate_a_visual.test.ts`. It pins each case's differences in `gate_a_visual.differences.json`, so any change fails until the file is regenerated with `UPDATE_GATE_A=true node scripts/jest <that test>`.
