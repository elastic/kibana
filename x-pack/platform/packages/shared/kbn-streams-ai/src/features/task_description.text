Task: Create a system prompt for an LLM to extract "features" from log data.

## What are Features?
Features are stable facts about real system components that are explicitly supported by log evidence. The primary focus is on identifying **entities** (what distinct components exist) and **dependencies** (how they are connected), supplemented by standalone **infrastructure**, **technology**, and **schema** features.

**Required BaseFeature schema fields** (include every field in each feature):
- `type` (string): "entity", "infrastructure", "technology", "dependency", or "schema"
- `subtype` (string): categorization within the type (e.g. `service`, `database`, `cloud_deployment`, `programming_language`)
- `id` (string): unique concise identifier for deduplication
- `title` (string): very short human-readable title for UI display
- `description` (string): A summary of what this feature represents
- `properties` (object): Stable, low-cardinality properties for deduplication (include at least one)
- `confidence` (number): 0-100 score
- `evidence` (array of strings): Supporting evidence from logs
- `evidence_doc_ids` (array of strings): Elasticsearch document `_id` values of sample documents that directly support the evidence
- `tags` (array of strings): Descriptive tags
- `meta` (object): High-cardinality or variable data; can be empty {}

## Feature Types
- **entity** (PRIMARY): High-level, stable system components (services, databases, queues, caches, API gateways, etc.)
  - Each entity carries relevant technology and infrastructure context in its properties/meta
  - Focus on high-level components rather than individual instances (pods, containers, hosts), keeping features stable as instances change
  - Only create when there is sufficient evidence; acceptable to omit when evidence is ambiguous
  - Add a `filter` by default when a stable, selective field-value pair is available
  - Filters use only `{field, eq}`, `{and: [...]}`, or `{or: [...]}` equality forms. Prefer the simplest selective condition so later sampling can target the component; use stable values and support every field/value with evidence
  - Keep entity identification rules generic rather than tying them to specific technologies or patterns
- **infrastructure**: Cloud providers, container orchestration, operating systems, networking
- **technology**: Programming languages, web servers, databases, libraries, frameworks
- **dependency**: Relationships between components (service-to-service calls, database connections, API integrations)
- **schema**: Log schema family (ECS, OTel, or custom) inferred only from field names and structure in `sample_documents`. Keep `properties` short (`schema_family`, optional `ecs_version`). When multiple schema families are evident, emit one feature per family.

## Naming Conventions
- Use **generic subtypes** with specific values in the properties object
  - Good: `{subtype: "service", properties: {name: "order-service"}}`
  - Bad: `{subtype: "order_service", properties: {}}`
- Use snake_case for subtypes; put specificity in `properties`, not in `subtype`
- ID rules: lowercase hyphenated, name as it appears in logs; exclude versions, build hashes, image tags, and instance ids so ids remain stable

## Properties vs Meta Field Usage
`properties` holds stable, low-cardinality facts for deduplication. High-cardinality or variable data goes in `meta`.

**Use `properties` for**: entity name, cloud provider, technology/library name, protocol, major/normalized version, stable service names in dependencies.

**Use `meta` for**: regions/AZs, hostnames, instance/pod/container IDs, IPs, URLs/paths, request/trace IDs, endpoint lists, build metadata, contextual notes.

**Conflict & cardinality rules**:
- If multiple values are observed for the same property, prefer the most frequent in `properties` and record alternates in `meta.observed_*` with evidence.
- Merge features that differ only by high-cardinality metadata and store varying details in `meta`.

## Inference, Confidence, Evidence & Versions
- Allow **one-level inference** from strong patterns with lower confidence; tag with `"inferred"` and explain in `meta.note`
- Accept features with confidence ≥ 30 if evidence supports them
- Confidence bands: 90–100 explicit; 70–89 strong patterns; 50–69 some ambiguity; 30–49 weak inference (include the `"inferred"` tag)
- Provide 2–5 short evidence strings per feature (`field.path=value` preferred); deduplicate by meaning; diversify aspects covered
- `evidence_doc_ids` is the minimal set of sample-document `_id` values covering the evidence; use `[]` only when no `_id` is available or evidence is aggregate/system-wide
- Version formatting: normalized numeric in `properties.version`; labels/codenames/build metadata in `meta.raw_version`

Schema note: the finalize schema must not add hard bounds that reject an otherwise usable payload (no `maxItems`/`minItems` on `evidence`, no `oneOf` on `filter`, and no newly required optional fields). Express those as guidance here and enforce them in code.

## Deduplication (single section)
State each rule once under one Deduplication heading covering:
1. **Consolidate vs separate**: consolidate when properties belong to the same logical component; separate distinct concerns; emit one feature per real-world component
2. **`previously_identified_features`**: reuse exact id on match; a version difference does not create a new feature; only re-emit when current docs add new information
3. **`known_feature_ids`**: authoritative inventory for whether an id already exists (including ids outside the detailed previously-identified subset)
4. **`search_similar_features`**: use only when candidate is not in `known_feature_ids`; reuse returned id only when same real-world thing and same type

## Excluded Features
If `excluded_features` are provided, suppress only the exact same real-world component and only when 100% certain. Report each skipped match in `ignored_features` (`feature_id`, `feature_title`, `excluded_feature_id`, `reason`).

## Input Context
The LLM receives:
- sample_documents: Sample log documents (typically 20 examples)
- previously_identified_features / known_feature_ids / excluded_features when present

The runtime may append grounding instructions and tools for memory and prior Significant Events. Keep the base prompt compatible with those instructions without duplicating them.

## Output Format
Return features via the finalize_features tool (call exactly once).

**Success criteria** (bullet list, not prose restating the schema):
- Prioritize entities, then dependencies, then standalone infrastructure/technology/schema
- Extract all evidenced features at/above the threshold; prefer fewer, higher-confidence features over speculative ones
- Entity threshold + filter defaults as above
- Dependency anti-spam: explicit relationship evidence only; aggregate/cap endpoints in `meta.endpoints`
- Schema: one feature per family; short properties; evidence only from `sample_documents`

## Examples to Include
One complete JSON example per feature-type family, plus one indirectly-inferred case (6 total), each containing every schema field:
1. Entity with filter (service + technology context)
2. Infrastructure showing properties vs meta (cloud provider vs regions/AZs)
3. Technology with version
4. Dependency with endpoint aggregation in meta
5. Schema (short properties)
6. Technology inferred from stack-trace patterns: low confidence, `"inferred"` tag, inference explained in `meta.note`

Keep every example internally consistent: each value in `properties` and `meta` must be supported by its example evidence.

Example confidence values must demonstrate the confidence bands, not just the top one: features named by explicit identifiers score high, while features inferred from structure or patterns (schema families, dependencies, technologies from stack traces) score lower.

Example evidence must obey the Evidence rules it is meant to teach — diversify the aspect each line covers instead of repeating one relationship with a different path.

Beyond these, do not add variants that only restate Naming or Deduplication rules.

## Prompt Structure
1. Opening: define features, primary goal (entities + dependencies), required fields
2. Feature Types (five types; entity primary)
3. Entity Extraction Guidelines (filters, evidence, generic rules)
4. Naming Conventions
5. Properties vs Meta Fields
6. Inference & Confidence
7. Evidence & Versions
8. Deduplication (consolidation + previously identified + known ids + semantic search — one section)
9. Excluded Features
10. Examples (6: one per type family plus an inferred case)
11. Success Criteria bullets
12. Closing: build one deduplicated list, call finalize_features exactly once

Each input-dependent section opens by naming the input it applies to ("When `previously_identified_features` is provided"), so no section needs a trailing "if empty or absent, ignore this" line. Assembling these sections conditionally at runtime would drop them from first-pass calls entirely; that is tracked separately and must not be assumed here.

## Style Requirements
- Keep prompt concise; state each rule once
- Use clear, directive language (imperatives: "Extract", "Consolidate", "Tag")
- Use markdown headers (##) for major sections
- Format examples as complete JSON objects in code blocks
- Every example title like "Example 1 — Entity with filter"
- Keep entity rules generic rather than tying them to specific technologies or log formats
