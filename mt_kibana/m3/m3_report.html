Multi-tenant Kibana hackathon · Milestone 3

One Kibana, three projects, behind the real Cloud Proxy

A single Kibana process runs in a dev MKI cluster behind the serverless Cloud Proxy. Each project's hostname reaches that one Kibana, and Kibana sends the request to that project's Elasticsearch. Every claim below is checked from both sides: what Kibana returns through the proxy, and what each Elasticsearch cluster says when asked directly.

What runs where

Methodology

The goal was to put M1/M2's multi-tenant Kibana on the real request path: client hostname → Cloud Proxy → one Kibana Deployment → that project's Elasticsearch. The parts that decide routing and isolation are the real production components. Parts that the devenv couldn't provide are stand-ins, and the table says which is which.

PieceHow it's set up
Cloud ProxyrealThe devenv's own serverless ingress-proxy, unmodified.
Multi-tenant routereal mechanismA Service labeled is-multi-tenant-service and application-id: mtkb, which is how the proxy discovers multi-tenant backends (read from elastic/proxy).
Per-project Ingresshand-writtenregional-network-controller normally writes these from an AppNetwork. The proxy only reads their annotations, so deploy.sh writes them.
KibanaPR imageThe branch built by CI (kibana-serverless-pr:pr-302955-26d59c7012d5), one pod, run in stateful mode like M1.
Elasticsearchstand-inThree single-node stateful clusters run by the devenv's ECK operator, with made-up 32-hex project ids. Real serverless projects couldn't be used (see below).
Credentialsreal patternKibana uses each cluster's elastic/kibana service-account token, the same kind project-controller gives a real project's Kibana. TLS to every cluster is verified against its own CA.

How each claim is verified

  • Two independent views. Every result Kibana returns through the proxy is compared with what the Elasticsearch cluster reports when queried directly from inside its own pod (kubectl exec), which bypasses both the proxy and Kibana.
  • Kibana's own record. Kibana's per-tenant query logger (elasticsearch.query.tenant-<projectId>) is on, so its log names the tenant client behind every call.
  • Fresh data each run. The demo writes a new marker (mt-demo-HHMMSS) every time, so a pass can't come from an earlier run's data.
  • Negative cases. A spoofed project header, another project's credentials, and an unknown project id must all fail in the expected way.

Repeat it or demo it

The scripts live in mt_kibana/m3/ on the hackathon branch. Run everything from the repo root. A fresh setup takes about 2 hours, almost all of it waiting for the devenv; once it exists, the clusters and Kibana take about 15 minutes.

  1. Prerequisites. devctl installed and logged in to docker.elastic.co. Connect the Aviatrix VPN, then log in to Teleport. preflight.sh checks every tool and login and says how to fix anything missing. 
    tsh login --proxy=teleport-proxy.staging.getin.cloud --auth=okta
mt_kibana/m3/preflight.sh
  2. Get a devenv. Use a direct one: a pooled devenv came with a broken CosmosDB account. It only needs the Cloud Proxy and the ECK operator, not working serverless projects. 
    devctl create --direct --cosmos-rbac --follow
devctl update-kubeconfig <name> && kubectl config use-context <name>-<suffix>
  3. Create the three clusters. Waits for green, creates an elastic/kibana token in each, and records ids, tokens, cluster_uuids and CAs in .es/mt/m3/ (gitignored). 
    mt_kibana/m3/eck.sh create
  4. Deploy Kibana. Initializes tenants a and b with a one-off single-tenant Kibana Job (like M1's init_tenant.sh), then deploys the multi-tenant Kibana, its Service and one Ingress per project. 
    export KIBANA_IMAGE=docker.elastic.co/kibana-ci/kibana-serverless-pr:pr-302955-26d59c7012d5
mt_kibana/m3/deploy.sh
  5. Prove it. smoke.sh is the short pass/fail test. demo.sh is the narrated version above; with DEMO_PAUSE=1 it waits for Enter between steps, for presenting live. Both can be rerun at any time. 
    mt_kibana/m3/smoke.sh
DEMO_PAUSE=1 mt_kibana/m3/demo.sh
  6. Optional: show the proxy headers. Deploys the echo backend for claim 6. 
    kubectl apply -f mt_kibana/m3/route_test.yaml
  7. Clean up. 
    kubectl delete ns mt-kibana mt-route-test
devctl destroy <name>

The devenv auto-hibernates; run devctl wake <name> before a demo. The clusters store data on emptyDir, so if an ES pod has restarted, rerun eck.sh delete, eck.sh create and deploy.sh.

Why not real serverless projects

  • QA projects can't be tenants. Serverless Kibana calls internal APIs such as _nodes, which serverless Elasticsearch allows only with operator privileges. Only the elastic/kibana service-account token has them, and a project's admin user can't create one.
  • Devenv projects would get that token, but they never got Elasticsearch in our devenvs. A pooled devenv had no control-plane CosmosDB account. A direct devenv was missing the OtelDeliveryConfig CRD, which we installed by hand. After that, global-escluster-controller never created a cluster.

Findings and limits

  • Routing is safe by construction at the proxy. The proxy overwrites the project and organization headers and rejects unknown ids, so Kibana's 400 guard for unknown projects only catches drift between the Ingresses and tenants.yml.
  • The Service selector must be exact. At first the ES pods carried the same app.kubernetes.io/name label as Kibana, so the proxy route had three ES pods as extra endpoints, and the first smoke test passed anyway. The Service now also selects on component: kibana, and demo step 1 checks that Kibana is the only endpoint.
  • One CA list for every tenant. Tenant clients inherit elasticsearch.ssl from the base config, so every cluster's CA is trusted for every tenant.
  • Per-process settings. server.publicBaseUrl, the serverless project id and similar values still have one value per Kibana process.
  • Tenant init is manual. Each tenant needs a single-tenant Kibana boot before the multi-tenant Kibana can serve it.
  • No browser path yet. There's no DNS for these hostnames, the proxy's wildcard cert doesn't cover *.mtkb.<domain>, and M2 notes that browser login for non-home projects fails. The proof uses curl --resolve with TLS verified against a name the cert covers.
  • Stateful, not serverless. Kibana runs without serverless: es, as in M1. Running in serverless mode also needs UIAM configured.
