## Summary

- Add **`ops.eluHistory.algorithm`**: `ema` (default, matches `main`) or `time-weighted-ema` (opt-in).
- Unify ELU history smoothing in **`createExponentialMovingAverage`**: both algorithms share **sample-count warm-up** (same as `main`), then exponential smoothing. Only **α** differs after warm-up.
- **`time-weighted-ema`:** after warm-up, `α = 1 - exp(-sampleGapMs / period)` where `sampleGapMs` is the monotonic gap since the previous sample (`performance.now()`).
- **Enable the HTTP circuit breaker by default:** `server.rateLimiter.enabled: true`, `elu: 0.8`, `term: medium` (30s EMA window).
- Same smoothed values feed the HTTP rate limiter (`getEluMetrics$`), **`GET /api/_elu_history`**, and autoscaler targets on `.history.long`.

**Default ELU smoothing stays `ema`** (`ops.eluHistory.algorithm`). Rate limiter defaults change from disabled → enabled at `0.8/medium`.

Addresses elastic/kibana-team#3969. Rollout plan: elastic/kibana-team#3968.

Assisted-by: Cursor (Composer 2.5)

## Why the formula change matters

Both old and new logic use exponential smoothing once the warm-up window is full:

`EMA_new = α × sample + (1 - α) × EMA_previous`

Warm-up (startup) is unchanged from `main`: for the first `period / ops.interval` samples, emit the accumulating mean `(sample × interval) / period`. Time weighting applies **only after warm-up**. The first post–warm-up step intentionally seeds from the **current sample**, not the warm-up mean, so costly startup is not treated as sustained load.

The difference is how **α** is chosen **after warm-up**:

| | Old (main) | New (`time-weighted-ema`) |
|---|---|---|
| **α** | `1 - exp(-interval / period)` | `1 - exp(-sampleGapMs / period)` |
| **`interval`** | Fixed nominal spacing (`ops.interval`, default **5s**) | — |
| **`sampleGapMs`** | — | Monotonic ms since the previous sample |

With default settings (`ops.interval = 5s`, short EMA `period = 15s`):

### Example 1 — Normal 5s cadence (unchanged with default `ema`)

Sampler runs on time; gap ≈ 5s.

- `ema`: α = `1 - exp(-5/15) ≈ 0.28`
- `time-weighted-ema`: α = `1 - exp(-5/15) ≈ 0.28`

If `EMA_previous = 0.4` and the new ELU sample is `1.0`:

- Both: `0.28 × 1.0 + 0.72 × 0.4 ≈ **0.57**`

Regular sampling behaves the same.

### Example 2 — 15s event-loop block, one late sample (the bug)

The loop is blocked for ~15s. The `setInterval` callback cannot run; when it finally fires, ELU reports **1.0** for the whole elapsed window (raw ELU is correct). Suppose `EMA_previous = 0.4`.

**`ema` (main)** still uses `interval = 5s`:

- α ≈ **0.28** (as if only 5s had passed)
- `EMA_new ≈ 0.28 × 1.0 + 0.72 × 0.4 ≈ **0.57**`

**`time-weighted-ema`** uses `sampleGapMs = 15s`:

- α = `1 - exp(-15/15) = 1 - e⁻¹ ≈ **0.63**`
- `EMA_new ≈ 0.63 × 1.0 + 0.37 × 0.4 ≈ **0.78**`

The late high-ELU reading moves the average **~37% more** toward 1.0, matching the fact that the sample represents three missed 5s intervals of stall.

### Example 3 — Back-to-back samples (`sampleGapMs = 0`)

Two samples arrive in the same tick (no time elapsed).

- `ema`: α ≈ 0.28 on every sample regardless of timing
- `time-weighted-ema`: α = `1 - exp(0) = 0` → EMA stays at `EMA_previous`

Avoids double-counting when multiple readings land at once.

## Enable time-weighted smoothing (cohort / opt-in)

```yaml
ops:
  eluHistory:
    algorithm: time-weighted-ema
```
