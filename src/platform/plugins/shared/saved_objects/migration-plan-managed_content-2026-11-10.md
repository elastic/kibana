# Managed content FTR migration plan

Source: `x-pack/platform/test/functional/apps/managed_content/{config.ts,index.js,managed_content.ts}`. This config inherits the broad x-pack functional config and runs in stateful CI. No matching serverless FTR suite was found.

**Ownership:** There is no single managed-content UI plugin. `content_management` has API tests but does not implement these app UI rules. `kbn-managed-content-badge` supplies the badge, and `saved_objects` supplies the save modal; each app decides when to use them. Keep the Scout tests with the app whose wiring they verify. This plan lives beside the shared modal tests for reference, not as the destination for the cross-app Scout specs.

1. **Keep the shared rule in unit tests.** `saved_object_save_modal.test.tsx` already checks that enforced copy-on-save disables the switch and submits `newCopyOnSave: true`. Extend it only if a missing managed/unmanaged branch is found. Unit tests cannot prove that Lens, Discover, Visualize, and Maps pass the correct managed state to the modal.
2. **Move the four active app scenarios to Scout UI.** Put Lens under `x-pack/platform/plugins/shared/lens/test/scout/core/ui`, Discover under `src/platform/plugins/shared/discover/test/scout/core/ui`, and Maps under `x-pack/platform/plugins/shared/maps/test/scout/ui`. Visualize has no Scout UI suite yet, so scaffold one under `src/platform/plugins/shared/visualizations/test/scout/ui`. For managed and unmanaged saved objects, assert badge presence/absence and the save-as-new switch's checked/disabled state. Reuse Scout app page objects where available, with explicit assertions in the specs. These four FTR `it` blocks each become one independent Scout test.
3. **Cover the library separately.** Put the active Visualize Library scenario in the new Visualizations Scout UI suite. Check that the inspector's title and description are read-only for managed Lens, legacy visualization, and map items. A component test may cover the inspector's prop logic, but keep one browser check for the library-to-inspector wiring.
4. **Make setup isolated and portable.** Port `managed_content.json` and the `logstash_functional` ES archive into Scout fixtures or equivalent API setup; use a dedicated space and clean up all created objects. Start with stateful parity, then enable serverless only after checking these apps and fixture imports there. Prefer Scout's default server configuration; the FTR leaf config adds no server arguments or roles.
5. **Defer the two skipped dashboard scenarios.** They are already disabled pending issue #190138. Do not count them as migrated coverage. Reassess the fix and existing Dashboard unit/Scout coverage before re-enabling or adding new tests. Once the five active scenarios pass, remove the FTR suite, its config, and its stateful CI manifest entry.

**Needs verification during implementation:** whether existing Scout page objects cover each interaction; whether the Visualizations Scout scaffold can use default servers; whether the fixture can be imported in a space without changes; whether serverless supports the same managed-content flow. These affect setup and deployment tags, not the active scenario inventory.
