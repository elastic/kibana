# FTR wait optimization failure log

This log records failures encountered while developing [PR #296962](https://github.com/elastic/kibana/pull/296962). Use it with the [optimization catalog](wait_optimization.md) when changing shared FTR helpers. The entries describe failure types, rather than counting every downstream failure from a broken setup step.

Each CI reference points to the observed attempt, including attempts that subsequently passed. A passing retry alone does not establish a root cause. Entries marked **fixed** have a corresponding implementation change; entries marked **unresolved** or **retry passed** retain the limits of the evidence. Local and FAST_3G observations are listed separately.

## Checks to run before submitting another optimization

1. Audit every caller of a changed shared helper, including negative actions, repeated calls to open/ensure helpers, inline editors, remote/CCS paths, accessibility tests, and applications with fixed chrome. Preserve existing timeout and matching contracts unless a caller migration is intentional.
2. Give each action an explicit precondition and completion signal. Derive selectors from the component or its registered constants, and verify them in a browser run. Perform the mutation once; retry fresh assertions. Verify that old state cannot satisfy the condition and that an empty collection cannot make an assertion pass vacuously.
3. For low-level helpers, cover delayed readiness, stale-element recovery, explicit zero-timeout behavior, restoration of implicit timeouts after errors, and permanently missing/disabled controls where relevant. Run the existing focused regressions rather than reproducing implementation details in tests.
4. Run complete affected configs, with hooks and cleanup, and compare test counts to the baseline. Include at least one representative caller outside the initial team when changing a shared contract. Failed or interrupted recordings are diagnostics, even if a runner exits zero.
5. Run scoped lint/types and affected unit tests using the pinned Node version. Rebuild browser plugins after product-source edits; cached bundles can otherwise test old code. Record the delayed-network scope and retain existing deadlines.
6. When CI fails, capture the first failing action, expected/actual state, artifacts, commit, and job link. Separate subsequent setup cascades, known-main failures, and infrastructure failures. A successful retry is an observation, not a fix.

Add future entries with the observed CI job, status, established cause or remaining uncertainty, implementation reference, and a concrete local check. Update pending local entries after their full-config reruns.
