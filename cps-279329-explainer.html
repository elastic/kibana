CPS Alerts Page — Data View Hard Failure

elastic/kibana#279329  ·  assigned @lgestc  ·  Team:Threat Hunting:Investigations
A fieldCaps request fans out to every linked CPS cluster with no isolation. When one cluster is in brownout, every failure class is silently laundered into a 404, which the UI treats as "no fields found" and renders a full-page error — even though alerts live only on the origin cluster and are fully available.

Phase 1 — Request shaping (browser · data-views client)

Before a single byte leaves the browser, the data-views client decides how to ask for fields. Because CPS is active, it reads the global project routing expression and embeds it in the request body — which silently upgrades the call from a cacheable GET to a POST. This method switch is the root cause of the divergence from the manual DevTools fetch.

The data-views client has no per-view routing override, so it falls back to the global CPS value. That value is always _alias:* — "query every linked project" — regardless of whether the data view's indices actually live on any of them. Alert indices exist only on the origin cluster, but there is nowhere in DataViewSpec to express that constraint.

Phase 2 — Fan-out (Kibana server → Elasticsearch)

    
The Kibana route handler passes the routing value straight to the Elasticsearch fieldCaps API. Kibana's CPS middleware sees the body already has a value and leaves it alone — skipping its normal behaviour of scoping the query to the current space. Elasticsearch then fans the request out to every cluster the expression matches, and waits for all of them before returning.

    


      

        
        
The route handler reads project_routing from the POST body and passes it verbatim to the field-caps fetcher. There is no server-side scope check, no override for known-local data views, and no fallback to the space's own routing expression. Whatever the client sent is what Elasticsearch will receive.

        

          

            fields_for.ts:183, 211[copy]

          

          

            The route passes projectRouting verbatim to getFieldsForWildcard.
            No server-side override or scope check here.
          

        

      


      

        
        
Kibana's CPS middleware intercepts every outgoing ES call. Its normal job is to inject the space's Named Project Routing Expression (NPRE) — a value like @kibana_space_default_default that resolves to the space's configured scope. But injectProjectRoutingBody only injects when the body has no existing value. Since the body already has _alias:*, the middleware is a no-op and the request goes to ES scoped to all clusters.

Phase 3 — Error laundering (server catch block) ← active in brownout

    
ES returns an error after 30 seconds. From here, a cascade of over-broad catch blocks discards all diagnostic information: a timeout becomes a Boom with no error code, the Boom becomes a bare HTTP 404 with no body, and the client receives a response it cannot interpret as anything other than a generic hard failure.

    


      

        
        
The ES client throws a timeout error. callFieldCapsApi only special-cases index_closed_exception and cluster_block_exception; everything else goes to convertEsError. That function assigns the no_matching_indices code only to index_not_found_exception errors. A timeout gets Boom.boomify() — a generic HTTP error wrapper with no meaningful code attached. The error type that the rest of the stack would need to handle gracefully is already gone.

Phase 4 — UI collapse (Security alerts page) ← hard failure visible to user

    
The generic Error from Phase 3 travels through two nested catch blocks in the data-views layer. The first rethrows after toasting; the second toasts again and then swallows the error, returning an empty DataView as if nothing went wrong. The hook sees a successful resolution, sets status = 'ready', and the Security UI — designed to flag empty DataViews — renders a full-page "Unable to retrieve the data view" error.

    


      

        
        
The generic Error reaches refreshFieldSpecMap's catch. Only DataViewMissingIndices is handled gracefully there; everything else fires onError (danger toast #1) and rethrows. The rethrow propagates to initFromSavedObject's outer catch, which fires onError a second time (danger toast #2) — and then does not rethrow. Execution falls through, fields and indices stay empty, and a DataView object is constructed and returned as if the call had simply found no data.

Four independent bugs in the swiss-cheese chain



  

    
1

    

      
No per-DataView project routing override

      
DataViewSpec has no projectRouting field.
      The security alert data view (origin-local indices) cannot opt out of global _alias:* routing.
      Every fieldCaps call fans out to all clusters even when there is nothing on linked clusters.

    

  

  

    
2

    

      
fields_for.ts maps every error class onto 404

      
Timeouts, connection errors, and "no matching indices" all become
      response.notFound(). An infrastructure failure is indistinguishable from a data query
      that matched nothing. No retry-with-origin is attempted.

    

  

  

    
3

    

      
Bare notFound() carries no body — client cannot classify it

      
The client distinguishes "no matching indices" by looking for
      attributes.code==='no_matching_indices' in the body. A bodyless 404 silently becomes a
      generic Error and propagates as a hard failure rather than an expected condition.

    

  

  

    
4

    

      
initFromSavedObject swallows the error, returns an empty DataView

      
Two onError toasts fire, then the error is swallowed.
      The caller receives a valid-looking DataView with matchedIndices=[] — no throw, no
      status='error'. The UI cannot distinguish a cluster failure from "no data".

    

  

  

    
5

    

      
Page filters make a second, independent field-caps trip to the same brownout

      
AlertFilterControls → useAlertsDataView → dataViewsService.create()
      performs its own _fields_for_wildcard call with global routing — hitting the paused cluster a
      second time. It survives only by accident: refreshFields swallows the error when displayErrors
      is true (data_views.ts:708–734), so create() still resolves — with an empty field list.
      The page-filter option lists come back empty and the filter row shows a spinner for the full 60–90 s window.
      Layers B and C each patch one call site; Layer A is the only fix that covers both.

      Root fix
      Layer A — Per-DataView projectRouting
    

    

      Add projectRouting?: string to DataViewSpec, DataViewAttributes, and AbstractDataView,
      following the allowHidden precedent (common/types.ts:168/:570, abstract_data_views.ts:137).

Risks & open questions

        
    
          
  • Backfill needed for existing saved objects. Alert data view saved objects already on disk won't carry projectRouting until the backfill path runs on the next Kibana restart. The fan-out behaviour applies in the window before restart — but the existing name-fixup pattern (index.ts:150–154) gives a clear template: read with getDataViewLazy (no field-caps fetch), set the attribute, call updateSavedObject.
    • 
          
  • Coverage is narrow. This fixes the security alert and attack data views. Any other data view backed by origin-local indices remains vulnerable unless its creation code is similarly updated.
    • 
          
  • API surface change + CM schema. DataViewSpec gains a new optional field. Code that clones specs should be audited. The CM schema must be extended to avoid unknowns: 'forbid' validation failures on create/update.
    • 
        

      

    

  

  

    

      Band-aid
      Layer B — Server-side origin fallback on cross-cluster failure
    

    

      Stop collapsing every failure class into 404. Add isEsTransportFailure to errors.ts
      alongside the existing isNoMatchingIndicesError helper, and use it in convertEsError
      to stamp a machine-readable code: 'es_unreachable' on transport failures (rather than boomifying them to
      a generic 500 that fields_for.ts then launders into a 404).
      On cross-project routing, bound the first attempt with a configurable timeout + maxRetries: 0,
      then fall back to projectRouting:'_alias:_origin' on failure and return origin fields with response
      header x-kbn-fields-degraded: cross_project_unavailable.

Risks & open questions

        
    
          
  • Budget reduces worst-case hang. With maxRetries:0 + a configurable timeout (default 10 s), the cross-project attempt costs at most 10 s rather than 90 s, then falls back immediately. Much better than today — but the fallback still adds origin-fetch latency. Any consumer on a cross-project data view sees this.
    • 
          
  • Origin retry can also fail. If the origin cluster is unavailable, the retry fails too. The user now gets a proper status code and machine-readable error rather than a bare 404, but the page still doesn't load.
    • 
          
  • x-kbn-fields-degraded header is currently unread. No existing client code inspects this header. Until a consumer is added (as part of Layer C's callout messaging), the degradation signal only appears in server logs. Layer C's callout fires on !hasMatchedIndices() regardless; the header allows it to give a more precise message once B lands.
    • 
          
  • Status-code change is a contract change. fields_for.ts is an internal route, but any caller treating any 404 from it as "no indices" now sees 503/500 for transport failures. The data_views_api_client gate already requires attributes.code==='no_matching_indices' so it is safe; FTR/Scout api-integration tests asserting 404 for timeout scenarios need updating.
    • 
        

      

    

  

  

    

      Band-aid
      Layer C — Graceful degradation in wrapper.tsx

Risks & open questions

        
    
          
  • Cannot cleanly distinguish brownout from legitimately empty indices. Both produce status==='ready' && !hasMatchedIndices(). The callout fires in both cases. A fresh deployment with no alert data yet would show a misleading warning. Mitigation: make the callout copy specific — show dataView.getIndexPattern() and a link to Data View Management so the analyst can tell the difference. Layer B's x-kbn-fields-degraded header allows a more precise message once that lands.
    • 
          
  • Genuine misconfiguration becomes less visible. A data view whose pattern truly matches nothing (typo'd index, deleted index, revoked privileges) currently produces an unmissable red page. After C it produces an amber callout plus zero rows. The analyst must connect the two signals. Non-dismissible callout text that includes the pattern string is the recommended mitigation.
    • 
          
  • Warning callout wording can be improved once Layer B lands. Without B's header the callout cannot yet say "linked project unavailable" with certainty. The initial wording should be cautious ("Some fields are unavailable — alerts are still shown"). Refine after B ships.

Layer interaction — recommended landing order: C → B → A

    
Why C first? Not intuition — code evidence.
    The alert rows are already fetched via ruleTypeIds + projectRouting={PROJECT_ROUTING.ORIGIN}
    at alerts_table/index.tsx:473, independently of the DataView's field list.
    The brownout ate the field metadata, not the data.
    C turns a full-page red error into a working alert table with a warning callout — analyst triage is restored.
    C also carries the browserFields={undefined} fix (Layer C above) that re-enables the shared table's own
    /internal/rac/alerts/browser_fields fetch, recovering the field browser and cell actions without B.
    C is ~20 lines in a single Security-owned file with zero platform surface area.

    
Why B second? B's primary job is not to make C work better — it is to fix the
    error-classification bug that affects every consumer of fields_for.ts, not just this page.
    It also bounds the worst-case brownout hang (configurable timeout + maxRetries:0 on the cross-project
    attempt) and provides the x-kbn-fields-degraded header that allows C's callout to say "linked project
    unavailable" with precision rather than "some fields unavailable" as a guess.
    B touches the data_views platform plugin and needs a new config key, so it lands in a separate PR.

    
Why A last? A is the root fix — it eliminates the fan-out entirely for the alerts data view,
    making B's retry path unreachable and C's degraded-state callout permanently quiet.
    Despite spanning two teams (data_views platform + security server), the code change is smaller than it looks:
    two one-line additions in data_views.ts plus spec/attribute plumbing and a CM schema line.
    No mapping change, no migration. A is also the only layer that covers bug #5 (the AlertFilterControls
    second field-caps trip) — C and B each patch one call site, while A patches both at once.
