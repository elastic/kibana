**Title:** [Alerting v2] Dispatcher: workflow dispatch fails with "no execution identity attached" when action policy API keys are UIAM keys
**Labels (suggested):** bug, Team:rna-project

---

## Description
In a UIAM-enabled serverless setup, the dispatcher cannot start the workflows of an action policy. The workflow execution is created as `FAILED` with `no execution identity attached`, so no notification is delivered.

Two separate problems have to be fixed. Fixing only the first one is not enough:

1. **Alerting v2:** the dispatcher sends the stored UIAM key in a format Elasticsearch cannot authenticate.
2. **Task Manager config:** once the first problem is fixed, scheduling the workflow still fails unless Task Manager is configured to handle UIAM keys (`xpack.task_manager.grant_uiam_api_keys`). We need a way to make sure that setting is correct wherever UIAM keys are used.

It is not yet clear whether the second problem only shows up on local serverless, or whether deployed serverless also needs a change (see Open questions).

## Steps to reproduce
1. Run local serverless Observability with UIAM (`pnpm es serverless --projectType=observability`, `pnpm serverless-oblt`), with `uiSettings.globalOverrides.alerting:v2:enabled: true`. Use a fresh environment (no stale data).
2. Create an action policy with a workflow destination.
3. Create an `alert` rule that breaches, so there are `type: "alert"` events in `.rule-events`.
4. Wait for the dispatcher tick (every 5s).

## Expected
The dispatcher schedules the workflow and the execution runs with the policy owner's identity.

## Actual
- The workflow execution is created as `FAILED` with `no execution identity attached`.
- Kibana logs show authentication errors against Elasticsearch for the policy API key (see Root cause).
- Rotating the policy API key (`_update_api_key`) does not help.

## Root cause

### 1. Wrong credential format in the dispatcher (verified)
- On UIAM-enabled deployments, `ApiKeyService.create` stores the policy key as `base64(id:essu_…)` (`server/lib/services/api_key_service/api_key_service.ts`, `grantAPIKeyAttributes`).
- `DispatchStep.craftFakeRequest` sends it as is: `authorization: ApiKey <stored value>` (`server/lib/dispatcher/steps/dispatch_step.ts`).
- Only the raw `essu_…` secret authenticates. With the base64 envelope, Elasticsearch looks the id up as a native API key, which fails (`API key: unable to find apikey with id …`). This is documented in `getUiamApiKeySecret` (`x-pack/platform/plugins/shared/task_manager/server/lib/api_key_utils.ts`), which Task Manager applies before building its own fake request.
- The workflows engine then cannot resolve a user (`getAuthenticatedUser`), so the execution is created with a missing identity (`build_workflow_execution_document.ts`).

### 2. Task Manager clones the key with the ES-only strategy (verified)
After sending only the secret, the next error is `status_exception: invalid API key credential: Illegal base64 character 5f` (`5f` is `_` from `essu_`). This comes from Task Manager:
- The workflows engine schedules each execution with `taskManager.bulkSchedule(tasks, { request, cloneApiKey: true })` (`workflows_execution_engine/server/plugin.ts`).
- Task Manager only uses its UIAM-aware strategy when `xpack.task_manager.grant_uiam_api_keys` is `true`. The default is `false` (`task_manager/server/config.ts`). With the ES-only strategy it clones through `cloneAsInternalUser`, and the native ES endpoint rejects raw `essu_` credentials (comment in `es_and_uiam_api_key_strategy.ts`).
- The `uiam_local` and `cps_local` Scout configs enable that flag explicitly. No `config/*.yml` file in the repo sets it, so a default `yarn serverless-oblt` does not have it.

The `uiam_local` Scout config also sets `--feature_flags.overrides.taskManager.provisionUiamApiKeys=true`. It has not been checked whether that flag is also needed here.

## Suggested fix

### Alerting v2 (applied locally, not committed)
- In `craftFakeRequest`, send `getUiamApiKeySecret(apiKey)` instead of the stored value. ES keys pass through unchanged.
- Add a unit test with a `base64(id:essu_…)` key that checks the `authorization` header.

### Task Manager setting (needs a decision)
The alerting v2 fix alone does not make dispatching work if Task Manager is not configured for UIAM keys. Options to evaluate:
- Enable `xpack.task_manager.grant_uiam_api_keys` wherever alerting v2 can mint UIAM keys (local serverless default config and, if needed, deployed serverless), so both sides always agree.
- Make the combination fail loudly instead of opaquely: when a policy key is UIAM but Task Manager cannot clone it, record a `dispatch_failed` entry with an explicit reason (today the symptom is the generic identity error).
- Document the required setting for local development.

## Acceptance criteria
- [ ] With UIAM enabled, an `alert` event matching an action policy results in a workflow execution that runs (not `FAILED` for missing identity).
- [ ] Policies using ES keys (stateful) behave as before.
- [ ] The Task Manager setting needed for UIAM keys is guaranteed by config (or the mismatch produces a clear `dispatch_failed` reason).
- [ ] Unit test covers the UIAM key format in `craftFakeRequest`.

## Open questions
- Is the Task Manager setting only needed because we run serverless locally (where the repo configs do not set `grant_uiam_api_keys`), or does deployed serverless also need a config change? The deployed serverless configuration is not part of this repo and has not been checked, so we do not know if `grant_uiam_api_keys` is already enabled there.
- If deployed serverless already has it enabled, the work is limited to the alerting v2 fix plus the local/default config for development. If it does not, the setting has to change in the deployed configuration too, and that needs the Task Manager owners.
- Is `taskManager.provisionUiamApiKeys` also needed? (see Root cause 2)

## Technical notes
- Task Manager builds its fake request with more context than the dispatcher: `spaceId`, `userName`/`userProfileId` enrichment and the external-key marker (`task_running/fake_request_factory.ts`). Aligning the dispatcher with it may be a separate improvement; it was not needed to explain this failure.
- Other places in alerting v2 that build a request from a stored key were not checked.
