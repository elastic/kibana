# Add `enabled` to Alerting v2 rules PUT upsert (#1134) — PR 1/2

## Summary
`PUT /api/alerting/v2/rules/{id}` cannot carry `enabled` state today: create always forces `enabled: true`, and replace always preserves the existing stored value, ignoring the executor task implications. This blocks a generated Terraform provider from creating disabled rules or toggling enabled state via PUT. Add optional `enabled: boolean` to a new PUT-only body schema, defaulting to `true` on create and preserving the stored value on replace when omitted. Companion PR ([.plan-add-enabled-alerting-v2-put-action-policies-1134.md](.plan-add-enabled-alerting-v2-put-action-policies-1134.md)) covers action policies separately.

## Decisions
- **Separate schema for PUT**, not a change to `createRuleDataSchema` (used by `POST /rules`). This keeps POST-create's implicit "always enabled" contract untouched and scopes `enabled` to the upsert body only.
- **Events:** on a PUT-driven enabled/disabled transition, emit both `ruleUpdated` (existing behavior, a PUT is a full replace) *and* the specific `ruleEnabled`/`ruleDisabled` event (matching what the dedicated `_enable`/`_disable` routes emit), so consumers listening for the specific transition still see it when it arrives via PUT.

## Steps
1. Add `putRuleDataSchema` in [rule_data_schema.ts](x-pack/platform/packages/shared/response-ops/alerting-v2-schemas/src/rule_data_schema.ts:739), built the same way as `bulkCreateRuleItemSchema` (line 940): `applyCreateRuleRefinements(createRuleDataBaseSchema.extend({ enabled: z.boolean().default(true).describe(...) })).meta({ id: 'alerting_put_rule' })`. Export `PutRuleData` / `PutRuleDataInput` types. Do not touch `createRuleDataSchema` or `createRuleDataBaseSchema` — leaves `IMMUTABLE_RULE_FIELDS` and POST-create untouched.
2. Update `UpsertRuleRoute` ([upsert_rule_route.ts](x-pack/platform/plugins/shared/alerting_v2/server/routes/rules/upsert_rule_route.ts:46)) to use `putRuleDataSchema` as the request body schema instead of `createRuleDataSchema`, and `PutRuleData` as the type passed to `RulesClient.upsertRule`.
3. In `RulesClient.createRule` ([rules_client.ts:618](x-pack/platform/plugins/shared/alerting_v2/server/lib/rules_client/rules_client.ts:618)), accept an optional `enabled` on its input (defaulting to `true` for the plain POST path where `CreateRuleData` has no `enabled` field) and pass it through instead of the hardcoded `true`. `upsertRule`'s create-path call (line 1792) passes `data.enabled` from the parsed `PutRuleData`.
4. Fix the resulting type plumbing: `prepareRuleForCreate`'s `data` param ([rules_client.ts:395](x-pack/platform/plugins/shared/alerting_v2/server/lib/rules_client/rules_client.ts:395)) keeps taking `CreateRuleData` (no `enabled`) with `enabled` passed as its own field, unchanged from today — no `CreateRuleData` type fallout since `enabled` now only lives on the new `PutRuleData` type, not on `CreateRuleData`. Confirm `bulkCreateRules` ([rules_client.ts:660](x-pack/platform/plugins/shared/alerting_v2/server/lib/rules_client/rules_client.ts:660)) is unaffected (still uses `bulkCreateRuleItemSchema`/its own `enabled` field).
5. In `RulesClient.upsertRule` ([rules_client.ts:1778-1855](x-pack/platform/plugins/shared/alerting_v2/server/lib/rules_client/rules_client.ts:1778)):
   - Change `data`/`parsed` typing to `PutRuleData`, parsed via `putRuleDataSchema`.
   - Replace path: compute the new stored `enabled` as `parsed.enabled ?? existingAttrs.enabled` instead of the hardcoded `existingAttrs.enabled` (line 1810).
   - Use the new enabled value (not the old one) for `validateSchedule`'s `checkLimit` (lines 1818-1824).
   - Branch task scheduling on the enabled transition: schedule the executor task when transitioning disabled→enabled (reuse `scheduleRuleExecutorTask`, same as `enableRule`), remove it via `taskManager.removeIfExists(getRuleExecutorTaskId(...))` when transitioning enabled→disabled (same as `disableRule`), and otherwise preserve current unconditional-schedule behavior only when the rule stays enabled. This also fixes the pre-existing bug where replace unconditionally reschedules the task even for rules staying disabled.
   - After writing the new attrs, emit `ruleUpdated` as today, and additionally emit `ruleEnabled`/`ruleDisabled` when `parsed.enabled` is present and differs from `existingAttrs.enabled` (mirror the payload shape used in `enableRule`/`disableRule`, lines 975 and 1022).
6. Add unit tests for `upsertRule`/`createRule` in [rules_client.test.ts](x-pack/platform/plugins/shared/alerting_v2/server/lib/rules_client/rules_client.test.ts) covering: create-disabled, replace-enable (task scheduled + `ruleEnabled` emitted), replace-disable (task removed + `ruleDisabled` emitted), omit-preserves-existing (no extra event).
7. Add/extend Scout API tests in [upsert_rule.spec.ts](x-pack/platform/plugins/shared/alerting_v2/test/scout_alerting_v2/rules/api/tests/upsert_rule.spec.ts) for the same scenarios end-to-end.
8. Add schema parse tests for `putRuleDataSchema` in [rule_data_schema.test.ts](x-pack/platform/packages/shared/response-ops/alerting-v2-schemas/src/rule_data_schema.test.ts) (default `enabled: true`, explicit `true`/`false`, and that `createRuleDataSchema` is unaffected).
9. Regenerate OAS docs via `node scripts/capture_oas_snapshot.js` so `oas_docs/output/kibana.yaml` / `kibana.serverless.yaml` reflect the new PUT-only schema with `enabled`; update `upsert_rule_oas_example.ts` if desired (leave `create_rule_oas_example.ts` untouched since POST is unchanged).
